# MCU-сторона (GD32, Cortex-M4F): прошивка и UART-протокол

Тематическая справка по контроллеру самоката `xiaomi.scooter.5pro`
(MCU fw `0007`, образ `firmware_ota/c0f78c49…_mcu_xiaomi.scooter.5pro_v0007.bin`).

> **Источник истины — [`FACTS.md`](FACTS.md)** (раздел «MCU⇄BLE: UART-протокол»).
> Полные доказательства — исполнение настоящего `mcu_0007.bin` под Unicorn в
> `research/REPORT.md` §16, §22–§35. Ниже — константы и карта протокола.

---

## 1. Чип и роль

| Параметр | Значение | Источник |
|---|---|---|
| Ядро | Cortex-M4F (GD32; регистровая карта STM32F1-типа) | исполнение/дизасм |
| Роль | **BLDC-контроллер**: TIM1+Холл, ADC, мотор, батарея, RTC, режимы | дизасм |
| SRAM | ~20 КБ (векторная таблица: SP=0x20004E40) | исполнение |
| UART'ы к BLE | два: **USART3** @0x40004800 (двунаправленный) и **UART4** @0x40004C00 (только push MCU→BLE) | исполнение + живая линия |
| Бод-рейт | **19200 8N1** | живой поток (совпадает с bw-flasher) |
| Системный тик | ADC ISR `0x1a31c` ≈ 1 кГц (u64 времени @0x1e0); главный цикл связи `0x1dfd8` | исполнение |

**Слои (кто что делает):**
- **MCU** = поставщик сырых значений + исполнитель device-specific операций (RTC,
  конфиг-блобы, режимы). Данные-канал — НЕ siid/piid-диспетчер: ответы фиксированные.
- **Слой спецификации Mi Home (siid/piid, GATT) живёт в BLE-чипе** (APP-регион
  зашифрован). Телефон читает/пишет свойства у BLE-чипа, тот опрашивает MCU запросами
  `63 CMD` по USART3.
- Конфиг #3 (@0x16aa) — зашифрованный blob из Mi Home (S-box шифр, S-box'ы @0xa907/@0xab07),
  приходит при привязке/калибровке (REPORT §27).

## 2. Образ прошивки `mcu_0007.bin`

| Факт | Значение |
|---|---|
| Размер | 0x24D39 = 150 841 Б (упакованный образ) |
| Шифрование | **НЕ зашифрован** (энтропия 5.0–6.3, чистый Thumb-код) — только подписан |
| Подпись | Mijia RSA + сертификаты в OTA-конверте (маркер `TFOTA` + модель `xiaomi.scooter.5pro` @0x24807) |
| Версия | строка `0007` в заголовке @0x22 |
| Векторная таблица | смещение 0x1000 (SP=0x20004E40) |
| Точка входа C-main | **инжектируется из RAM** @0x20004e4c BLE-чипом (data-driven, REPORT §26) |

Не путать: шифрование есть лишь у BLE-образа (AES, ключ в OTP) — см. [`BLE.md`](BLE.md) §1.
MCU-образ предназначен для доставки **по воздуху** (подписанный контейнер + отдельные
MCU-опкоды DFU в приложении); прошивка по BLE реально работала — Mi Home обновил
0006 → 0007 (см. [`DFU.md`](DFU.md) §6).

## 3. Физический уровень

| Линия | Направление | Что ходит |
|---|---|---|
| USART3 RX (BLE→MCU) | BLE шлёт | телеметрия `74 …` + данные-канал `51-54/5a/64`; фреймер `0x1e480`, два кольца (шаг 0x96=150 Б): @0x881 телеметрия, @0xc05 данные-канал |
| USART3 TX (MCU→BLE) | MCU шлёт | ТОЛЬКО запросы `63 CMD CHK 9C` (планировщик `0x1f600`, описатель @0xa43): ≤1 байт/тик, кадр не чаще раза в 432 тика |
| UART4 TX (MCU→BLE) | MCU шлёт | ответы данных-канала + push `61 …` (отправитель `0x216e4`, кольцо @0x10b5, 8 слотов) |

Живая верификация (USB-TTL, 2026-08-21):
- формат push подтверждён байт-в-байт: `61 SUB LEN DATA[LEN] CHK 9E`,
  **CHK = Σ(все предшествующие байты) & 0xFF**, `0x9E = ~0x61`; длина переменная (LEN-байт).
- поток непрерывный, ~217 Б/с (~14.8 кадр/с); «паузы» в наивных чтениях — артефакт
  буферизации драйвера CH340 (чанки по 4 КБ).
- линия = **UART4** (100% push-кадры `61`, ноль запросов `63`) — односторонняя MCU→BLE;
  инъекция через неё невозможна (телеметрия `74` и запросы `63` живут на USART3).
- после подтягивания GND к пину BTN на плате поток появился (BTN — вероятно тестовый/
  отладочный пин; требует верификации).
- **Источник батарейных данных:** MCU шлёт запрос `63 44`, BLE-чип отвечает `74 44` —
  батарея/температура измеряются на плате RTL8762C (свой ADC), GD32 хранит и пушит.
- Мост: `tools/uart_telemetry.py --port COM3` — живой парсер push-кадров.

## 4. Кадры

```
BLE→MCU (USART3 RX):
  74 CMD LEN DATA[LEN] CHK 8B     ; данные: CMD ∈ {0x41..0x46, 0x48..0x4A, 0x60, 0x61}
  74 CMD 4F 4B CHK 8B             ; «OK»:   CMD ∈ {0x40, 0x47, 0x4B, 0x63}
  CHK = Σ(все предыдущие байты) & 0xFF;  0x8B = ~0x74 (комплемент синхро-байта)

MCU→BLE (USART3 TX):
  63 CMD (0x63+CMD) 9C            ; 0x9C = ~0x63; CMD ∈ {0x42..0x47, 0x4B, 0x63}
                                  ; 0x47 = RTC time-sync раз в 5 циклов;
                                  ; 0x4B/0x63 — форвард настроек из Mi Home

MCU→BLE (UART4 TX):
  LEN 64/65 SUB DLEN DATA CHK (0xFF−HDR)   ; ответы данных-канала
  61 SUB LEN DATA[LEN] CHK 9E              ; push статуса, период ~2.5 с (2560 тиков);
                                           ; гейт: флаг сессии @0x339 и mode @0x358 должны быть 0…
```

### Данные-канал приложения (BLE→MCU, USART3)
```
Path A (set): 51-54 SUB LEN DATA CHK TRAILER
Path B (get): 51-54 SUB (HDR+SUB)&FF TRAILER [DATA]
ВСЕГО 32 подкоманды (12 set + 20 get); заголовки 0x51..0x54 идентичны — ID канала/версии
```

### Событийный канал (BLE→MCU, USART3)
```
5A 51 0A SUBTYPE …              ; LEN=10 фиксированный; подтипы 0xa0..0xa6, 0xae
ACK: 0A 5A 61 0A SUB 00 00 00 00 XORCHK A5   ; XOR байтов [1..8] (НЕ сумма!), A5 = 0xFF−0x5a
```

## 5. Push-кадры `61` (UART4)

Два подтипа (живая линия опровергла «только 0x30»):

**`61 30 0A <10 Б> CHK 9E`** — payload постоянен: `03 00 08 1a a8 10 00 00 00 00`.

**`61 31 09 P0..P8 CHK 9E`** — баттари-пуш (билдер `0x214c2`, функция `0x211f8`):
```
P0      = byte @0x2e6            ; live: 0x9b (постоянно) — смысл TBD
P1      = byte @0x306 = SoC%     ; live: 0x62 = 98% ✓
P2 P3   = u16 @0x308 (high, low) ; live: cd cX — джиттер ±2 вокруг дрейфующего центра;
                                   кандидат на ток/сырой замер, единицы TBD
P4 P5   = u16 @0x30a (high, low) ; live: 80|00 — флаг бит7 переключается
P6 P7 P8= u16 @0x30c (low, high, low) ; live: 19 00 19 = 25 °C ✓
```

## 6. Ключевые значения и RAM-адреса (база 0x20000000)

| Константа | Значение | Смысл |
|---|---|---|
| кадр `0x41` | год u16BE @0x2b0, месяц/день в нибблах, 12/24-ч режим, високосный | **RTC/календарь**: время приходит телефон→BLE→MCU |
| кадр `0x44` | `0x306`=SoC%, `0x30c`=температура °C, `0x30e` бит14=холодный режим | батарея/температура; SoC = clamp((i16@0x17a0−415)×100/120, 0, 100); перегрев ≥46 °C → флаг @0x318 |
| `u16@0x1e8` | мастер-значение (сессия 0x5a: ±6 на событие, fan-out в 18 полей @0x1f2..0x216) | NVRAM: flash @0x0801F400 |
| `u16@0x1ec` | калибровка батарейного замера (0x5a/0xa1: raw×41/48) | NVRAM: flash @0x0801F404 |
| `i16@0x17a0` | результат батарейного замера (кастомный блок 0x40023c00) → SoC | единицы — только по живому |
| `u16@0x32e/0x330` | «счётчики» (get 0x36) | **CPU-писателя в образе нет** — живой забор только |
| `5A … 0xae` | ответ-строка `"PA68407 V0007"` | внутренний ID продукта + версия MCU |

## 7. Регион в прошивке MCU

В `mcu_0007.bin` @0x24164 найдена **ASCII-таблица всех 7 префиксов SN модели 5 Pro**
(`60550 60555 60556 60557 60561 60564 61143`) — регион закодирован и в контроллере, не
только в UI. Но КАК прошивка её использует, статически неизвестно (таблица адресуется
рантайм-базой, как и все данные MCU). Кросс-референс: на Scooter 4 Pro региональный лимит
скорости доказанно энфорсится в прошивке контроллера (diff анлок-мода) — для 5 Pro это
сильная аналогия, не прямое доказательство. Подробности — FACTS.md «Серийник», REPORT §15, §17.

## 8. Проводной DFU MCU (UART-консоль bw-flasher)

Живая DFU-консоль на линии USB-TTL (2026-08-21/22), полный write-флоу пройден успешно —
детали и команды в [`DFU.md`](DFU.md) §7. Кратко:

```
53 2A 7D AC              -> 64 2A 10 <UID 16Б> <chk> 9B
down get_ver/rd_info/ble_rand/mcu_rand/mcu_key/nvm_write/wr_info/dfu_verify/dfu_active
чанки FW: 01 N ~N data(128) crc16-xmodem-BE;   ACK 06 / CRC-fail 15
```

Крипто `sign_rand(uid, rand, fw, off0, off1)` подтверждена живым MCU ПОБАЙТОВО:
**off0=0x24187** (стандартная AES S-box), **off1=0x24387** (степени x в GF(2⁸):
`01 02 04 08 10 20 40 80 1b 36`), ключ 176 Б из UID, 10 раундов manipulate+XOR+S-box+перестановка.

⚠️ Консоль отвечает **в штатном режиме** (не бутлоадер-режим — push-поток `61…` идёт
параллельно). MCU-таргет принял переустановку той же версии 0007 (в отличие от BLE-таргета,
который даёт status 6 на той же версии) — либо разный механизм проверки, либо MCU-таргет
версию не проверяет вовсе.
