# DFU: обновление прошивок (BLE-чип, MCU — по воздуху и по проводу)

Тематическая справка по механизмам обновления `xiaomi.scooter.5pro`:
образы, беспроводной DFU через BLE-чип, асинхронная установка MCU, проводные пути.

> **Источник истины — [`FACTS.md`](FACTS.md)** (раздел «DFU» + поправки 2026-08-22).
> Исторический журнал разбора — [`dreame_dfu_protocol.md`](dreame_dfu_protocol.md)
> §6.14–§6.17; статический реверс образов — `research/REPORT.md` §30.

---

## 1. Обзор: два образа, один релиз

- `/v2/device/latest_ver` возвращает **одну запись на оба компонента**:
  `version`+`url`+`md5` (BLE) и `mcu_version`+`mcu_safe_url`+`mcu_md5` (MCU).
- Телеметрия подтверждает связку: `4.5 FIRMWARE_VERSION` = **`"2.7.0_0015.0007"`**
  (BLE + MCU одной строкой).
- Оба образа несут **одинаковый OTA-конверт**: маркер `TFOTA` + строка модели
  `xiaomi.scooter.5pro` в трейлере (`mcu_0007.bin` @0x24807, BLE @0x253ef).
  ⇒ MCU-образ предназначен для доставки **по воздуху**, а не только для программатора.
- MCU-образ **НЕ вложен** в BLE `upd`-образ (опровергнуто тремя замерами: размеры
  150 841 + ~120 КБ не влезают в 153 890; байт-поиск начала MCU в upd пуст; единственное
  пересечение — общая Mijia-цепочка сертификатов в трейлере).

| Образ | Файл | Размер | Версия |
|---|---|---|---|
| BLE-чип (RTL8762C) | `0d41b4df…_upd_xiaomi.scooter.5pro_v2.7.0_0015.bin` | 153 890 Б | `2.7.0_0015` |
| MCU (GD32) | `c0f78c49…_mcu_xiaomi.scooter.5pro_v0007.bin` | 150 841 Б | `0007` |

## 2. Формат OTA-образа

### Карта BLE-образа (по энтропии, блоки 0x200)
```
0x00000  PLAIN   заголовок + bootloader
0x03000  ENC     шифроблок 1 (~ENC1, size из header[0x24]=0x2e00=11776)
0x05e00  PLAIN   код флеш-драйвера/OTA
0x0a200  ENC     APP: 4 под-образа (разрывы 0x15a00 / 0x1e000 / 0x23600)
0x25400  PLAIN   трейлер MITFOTA (сертификаты Mijia + подпись)
```

### Трейлер `MITFOTA` @0x253ec
```
magic 'MITFOTA'
+0x0e product_id = 0x50d3 (20691, наш 5 Pro)
+0x10 signed_len = 152552 (0x253e8) — самоссылка на начало блока подписи
далее: модель "xiaomi.scooter.5pro", дескрипторы, RSA-подпись
```

### Две вариации в облаке (проверено)
Облако отдаёт **с подписью** (`url`) и **без** (`safe_url`): вторая — тот же файл,
обрезанный ровно на `signed_len` (BLE: 153 890 → 152 552, отрезано 1 338 Б;
MCU: 150 841 → 149 504, отрезано 1 337 Б) — байт-в-байт идентичный префикс.
Отрезанный хвост = блок `MITFOTA`. ⚠️ Обрезанные файлы **НЕ пригодны для DFU**
(нет подписи → `switchFirmware` отвергнет).

### Модель распространения: образ ОБЩИЙ и ОБЕЗЛИЧЕННЫЙ
1. **Content-addressing:** имя файла = MD5 содержимого = `md5` из `latest_ver`.
2. URL не параметризован по DID: `/default/signed_<md5>_upd_....bin` — общий.
3. BLE-образ полностью обезличен (наших DID/MAC/серийника нет).
4. В MCU «60555» — это **регион-таблица** @0x24169 (общий список префиксов 5 Pro),
   а не наш серийник; уникальный суффикс в образе отсутствует.

Заливка идёт байт-в-байт (`FileInputStream.read` → `arraycopy`, ноль модификаций);
CRC32 считается по файлу и сверяется устройством. **Патч невозможен** — образ подписан
Mijia, `switchFirmware` отверг бы (status 6, наблюдалось). Специфика устройства
(серийник, регион, привязка) живёт в **NVM устройства**, пишется отдельными командами
(spec set по BLE / UART `0x97` по проводу). Контраст: старое поколение (M365/MiDu) —
прошивка без подписи, флешер свободно патчил.

## 3. Беспроводной DFU по BLE

### Командный канал `0x0017` (W/RESP)
Кадр: `[opcode u16 LE][paramsLen u8][params]`, `params ≤ 17 Б`, прямой GATT-write.
Ответ notify: `[01][len][opcode u16][status][data]`.

| Опкод | Назначение |
|---|---|
| (сначала) | проверка protocolVersion устройства (≤4 поддерживается) |
| `2` | getFragmentSize → **512** |
| `3` | lastFragmentIndex (**BLE**) |
| `5` | lastFragmentIndex (**MCU**, `getMCULastFragmentIndex`) |
| `4` | switchFirmware (**BLE**) — необратим |
| `6` | switchFirmware (**MCU**) — необратим |

DFU-команды работают **plaintext** после login (session-крипта тут не нужна).

### Данные: канал `0x0018` (только WWR)
- Канальное сообщение: `[index u16 LE][данные фрагмента]`, **CRC к данным НЕ клеится**.
  `index` — сквозной, 1-based: первый кадр = `lastFragmentIndex + 1`,
  `skip = lastFragmentIndex × fragmentSize`.
- Per-fragment CRC32 (BE) считается локально в `checkLastFragmentIndex` для докачки —
  в поток данных не входит.
- Транспорт: frameSize **18 Б фиксировано**; CTR/ACK/DATA, `ACK 05 [seq]` = pull.
  По умолчанию шлём **все кадры сообщения подряд** (0 pull'ов, ~2.7–4× быстрее;
  `--burst=1` — прежнее поштучное поведение). Подробности — [`BLE.md`](BLE.md) §3.
- Событие фрагмента на `0x0017`: `[00 00][02][03][status]`, **status 0 = принят**.

Порядок: openCommandNotify(`0x0017`) → openDataNotify(`0x0018`) → protocolVersion →
getFragmentSize → lastFragmentIndex → цикл фрагментов → switchFirmware.

## 4. Статусы и «защита от дурака»

### BLE-таргет
| Наблюдение | Код |
|---|---|
| принял все 301 фрагмента (bad=0), образ лёг в буфер; отказ только на `switchFirmware` | **status 6** (та же версия — проверено; переключения не происходит, кирпича нет) |

### MCU-таргет: staging (поправка 2026-08-22 — «версионного гейта» НЕ существует)
| Код | Настоящий смысл (доказано пробами `probes/mcu_gate_*.py`) |
|---|---|
| **0** | фрагмент принят, лёг в MCU-staging |
| **5** | **дубликат индекса**: фрагмент с этим индексом УЖЕ в staging. После такого отказа устройство **закрывает DFU-сессию** (следующие кадры — без ответа) |
| **7** | **MCU временно «не готов»** (транзиент: сразу после ребута самоката / после `switchFirmware(4)` на пустом банке). Повтор через несколько минут проходит с 0 |

Ключевые факты:
- MCU-staging **персистентен между сессиями** (frag1 принят в одной → дубликат/5 в следующей).
- `getMCULastFragmentIndex` (опкод 5) **не отражает staging** — отдаёт 0 даже когда
  фрагменты приняты. Резюм по нему невозможен; ориентир — только свои логи.
- Образ **той же версии**, что установлена, **принимается** (status 0) при чистом
  staging и готовом MCU — версионной проверки на фрагментах НЕТ.
- Итог 2026-08-22: полный цикл пройден — весь образ 0007 в staging (ok=293, bad=0) →
  `switchFirmware(6)` → **staging очищен** (образ потреблён активацией) → версия `0007`
  без смены (переустановка той же версии), FAULT=0.

## 5. OTA-буфер BLE: граница `lastFragmentIndex = 296`

**Окончательно замкнуто с двух сторон** (FACTS.md «DFU»):
- чистый буфер + ПОЛНЫЙ файл (301 фрагм.) → **296**;
- чистый буфер + ОБРЕЗАННЫЙ файл (298 фрагм.) → **296**.

⇒ **296 (смещение 0x25000) — жёсткая граница устройства**: не зависит от длины образа,
чистоты буфера и питания (переживает выключение — NVM-метаданные OTA-банка во флеше).
Фрагменты 297+ квитируются на транспорте (status 0), но **не засчитываются**. Полезная
нагрузка по OTA-парсеру устройства кончается на 0x25000 — на 2 фрагмента раньше
`signed_len` 0x253e8; вероятно, парсер сам вычисляет длину из шифрованных заголовков
под-образов. Точную причину даст только SWD-дамп flash живого чипа.

**🔑 `switchFirmware` СБРАСЫВАЕТ OTA-буфер даже при отказе:** отправлен на буфер
296/298 той же версии → `resp 0103040006` (status 6) → после него `lastFragmentIndex=0`,
crc=0. Это штатный механизм сброса незавершённой сессии.

Практического значения: применить образ той же версии всё равно нельзя (status 6).

## 6. Как обновляет Mi Home (реверс `MeshDfuManager`)

**Предусловия:** заряд батареи **≥ 10 %**; BLE подключён; самокат **не в движении**.

```
openCommandNotify / openDataNotify      notify на 0x0017 / 0x0018
handleProtocolVersion                   версия протокола устройства
getFragmentSize / handleFragmentSize    согласование размера кадра
getLastFragmentIndex (BLE) / getMCULastFragmentIndex (MCU) / checkLastFragmentIndex
  + readInputStreamCRC32                докачка с проверкой CRC32
transferFragment / sendFragmentData / sendData
switchFirmware
pollMcuVersion                          ← ЖДАТЬ, пока версия MCU сменится
onUpgradeSuccess / onUpgradeFailed / release
```

⚠️ **Установка MCU асинхронная.** После `switchFirmware` приложение опрашивает версию MCU
(опкод 1 на `0x001c`), пока она не изменится — BLE-чип ретранслирует образ в контроллер
по USART3, и MCU прошивает себя сам (строки `"start poll mcu version"`,
`"mcu installing timeout="`). **Реализовано в `dreame_flasher.py`**: опрос до смены
(таймаут 180 с, интервал 3 с); read-only проверка задним числом — `poll-mcu`.

**Две отдельные DFU-передачи:** BLE-образ опкодами 2/3/4, затем MCU-образ 2/5/6.
Доказано, что MCU-over-BLE работает: Mi Home обновил самокат `2.5.3_0011 / 0006` →
`2.7.0_0015 / 0007` по воздуху (активация 2026-08-11; наш флешер к тому моменту ничего
не применял).

## 7. Проводные пути

### MCU: DFU-консоль по UART (bw-flasher, 19200 8N1) ✅ полный write-флоу пройден
Консоль отвечает **в штатном режиме** (push-поток `61…` идёт параллельно):

```
53 2A 7D AC        -> 64 2A 10 <UID 16Б> <chk> 9B
down get_ver       -> 0007
down rd_info       -> ok 0000 00000000 00000   (DFU/NVM-область)
down ble_rand      -> ok <BLE_KEY 16Б>        (сигнатура сверена ПОБАЙТОВО)
down mcu_rand / mcu_key / nvm_write / wr_info / dfu_verify / dfu_active
чанки FW: 01 N ~N data(128) crc16-xmodem-BE;   ACK 06 / CRC-fail 15
```

- Крипто `sign_rand(uid, rand, fw, off0, off1)`: S-box @**off0=0x24187** (стандартная
  AES S-box), таблица @**off1=0x24387** (степени GF(2⁸)), ключ 176 Б из UID, 10 раундов.
- Пройдено: bw-flasher (2026-08-21, все 75 пакетов, verify OK, activate OK) и наш
  `tools/mcu_uart_flash.py` (2026-08-22, ~8 мин, `dfu_verify` OK).
- **`dfu_active` может НЕ ответить** — MCU закоммитил активацию и сбросился до «ok»
  (гонка). Дискриминатор (read-only): после ребута `rd_info` = `ok 0000 00000000 …`
  (регион очищен) + `get_ver` отвечает + push-поток жив ⇒ активация закоммичена.
- MCU-таргет принял переустановку той же версии 0007 (BLE-таргет на той же версии даёт
  status 6 — см. §4).

### BLE-чип: 5A-кадры по USART3 (PB10/PB11)
```
[5A][12][CMD][LEN…][data][CRC16-XMODEM-BE]
CMD: 0x02 DeviceInfo (read-only), 0x03 start, 0x04 data(128), 0x05 end, 0x97 set-serial
ответы: [5A][21][CMD]…
```
На нашей линии (UART4) read-only DeviceInfo **без ответа** — 5A-протокол живёт на
двунаправленном USART3, а UART4 односторонняя (MCU→BLE push). Для диалога с BLE-чипом
провод нужен на USART3. Запись серийника (`5A 12 97 …`) — в [`BLE.md`](BLE.md) §9.

### ST-Link / SWD
Проводной путь через сервисный коннектор (ST-Link, ScooterHacking ReFlasher) работает с
**сырыми** образами, а не с подписанным контейнером. **Даунгрейд через DFU невозможен —
только SWD.**

## 8. Безопасность и необратимость

- `switchFirmware` **необратим** (риск кирпича). На той же версии бесполезен: BLE-таргет
  отвергает (status 6), MCU-таргет переустанавливает ту же версию.
- Прошивать только **официальные подписанные образы** (`firmware_ota/`, MD5 сверены).
- Наш флешер по умолчанию **без коммита** (загрузка фрагментов — безопасно); `--commit`
  только с явным `--yes`. Лог операций webui — `logs/flash_log.jsonl`.

## 9. Команды

```bash
# Прошивка БЕЗ коммита — только загрузка фрагментов, безопасно:
python dreame_flasher.py ble firmware_ota/<image>.bin
python dreame_flasher.py mcu firmware_ota/<image>.bin

# Полная прошивка с необратимым переключением (только на версии НОВЕЕ установленной!):
python dreame_flasher.py ble firmware_ota/<image>.bin --commit --yes

# Проверить, применилась ли установка MCU (read-only, ничего не шьёт):
python dreame_flasher.py poll-mcu --poll-timeout=60

# Проводной DFU MCU (USB-TTL, 19200 8N1):
python tools/mcu_uart_flash.py <image.bin>
```

Пробы (read-only / staging-тесты): `probes/mcu_ble_upload_rest.py`,
`probes/mcu_ble_commit.py`, `probes/mcu_gate_*.py`, `probes/mcu_version_gate_probe.py`.
