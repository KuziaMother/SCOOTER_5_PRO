## 1. Общая структура образа

| Offset | Размер | Тип | Содержимое |
|---|---|---|---|
| 0x00000 | 1 КБ | заголовок | OTA-заголовок, маркер `&release#`, адреса загрузки, 16-байтовый GUID |
| 0x00400 | ~9.7 КБ | **код (открыт)** | secure-boot / DFU-загрузчик (~46 функций) |
| 0x03000 | ~11.7 КБ | шифр | (зашифрованный сегмент) |
| 0x06000 | ~16.9 КБ | **код (открыт)** | драйвер SPI-флеша + OTA (~74 функции) |
| 0x0a200 | ~111 КБ | **шифр** | **главное приложение (зашифровано, AES)** |
| 0x25400 | ~1.3 КБ | трейлер | модель, маркер `TFOTA`, 2× PEM-сертификата, подпись |

Итого в открытых секциях **~120 функций** (грубая ранняя оценка по строкам, устарела);
точный подсчёт детектором «пролог+эпилог» — **170 подтверждённых** (покрытие кода
83 %/88 %, пересечений границ 0) — авторитетный справочник [`functions_ble/`](functions_ble/README.md)
(один md на функцию: дизассемблер, литералы, callees/callers; генератор `gen_functions.py`).
Всё остальное — зашифровано.

## 2. Открытый bootloader / DFU — что делает

Это ровно тот код, что принимает OTA-фрагменты по BLE и пишет их во флеш. По строкам:

- `Wrong Ctrl Header.` — разбор **CTR-заголовка** канального протокола (наши CTR-кадры DFU).
- `dfuPacketWaitTimer`, `Before dfu reset, unlock bp fail!` — приём DFU-пакетов, сброс, снятие **Block Protection** флеша перед записью.
- `temp have no valid image` — проверка валидного образа в OTA-банке (dual-bank).
- `RDID:%x` — чтение JEDEC-ID SPI-флеша; `Eras 0x%08x fail,retry %d` — стирание секторов; `BP en=%d,lv=%d` — управление защитой записи.

Вывод: секции 0x400 и 0x6000 = **secure-boot + OTA-приёмник + флеш-драйвер**. Именно этот код возвращал нам `status`-коды и проверял образ перед `switchFirmware`.

## 3. Главное приложение — зашифровано

Блок 0x0a200–0x25400 (~111 КБ) имеет энтропию **7.76–7.78** — признак AES-шифрования (у обычного ARM-кода ~6.0–6.5). Логика самоката (батарея/BMS, мотор, скорость, свет, замок, дисплей) — **внутри и нечитаема без ключа**. Строк оттуда нет.

## 4. Безопасность / подпись

Трейлер содержит цепочку **Mijia**:
- сертификат `Mijia Root` (корневой),
- сертификат `Mijia Open` (промежуточный),
- ключи **ECDSA P-256**, маркер `TFOTA`, модель `xiaomi.scooter.5pro`.

Образ **подписан** (проверяется по этой цепочке) и **зашифрован**. Поэтому:
- модифицировать/подменить прошивку нельзя (подпись не сойдётся);
- устройство при `switchFirmware` валидирует образ и отвергает негодный (`status 6`) — та самая «защита от дурака».

## 6. Итог
Открытая часть = **secure-boot/OTA-загрузчик и флеш-драйвер** (разбираемы, детальный справочник — `functions_ble/`). Основное приложение = **AES-зашифровано**, подписано цепочкой Mijia (ECDSA P-256). ## 6.1. MCU-образ mcu_0007.bin

**Файл:** `c0f78c49f322bd3d71fea19c90241882_mcu_...v0007.bin`, 150 841 Б. Версии в заголовке (ASCII): `0108`, `0007`, `0001`, `0001`.

- **НЕ зашифрован.** Энтропия почти везде 5.0–6.3 = обычный код/данные. Это **чистый ARM Cortex-M Thumb-код** (дизасм чистый: strcmp-подобные функции, `push/pop`, `ldrb`, `eor.w`).
- **~500 функций** (прологи `push {..,lr}`) в code-секциях.
- **Строк почти нет** — типичный контроллер без логирования (мотор/питание). Понять функции можно только ручным реверсом (нет строк-подсказок).
- Подпись — та же цепочка **Mijia** (`TFOTA` + 2 сертификата в хвосте 0x24800+, ASCII-строка
  `xiaomi.scooter.5pro` прямо перед первым `-----BEGIN CERTIFICATE-----`). Разобрано (openssl x509,
  2026-08-16): оба ECDSA P-256/SHA256.
  1) `O=Mijia Open` подписан `O=Mijia Root` (2018–2068) — промежуточный;
  2) `O=cert, C=CN` подписан `O=Mijia Open` (2020–2120) — лист, им реально подписан образ.
  Subject листового сертификата обезличен (`O=cert`, без серийника/чипа) ⇒ цепочка **общая для
  всей линейки Mijia**, не device-specific — подтверждает вывод, что это защита ПОДПИСИ образа,
  не имеющая отношения к AES-ключу шифрования APP (разные механизмы, см. §19.2).

Итог: MCU (контроллер самоката) — **открытый ARM-код, анализируем**, но без строк требует полноценного RE; шифрования нет, только подпись.

## 6.2. Расшифровка AES-части BLE — ВЕРДИКТ: невозможно из файла

Проверено (`analyze_crypto.py`):

| Проверка | Результат |
|---|---|
| AES-ECB (повтор 16-б блоков) | 0 повторов из 6944 → **не ECB** (CBC/CTR/поток) |
| Энтропия enc-блока | **7.998/8.0** — сильное шифрование |
| Таблицы AES (S-box/T-box) в образе | **нет** → шифрование **аппаратное** (крипто-движок RTL8762C) |
| Ключ/расписание в открытом коде | **нет** (кандидаты 0x440 — это код загрузчика) |
| Сигнатуры сжатия (gzip/lzma/lz4/zstd…) | нет (gzip@0x3dda — ложная, не распаковался) |

**Вывод:** главное приложение BLE зашифровано аппаратным AES RTL8762C, а **ключ хранится в eFuse/OTP чипа** (secure boot), которого в файле нет и быть не должно. Расшифровать образ **из одного .bin невозможно** — ключ прошит в кристалл на заводе Xiaomi/Realtek. Достать его можно лишь физической атакой на сам чип (глитчинг/декап), что вне рамок программного анализа.

Это согласуется со всем поведением: прошивка **подписана (Mijia ECDSA P-256) + зашифрована (AES в OTP)** — её нельзя ни прочитать, ни подменить без приватных ключей и доступа к OTP.

## 6.3. MCU — глубокий разбор, реверс Cortex-M

**Ядро:** ARM **Cortex-M4F** (FPU: обращение к `CPACR` 0xE000ED88). NVIC/SCB/SysTick присутствуют. `AIRCR` (0xE000ED0C) ×4 — программный сброс (перезагрузка после применения OTA).

**Карта памяти:** флеш @ 0x00000000 (или 0x08000000-alias), RAM @ 0x20000000 (доминирующий указатель-регион).

**Векторной таблицы в OTA-образе нет** — обновляется только APP-регион; таблица+загрузчик MCU лежат в защищённой области вне образа (стандартная схема безопасного OTA).

**Семейство:** периферийная карта = **STM32F1 / GD32F103-class** (GigaDevice — типовой выбор для контроллеров самокатов). Идентифицированные блоки (по literal-пулам, выровненные базы):

| Адрес | Периферия | Назначение |
|---|---|---|
| 0x40010800/0c00/11000/11400 | GPIOA/B/C/D | пины: гейт-драйверы, датчики Холла, свет, кнопки |
| 0x40021000 | RCC | тактирование/сброс |
| 0x40022000 | FLASH-контроллер | самозапись прошивки (OTA) |
| 0x40012C00 | **TIM1** (advanced) | **3-фазный комплементарный ШИМ — привод BLDC-мотора** |
| 0x40012400 | **ADC1** | токи фаз, напряжение АКБ, ручка газа, температура |
| 0x40013800 / 40004800 / 40004400 | USART1/3/2 | связь с BLE-чипом, дисплеем, BMS |
| 0x40005400 | I2C1 | датчики/EEPROM |
| 0x40013000 | SPI1 | периферия |
| 0x40000400 / 40000800 | TIM3/TIM4 | тайминги/доп. ШИМ |
| 0x40020000 | DMA1 | потоки ADC/USART |

**Функциональный портрет MCU:** это **контроллер BLDC-мотора самоката** на GD32/STM32 F1-class Cortex-M4F:
- TIM1 → трёхфазный ШИМ силового моста (управление мотором);
- ADC1 → измерение фазных токов, напряжения батареи, положения ручки газа, температуры;
- USART → обмен с BLE-модулем (RTL8762C), дисплеем и BMS;
- FLASH-контроллер → приём и запись OTA (тот самый MCU-путь DFU через ретрансляцию BLE-чипом);
- ~500 функций, но **без строк** — дальнейшее понимание конкретных алгоритмов (управление мотором, ограничения скорости, калибровки) требует ручного трассирования кода.

**Итог по MCU:** прошивка открыта и охарактеризована на уровне архитектуры/периферии; это motor-controller на Cortex-M4F (STM32F1/GD32-совместимый), не зашифрован, только подписан (Mijia). Детальный алгоритмический реверс (без строк) возможен, но это отдельная крупная работа по трассировке инструкций.

## 6.4. MCU — детальный реверс функций, ч.3

**Кодовая база:** прошивка построена на **HAL (STM32/GD32)** — характерный ассерт-паттерн `cpsid i; b .` (disable IRQ + вечный цикл) при провале проверки параметров, как в HAL_* функциях. Всего **503 функции**, **80** работают с известной периферией.

### Карта «функция → периферия»
| Подсистема | Функции |
|---|---|
| **Мотор (TIM1 ШИМ)** — 11 | блок `0x22a48–0x22fac` (TIM1+TIM3+TIM4), `0x1e2f8` (RCC+TIM1 init) |
| **Датчики (ADC1)** — 4 | `0x1a31c` (стейт-машина выборки), `0x1e298` (DMA+ADC), `0x1c0b0`, `0x21ca8` |
| **Связь (USART)** — 9 | `0x1302c`/`0x23188` (init/драйвер всех трёх), `0x1e480/1e9e0/1f600/1f6b4` (протокол на USART3 ↔ BLE) |
| **OTA (FLASH)** — 8 | `0x06230` (программирование), `0x06304`, `0x11cb4` (RCC+PWR+FLASH) |

### Разобранные функции
- **`0x22c70` — конфиг ШИМ-канала мотора** (HAL `TIM_PWM_ConfigChannel`-стиль): валидирует хэндл против TIM1 (0x40012C00) и таймеров 0x40014000–0x40014C00, индекс канала 0–3, флаги; при ошибке — assert-trap `cpsid i; b .`.
- **`0x1a31c` — стейт-машина выборки ADC**: `switch` по состоянию (0/1/3/5), чтение `ldrh` из ADC, аккумуляция значений (токи фаз / напряжение / газ / температура), вызывает DMA-ADC `0x1e298`.
- **`0x1e480` — ISR USART3** (линк к BLE-чипу RTL8762C): чтение статуса, тест бит ошибок сдвигами, сброс флагов PE/FE/ORE в 0x40004840. Обмен MCU↔BLE идёт по **USART3**.
- **`0x06230` — программирование FLASH** (OTA self-write): ожидание готовности, `PG`(bit1) в `FLASH_CR`(+0x10), запись слова, `STRT`(bit6), ожидание, снятие бит. Это приёмник MCU-прошивки (тот путь, что BLE-чип ретранслирует).

### Константы — кандидаты, НЕ подтверждённые лимиты
Среди immediate-значений в код-секциях: `4096/2048` (12-бит ADC, средняя точка), `16384/1024` (период ШИМ-таймера), `1000/10000` (масштаб/время), и правдоподобные пороги батареи **`30000` и `37282`** (≈30.0 В и 37.3 В — рабочий диапазон 10S Li-ion пакета). Точные тюнинг-лимиты (макс. скорость/ток) требуют трассировки конкретных функций управления — по одним immediate это лишь гипотезы.

### Итоговый портрет MCU
GD32/STM32F1-совместимый **Cortex-M4F motor-controller** на HAL: TIM1 — 3-фазный ШИМ силового моста; ADC1(+DMA) — токи/напряжение/газ/температура; USART3 — канал к BLE-модулю (плюс USART1/2 — дисплей/BMS); FLASH-драйвер — OTA. Код открыт и структурно разобран (периферия, драйверы, ISR, OTA), но без строк детальная логика (алгоритм управления мотором, точные лимиты) — предмет отдельной трассировки.

_Скрипты MCU: `mcu_analyze.py` (VT/арх/периферия), `mcu_xref.py` (функция→периферия), `mcu_deep.py` (дизасм+константы)._

### Справочник по функциям MCU — `gen_functions_mcu.py` → `functions_mcu/`
Авторитетный справочник **678 подтверждённых функций** (один md на функцию: дизассемблер,
literal-пулы, литералы с классификацией RAM/периферия/Cortex-M, callees/callers, внутренние
dispatch-блоки). Детекция: пролог `push{..,lr}`(B5xx)/`push.w`(T32) ∪ цели `bl`; границы — BFS;
пересечения разрешаются по входящим xref (демоция). Итог: 691 кандидат → 678 kept, 28 ложных,
276 трамплинов, 13 демоций.

**Фильтр ложных literal-пулов по достижимости** (добавлен, чтобы убрать «фантомные» пулы):
настоящий пул **невозможно** пересечь с достижимым кодом — в данные не переходят. Если кандидат
пула ложится на достижимую инструкцию/цель ветвления, это код, а не пул. Три обязательных фикса:
- **Классификация ветвлений**: capstone выдаёт `beq/bne/blo/bhs/…` (НЕ `b.eq`) — прежняя проверка
  `startswith("b.")` их пропускала. Теперь точные наборы `UNCOND_BR`/`COND_BR` (без ложных друзей
  `bfi`/`bic`/`bics`/`bkpt`, которые тоже начинаются на `b`). Попутно исправлено в `find_internal_blocks`
  и xref/callees — секция «Внутренние блоки» теперь ловит и условные цели (235 функций, 2677 блоков).
- **Запись в PC = терминально** (`bx` / `ldr pc,[..]` / `pop {..,pc}` / `mov|add|sub pc,..`): иначе BFS
  «проваливался» fall-through сквозь return в trailing-пул и ложно подавлял РЕАЛЬНЫЕ пулы. До фикса
  терялось 11 настоящих указателей (RAM/периферия), после — **0**; подавляется только 2 истинно ложных.

**Пример (RX-парсер `func_0x1e9e0`):** `ldr r4,[pc,#0x104]`@`0x1ea18` указывал на `0x1eb20`, но это
живой convergence-блок (цели ветвлений `0x1eb22/0x1eb24`), а не пул; raw-слово `0x70447014` распадается
на два `strb`. Ложная аннотация «литерал 0x70447014» и «пул @0x1eb20» удалены; реальные tail-пулы
`@0x1ede0`(40 слов) и `@0x1f15c`(25 слов, в т.ч. за границей) сохранены. ⚠️ Сам `ldr` при этом —
реальные байты (подтверждено capstone+keystone+unicorn), но его «пул»-цель — код ⇒ признак
десинхронизации/мёртвого пути в этой функции (см. §16.2, RX под эмулятором).

## 6.5. MCU ч.4 — управление мотором №1 и протокол USART3 №2

### №1. Управление мотором — трапеция/6-шаг, НЕ FOC
- **Sine-LUT (int16) не найдено** → это не классический FOC, а **трапецеидальная 6-шаговая коммутация** BLDC по датчикам Холла.
- **Таблицы коммутации** — блок 0x17d3a–0x17d7e: строки нибблов (0x00–0x0f), напр. `02 01 04 07 03 08 0a 0c 0e 09`, `04 07 09 0a 0c 05 03 01` — это lookup «состояние Холла/шаг → паттерн включения ключей моста».
- **TIM1** (0x40012C00) — 3-фазный комплементарный ШИМ силового моста; вспом. таймеры 0x40014000–0x40014C00.
- **ADC1 стейт-машина** (`0x1a31c`, +DMA `0x1e298`) — выборка фазных токов / напряжения / газа / температуры.
- **GPIO** (18 обращений) — вход датчиков Холла + гейт-сигналы.

### Калибровки/лимиты (блок 0x17d20)
Значения int16 перед сигнатурой кадра: `10000` (масштаб/100%), **`4150`** (макс. напряжение ячейки, 4.15 В), **`3000`** (отсечка разряда, 3.0 В), `3140`, `280`, `10`. Это параметры **защиты батареи** (порог заряда/разряда). Точная привязка каждого поля — предмет трассировки функций BMS.

### №2. Протокол USART3 — MCU ↔ BLE-чип RTL8762C
- Физически: **USART3** (0x40004800) — линк к BLE-модулю; USART1/2 — дисплей/BMS.
- **Сигнатура кадра `55 AA`** (0x17d3a) — классический Xiaomi/m365-протокол.
- **RX** (`0x1f600`): кольцевой буфер (head/tail в RAM 0x200002c1/0x200002c2), таймаут, **диспетчеризация по таблице дескрипторов** (шаг 0x96 = 150 байт на запись) в структуру 0x20000170 (поля len[0xa]/[0xb]).
- **ISR** (`0x1e480`): чтение статуса USART3, сброс флагов ошибок PE/FE/ORE.
- **TX**: кадр собирается вызывающим (напр. `0x1f6b4` строит дескриптор `[type=2][len][data]`) и отправляется через **HAL_UART_Transmit** `0x23188` (валидация порта/длины/режима/паритета/стоп-бит, assert при ошибке).

### Резюме протокола
Обмен BLE↔MCU — кадры с синхро-словом **`55 AA`** поверх HAL-UART на USART3, с приёмом через кольцевой буфер и разбором по таблице дескрипторов сообщений. Полная расшифровка полей каждого типа кадра (команды скорости/режима, телеметрия) требует трассировки RX-диспетчера и таблицы дескрипторов — структура найдена, но байтовая раскладка каждого сообщения — отдельная работа.

### Что осталось — честно
- Точная раскладка кадров `55 AA` (id/длина/поля/CRC) — по таблице дескрипторов на 150 Б.
- Привязка калибровочных констант к конкретным лимитам (скорость/ток) — трассировка BMS/мотор-функций.
Оба — ручной дата-флоу реверс без строк; фундамент (где что лежит) заложен выше.

### RX-команды `0x42`–`0x46`: layout полей и потребители (разобрано 2026-08-15)

Парсер `0x1e9e0` (RX BLE→MCU) имеет **вторую** диспетчерскую таблицу по байту команды `r4`;
она — пара первой таблицы §16.1 (там направление MCU→BLE: `63 CMD (0x63+CMD)&FF 9C`).
Каждая ветка `b` ведёт в inline-хендлер, который кладёт поля кадра-ответа в RAM-стейт.
Все адреса ниже получены исполняемым дизассемблером + F1-резолвом literal-пулов
(`((A+4)&~3)+imm` для 16-бит `ldr`, `((A+8)&~3)+imm` для `ldr.w`).

| cmd | хендлер | layout полей кадра → RAM |
|-----|---------|--------------------------|
| `0x42` | `0x1ed90` | `[3..9]` → 7 байт подряд `0x200002cb..0x2d1` |
| `0x43` | `0x1edba` | `[3..8]` → 6 байт подряд `0x200002d2..0x2d7` (смежно с 0x42) |
| `0x44` | `0x1eeb4` | `[3]`→`0x2e6`(clamp≤0xfe); `[4]`→`0x306`(clamp≤100); `[5][6]`→u16@`0x308`; `[7][8]`→u16@`0x30a`; `[9]`→byte@`0x30c`; `[0xa][0xb]`→u16@`0x30e` — **9-байтовый payload** |
| `0x45` | `0x1ef08` | 6×u16 LE: `[3][4]`@`0x2da`, `0x2dc`, `0x2de`, `0x2e0`, `0x2e2`, `0x2e4`; + byte`[0xf]`@`0x2e7` (13 байт; gap в `0x2e6`) |
| `0x46` | `0x1ee86` | len=`frame[2]` (cap 0x14): копирует `frame[3..3+len)` в буфер `0x200002f2`; счётчик в CTX+4 (`0x20000174`); буфер сначала обнуляется |

**Потребители (cross-ref по RAM-адресам):**
- `func_0x211f8` читает **весь** блок 0x44 и пересобирает его в исходящий кадр для телефона:
  `frame[3]=9`(длина), `[4]`=`0x2e6`, `[5]`=`0x306`, `[6][7]`=u16@`0x308`, `[8][9]`=u16@`0x30a`,
  `[0xa]`=`0x30c`, `[0xb][0xc]`=u16@`0x30e` → ответ 0x44 ретранслируется в приложение **как есть** (9-байтовая телеметрия).
- `func_0x1f71c` (агрегатор, 6860 Б) ссылается на все четыре блока `0x2cb/0x2d2/0x2da/0x2f2`.
- `func_0x1a938` / `func_0x1d898` читают `0x306`: `cmp #0x5a`(90), `cmp #0xa`(10), кламп `#0x64`(100)
  → поведенчески это **процент уровня заряда** (пороги 10/90, диапазон 0–100).

**Структурные наблюдения:** 0x42 и 0x43 складываются в один 13-байтный регион `0x2cb..0x2d7`;
u16-блок 0x45 (`0x2da..0x2e5`) оставляет 1-байтный gap в `0x2e6`, который заполняет 0x44 — комплементарные записи в одну структуру.

**Уровень уверенности:** ВЫСОКИЙ (исполняемый дизассемблер + резолв пулов) — таблица dispatch,
field→RAM всех пяти команд, ретрансляция 0x44 в телефон, кламп/пороги процента.
СРЕДНИЙ — смежность блоков, gap-fill, роль агрегатора. НИЗКИЙ / нужен live-снуп USART3 или
корреляция с MIoT-свойствами телефона — физический смысл каждого u16 (напряжение/ток/скорость/температура/дистанция).

## 6.6. ВАЖНО: коррекция и предел автоматического разбора

При проверке две ранее «найденные» детали протокола **не подтвердились** (ложные срабатывания сигнатурного поиска в большом бинаре):

- **CRC16-CCITT таблица @0x3570 — НЕТ.** Прямая сверка с эталоном не совпала (`0000 1021 0000 1031 0012…` — это код с нулевыми байтами, а не CRC-таблица), ссылок из кода нет. Алгоритм контрольной суммы кадра НЕ установлен.
- **`55 AA` @0x17d3a как заголовок кадра — НЕ подтверждено.** В RX-пути нет сравнения с 0x55/0xAA; блок 0x17d20–0x17d80 не имеет код-ссылок. Скорее это **magic валидности конфиг-блока** (типовой 0x55AA), рядом с нибблами коммутации и параметрами батареи, а не синхро-слово serial-протокола.

**Подтверждено достоверно** остаётся: USART3 = линк к BLE-чипу; RX через кольцевой буфер + диспетч по таблице дескрипторов (шаг 150 Б, `0x1f600`); ISR `0x1e480`; TX через HAL_UART `0x23188`. Точная байтовая раскладка кадров и алгоритм контрольной суммы — **НЕ вскрыты**.

### Реальный предел «полного охвата»
Прошивка **без строк** (503 функции, 88% образа — код). Автоматические сигнатурные методы дают:
- архитектуру/периферию/роли подсистем — надёжно (~85–90% «что и где»);
- но **байтовые форматы, алгоритмы и точные константы** — только гипотезы, которые при проверке часто оказываются ложными (как CRC/55AA выше).

Полный построчный охват (расшифровка каждого кадра, петли управления мотором, всех лимитов) достижим **только ручной трассировкой каждой функции** — это работа на многие дни/недели RE, вне возможностей скриптового анализа за сессию. Честная оценка построчного понимания сейчас — **~1–2%**; «архитектурного» — ~85–90%.

## 6.7. Функция `0x1f600` — ПОЛНОСТЬЮ разобрана, проверено

USART3-**планировщик исходящих запросов** (round-robin поллер). Разобраны все 180 байт + вызываемая `0x1f1c0`.

**RAM-структуры:**
- `0x200002C2` — `slot` (текущий слот 0..2), `0x200002C1` — `slot_target` (до какого слота идти).
- `0x200001E0` — 64-бит `now` (системный тик).
- `0x20000170` — контекст CTX: `[0x0A]`=itemCount дескриптора, `[0x0B]`=itemIdx, `[0x28:0x2C]`=время слота (64б), `[0x30:0x34]`=под-таймер (64б).
- `0x20000A43` — таблица дескрипторов, шаг **150 Б**; `desc[slot][0]`=число элементов, `desc[slot][1..]`=байты-команды.

**Восстановленная логика (Си-псевдокод):**
```c
void uart3_poll_tick(void){
  if (slot == slot_target) return;              // дошли до цели — стоп
  if (now - CTX.slot_time <= 432) return;       // пауза 432 тика между слотами
  CTX.itemCount = desc[slot][0];
  if (CTX.itemCount < CTX.itemIdx+1){            // элементы слота исчерпаны
     CTX.itemIdx=1; CTX.subtimer=11; CTX.slot_time=now;
     if (++slot >= 3) slot=0; return;            // -> следующий слот (0..2)
  }
  if (CTX.subtimer <= 8){ CTX.subtimer++; return; }        // пауза 8 тиков между байтами
  if (USART3.SR & TX_BUSY) return;                          // ждать готовности UART
  uint8_t cmd = desc[slot][CTX.itemIdx];                    // байт-команда из дескриптора
  usart3_send_byte(cmd);       // 0x1f1c0: USART3->DR = cmd
  CTX.itemIdx++; CTX.subtimer=0;
}
// 0x1f1c0:  void usart3_send_byte(u8 b){ *(u32*)(0x40004800+4)=b; }  // DR
```

**Смысл:** MCU периодически по USART3 рассылает последовательность **байт-команд/запросов** из 3 конфигурируемых слотов (round-robin), с паузами 8 тиков между байтами и 432 тика между слотами, проверяя готовность передатчика. Конкретные ID команд лежат в RAM-таблице `0x20000A43` (заполняется при инициализации — вероятно копией из flash; чтобы прочитать список ID, надо найти инициализатор этой таблицы).

**Статус:** функция `0x1f600` + `0x1f1c0` — понятны на 100%. Это +2 функции к детально разобранным (итого ~10/503).

## 6.8. Попытка вытащить ID команд опроса USART3 — предел

Цель: прочитать конкретные байты-команды, которые планировщик `0x1f600` шлёт из дескрипторов `0x20000A43` (slot×150).

**Что установлено (проверено):**
- Регион `0x20000A40–0x20000C10` — **большой глобальный стейт-структ** самоката; на него ссылаются десятки функций (поля читаются/пишутся врассыпную).
- Соседние функции — это **логические стейт-машины**, не инициализатор: `0x11894` — 5 состояний через `tbb` jump-table (пороги, сравнение с 50); `0x01984` — счётчик/дебаунс (состояния 0..3).
- Базы дескрипторов `0x20000A43/AD9/B6F` **НЕ заполняются memcpy из flash** — прямых литеральных ссылок на них нет, кроме самого `0x1f600`. Значит команды пишутся **динамически через указатель-базу + смещения**.

**Вывод:** список ID команд **статически не извлекается** — он формируется рантайм-логикой в глобальном структе. Чтобы его получить, нужно либо (а) трассировать указатель структуры через десятки функций записи, либо (б) снять дамп RAM с живого MCU в момент работы (JTAG/SWD). Оба — вне статического анализа .bin.

Это тот же принципиальный предел, что и с AES: часть информации физически отсутствует в образе (ключ — в OTP; значения таблиц команд — в рантайм-RAM).

## 6.9. Внешние ресурсы по RTL8762C — hackaday FT10 и rtl8762c-gcc-examples, что дают

**Подтверждённая карта памяти RTL8762C** (из линкер-скрипта cyber-murmel/rtl8762c-gcc-examples):
- **RAM @ 0x00200000** (vector table 0x00200000, app-data 0x00207C00, cache 0x0021C000, uninit 0x00217F00).
  → совпадает с нашим BLE-заголовком `[0x1c]=0x00203800` (RAM-адрес) — опознано верно.
- **Flash @ 0x00800000** (8 МБ; у Dreame OTA-адресация 0x018xxxxx — вероятно вторичный банк/алиас).
- Ядро/тулчейн: ARM Cortex-M, `arm-none-eabi-gcc`; прошивка **по UART**.

**Проект FT10 (hackaday 182205)** — реверс устройства на RTL8762C. Ключевое для нас:
- **UART-загрузчик**: тест-пойнты GND/RX/TX/RST/**LOG**; LOG→GND при сбросе = режим программирования; handshake-магия `01 17 FC 04 14 C0 52 02`.
- Утилита **`rtltool`**: `rtltool.py read_flash 0x00800000 <size> dump.bin` — **дамп всего flash по UART** (flasher-stub, CRC-16/ARC).

### Почему это важно — возможный обход AES-стены
Наш `.bin` — зашифрованный **OTA-транспортный** образ. Но в самом flash чипа приложение может лежать **расшифрованным** (если Dreame включил только OTA-шифрование, а не flash-encryption по OTP). Тогда **дамп flash через rtltool = расшифрованная BLE-прошивка** — со всеми строками/функциями логики самоката, которые сейчас недоступны.

- Если flash плейнтекст → получаем полный дизассемблируемый образ (обход AES без атаки на кристалл).
- Если включено flash-encryption (XIP-decrypt) → дамп вернёт шифртекст (та же стена).
Проверяется только дампом. У FT10 flash оказался читаемым (нашли адреса ROM-функций) — шанс реальный.

### Требования — физический доступ
1. Разобрать BLE-модуль самоката, найти на плате RTL8762C и тест-пойнты (GND/RX/TX/RST/LOG).
2. USB-UART адаптер (3.3 В), подтянуть LOG к GND при сбросе → download-режим.
3. `rtltool read_flash` → полный дамп → повторить наш анализ (энтропия/дизасм): плейнтекст ли app-регион.

### Про MCU
rtltool читает RTL8762C, не GD32-контроллер. Для MCU (значения таблиц команд в RAM) аналогичный путь — **SWD/JTAG-дамп GD32** (ST-Link/J-Link на отладочных пинах платы контроллера).

**Итог:** ресурсы полезны — они дают **аппаратный путь** к тому, чего нет в файлах: (1) дамп flash RTL8762C по UART → возможно расшифрованная BLE-прошивка; (2) SWD-дамп GD32 → значения рантайм-таблиц MCU. Оба требуют физического доступа к платам, но это реальный обход обеих «стен» (OTP-ключ / рантайм-RAM).

## 6.10. Research: криптоструктура BLE + rtltool, продолжение

### Уточнённая структура шифрования BLE
- Оба шифроблока **кратны 16 Б** (ENC1=11776, ENC2=111104), E=7.98–8.0, **не ECB** (0 повторов, 0 общих блоков) → **AES-CBC/CTR, свой IV на регион**.
- Это **контейнер под-образов Realtek multi-image OTA**: на границах — плейнтекст-дескрипторы. Конец ENC1: `00 00 10 00 05 0f … 40 00` (size/flags/CRC/addr). Конец ENC2 упирается в `46 4F 54 41`="FOTA" (трейлер `TFOTA`).
- Кандидат IV — `header[0x0c:0x1c]` = `6d67def1 3e33e811 b1024d2d f40cde01`.

### rtltool, репозиторий cyber-murmel/rtltool — команды
`read_flash`, `write_flash`, `erase_flash`, `erase_region`, `verify_flash`, `read_mac`(OTP), `chip_id`(OTP). Опции `-p PORT -b BAUD -r RETRIES`. Декрипта/ключей нет.
→ даёт **сырой дамп flash по UART**. Плейнтекст ли app — зависит от того, включил ли Dreame flash-at-rest encryption (XIP-decrypt по OTP-ключу) или только OTA-транспортное шифрование.

### Реальные ветки продолжения — по убыванию доступности
1. **Realtek SDK default OTA AES-ключ.** RTL8762x SDK в ряде версий шифрует OTA фиксированным (публичным) ключом. Если Dreame его не сменил — наш `.bin` расшифровывается **программно, известным ключом** (нужен ключ из SDK/сообщества; IV — кандидат из заголовка). Самый дешёвый путь, если ключ найдётся.
2. **UART-дамп RTL8762C через rtltool.** Физдоступ к тест-пойнтам (GND/RX/TX/RST/LOG), LOG→GND при сбросе. Если flash не зашифрован «на месте» → расшифрованная BLE-прошивка сразу.
3. **SWD-дамп GD32 (MCU).** Рантайм-значения таблиц команд USART3 (`0x20000A43`) и полный образ контроллера.
4. **Продолжать статический реверс MCU** — единицы % охвата за дни ручной работы.

### Стены — это отсутствие данных в файле
- BLE app: **AES-ключ** — в OTP (или SDK-дефолт, если не менян).
- MCU команды: **значения** — в рантайм-RAM.
Оба обходятся только (1) известным ключом или (2) аппаратным доступом — не улучшением статического анализа `.bin`.

## 6.11. RTL8762C SDK-репозиторий rtl8762c-gcc-examples — РЕШАЮЩИЕ данные

Склонирован `cyber-murmel/rtl8762c-gcc-examples` — там реальные конфиги SDK.

### Точная flash-карта: base 0x00800000, у Dreame — 0x01800000, тот же layout
```
0x_800000  Reserved     4K
0x_801000  OEM Header   4K
0x_802000  OTA Header   4K
0x_803000  ROM Patch   40K   ← наш плейнтекст-код (PIC)
0x_80D000  Secure boot  4K
0x_80E000  APP code   100K   ← наш ЗАШИФРОВАННЫЙ блок
0x_82B000  OTA Tmp    100K   ← DFU-буфер (сюда шли наши фрагменты!)
```
Наш `header[0x28]=0x01803000` = ROM Patch start → подтверждено.

### Флаги шифрования — T_OTA_HEADER_FORMAT, ota_bank0_header.c
```
ic_type=5 (=наш header[0]=0x05, RTL8762C)
xip=1  enc=1  enc_load=1  enc_key_select=7  integrity_check_en_in_boot=1
+ rsaPubKey{N,E} + sha256  → secure-boot RSA-подпись (поверх Mijia ECDSA в трейлере)
magic 0x5A5A12A5
```

### Вывод про расшифровку — ИСПРАВЛЕНО и точно
`xip=1 + enc=1` ⇒ flash-контроллер расшифровывает код **на лету при исполнении** (inline XIP-decrypt), ключ — в OTP (`enc_key_select=7`).
- **UART/`rtltool read_flash` → ШИФРТЕКСТ** (сырые байты SPI-флеша; декрипт к чтению не применяется). Дамп flash **НЕ** обходит шифрование.
- **SWD-чтение XIP-региона `0x0180E000` (100K)** идёт через шину с inline-декриптом ⇒ **ПЛЕЙНТЕКСТ** — если SWD включён.

### SWD-доступ
`otp_config.h`: `SWD_PINMUX_ENABLE 1` (в SDK по умолчанию включён). `debug/rtl8762c.cfg` — готовый OpenOCD-конфиг: Cortex-M DAP, TAPID `0x2ba01477`, flash bank `0x00800000` 512K, work-area RAM `0x00200000`. Любой ST-Link/J-Link/CMSIS-DAP + OpenOCD.
**Риск:** прод-устройства часто отключают SWD в OEM/OTP. Если Dreame отключил — SWD не подключится (проверяется попыткой).

### ИТОГ по обходу AES-стены
Единственный реальный путь к **расшифрованной BLE-прошивке** = **SWD-дамп XIP-региона 0x0180E000** на живом чипе (не UART-дамп flash). Требует: физдоступ к SWD-пинам BLE-модуля + OpenOCD + чтобы SWD не был залочен в OTP. Программно из `.bin` — невозможно (ключ в OTP, декрипт аппаратный XIP).

## 6.12. Охота за телеметрией: батарея/скорость/пробег — on-device, 2026-08-13

Самокат включён, все пробы прогнаны на живом устройстве. Скрипты — в `probes/`.

### 1. Инфо-канал 0x001c: перебор всех 256 опкодов — `probes/mcu_opcode_sweep.py`

Дискриминатор: формат ошибки `ff [len] [echo_op] [errcode]`, причём коды **разные** —
`err 0x02` = опкода не существует, `err 0x08` = опкод есть, но нужен параметр
(так себя ведёт известный опкод 8 = серийник постранично). Это позволило перебрать
диапазон 0..255 однобайтовыми кадрами `[op]` (геттеры; сеттер требует `[op][len][data]`,
так что перебор безопасно смещён в сторону чтения).

Результат — канал содержит **ровно 4 опкода**:
```
op 0  -> 00020103            (payload 0103 — версия протокола/капабилити?)
op 1  -> mcu_version 'RTL8762C'-парой: ascii '0007'
op 3  -> hardware 'RTL8762C'
op 8  -> serial (нужен параметр offset; бареты дают err 0x08)
все остальные 252 -> err 0x02 (нет опкода)
```

### ⚠️ ПОПРАВКА к прежней модели
Опкод 3 отдаёт **`"RTL8762C"` — имя самого BLE-чипа**, не GD32. Значит `0x001c` —
**НЕ проброс к MCU**, как считалось ранее, а инфо-канал, обслуживаемый самим
BLE-чипом: он отдаёт лишь то, что нужно OTA для решения об обновлении (свои версии
+ версия MCU). Телеметрии здесь не могло быть по определению.

### 2. MIoT-спека: телеметрии нет, авторитетно

`miot-spec.org/miot-spec-v2/instances?status=all` — **47 161** инстанс; для
`xiaomi.scooter.5pro` существует ровно один, `status=released`:
`urn:miot-spec-v2:device:scooter:0000A077:xiaomi-5pro:1`.
В нём **только** сервис device-information (manufacturer, model, did, fw-revision,
serial) — **ни одного свойства батареи/скорости/пробега**. То есть телеметрия у этой
модели не выражена в MIoT-модели вообще.

### 3. Пассивное прослушивание после логина — `probes/telemetry_listen.py`

Логин отработал (Stage A+B OK, sessionKey 64 Б). За 40 с после успешного логина —
**0 нотификаций**. Устройство телеметрию само не пушит, нужен запрос.

Раскладка sessionKey: 64 Б (HKDF-SHA256 от `shared||ltmk`), для login-подтверждения
берётся `sk[16:32]` + фиксированный nonce `10..1b`.

### 4. MiBeacon в рекламе: только идентификация — `probes/beacon_scan.py`

Service data FE95 стабилен, 11 байт, повторяется без изменений:
```
1055 d350 00 88dede5c192c
frame_ctrl=0x5510  version=5  auth_mode=1  [registered, mac]
product_id=0x50d3   frame_cnt=0   mac=2c:19:5c:de:de:88
```
11 байт = `fctrl(2)+product_id(2)+frame_cnt(1)+mac(6)` — учтены полностью, **хвоста нет**.
Биты: `object=0`, `encrypted=0` ⇒ ни объектов телеметрии, ни шифрованной нагрузки.

> Методическая заметка: в первой версии парсера таблица бит frame_control была
> сдвинута на 1 (выдавала ложное «ЗАШИФРОВАНО»). Исправлено на канонические сдвиги
> (`encrypted=bit3, mac=bit4, capability=bit5, object=bit6, mesh=bit7,
> registered=bit8, auth_mode=bits10-11, version=bits12-15`).

### 5. Перебор номеров каналов — НЕУДАЧНАЯ методика, результат недействителен

`probes/channel_probe.py`: идея была слать CTR `[00 00][03][channel][fc]` и считать
ACK признаком живого канала. И с `fc=0`, и с `fc=1`, на `0x0016` и `0x001a`, каналы
0..31 дали **полную тишину — включая канал 5**, который заведомо рабочий во время
логина. Значит после завершения логина CTR на `0x0016` не обслуживается, и проба
**не обладает различающей силой**. Это НЕ доказательство отсутствия каналов —
эксперимент просто ничего не измерил. Скрипт оставлен с этой пометкой.

### ИТОГ: что закрыто и что осталось

Закрыто эмпирически (три независимых пути):
1. инфо-канал `0x001c` — 4 опкода, только версии/железо/серийник;
2. MIoT-спека — свойств телеметрии не существует;
3. MiBeacon-реклама — только идентификация, без объектов и шифрования.

**Единственный оставшийся программный путь:** приватный протокол Dreame поверх
шифрованной сессии (`0x001a`/`0x001b`), логика которого лежит в **плагине Mi Home
для `xiaomi.scooter.5pro`** — отдельном бандле, которого нет в базовом APK. Его можно
скачать облачным API (у нас уже есть рабочая QR-авторизация, см.
`scratchpad/fetch_firmware.py`) и отреверсить. Без него формат кадров на `0x001a`
угадывать бессмысленно — мы уже убедились, что вслепую канал не отвечает.

### 4. Транспорт: `0x001a` / `0x001b`, каналы 6 и 7

Плагин читает так (`modules/10013.js`):
```js
_miot.Bluetooth.spec.getPropertiesValue(mac, JSON.stringify({objects: props}))
```
⇒ это **MIoT-spec поверх BLE**, не облако. Нативная реализация — в APK, и лежит
**в том же пакете, что уже реверснутый нами канальный транспорт**:
`core/server/internal/bluetooth/channel/` (наш `ChannelManager` = `channel/OooO00o`).

- `SpecChannelManager` = `channel/OooO0o`
  - `writeBle` → **канал 6** (`const v3, 6`)
  - `writeBatchBleData` → **канал 7** (`const v3, 7`)
  - `useCrc32Verify` → **false** (в отличие от DFU-канала)
- `SpecWriteChannelManager` = `channel/OooOO0`, UUID `ry0->OooOOOO`
- `SpecNotifyChannelManager` = `ctc`, UUID `ry0->OooOOOo`

UUID разворачиваются по короткому номеру (`ry0-><clinit>`, `dj8->Oooooo(int)`):
```
OooOOOO = 26 = 0x001a  → spec WRITE
OooOOOo = 27 = 0x001b  → spec NOTIFY
```
**Это ровно те две характеристики, что оставались белым пятном.**

Broadcast-интерфейс: `action.miot.write.specv2.ble.data` / `...data.resp`
(с полями `mac`, `value`, `timestamp`, `code`).

### 5. Что это значит для нас

Транспорт (`CTR/DATA/ACK`, окно, пейсинг) у нас **уже реализован** в
`dreame_auth.Transport.send_stream`, логин работает. Для чтения батареи нужно:
1. слать на `0x001a` каналом **6** (или 7 для batch), **без** CRC32;
2. слушать `0x001b`;
3. осталось выяснить **бинарную кодировку** запроса `{siid, piid}` (JS отдаёт JSON,
   в байты его превращает нативный слой — искать в `RnBluetoothProviderImpl->doSpecOperation`
   / `bleSpecOperation`).

⚠️ Оговорка про наш прежний неудачный `channel_probe.py`: он слал CTR на канал 6
`0x001a` и получил тишину. Но та проба была признана невалидной (канал 5 на `0x0016`
тоже молчал), так что противоречия с этой находкой нет — проба просто ничего не мерила.
Скорее всего устройство не ACKает CTR без последующих DATA-кадров.

### 6. БИНАРНЫЙ ФОРМАТ spec-кадра — реверс `_m_j/n14->buildBytes`, `classes9.dex`

Кодировщики: `_m_j/c6c` (база, `super z44`) → `_m_j/n14` (одиночный запрос),
`_m_j/m6c` (batch). Всё little-endian.

### Кадр
```
[u16 LE]  (totalLen | 0x2000)     totalLen = 6 + сумма размеров объектов
[u16 LE]  id                       (c6c.OooO0Oo — из конструктора; похоже на transaction id)
[u8]      0                        (константа 0 в этой ветке)
[u8]      count                    число объектов
объекты × count
```
### Объект (размер = 5 + valueLen)
```
[u8]      siid
[u16 LE]  piid
[u16 LE]  (typeCode << 12) | valueLen
[...]     значение, valueLen байт
```
`valueLen` = `SpecValueType.byteLength()`, а для STRING (byteLength==0) — длина
байтов строки (лимит 1024, иначе IllegalArgumentException).

### Таблица типов (`com/miot/spec/entity/SpecValueType.<clinit>`)
```
BOOL=0 (1Б)  UINT8=1 (1Б)  INT8=2 (1Б)  UINT16=3 (2Б)  INT16=4 (2Б)
UINT32=5 (4Б)  INT32=6 (4Б)  далее UINT64/INT64/FLOAT/STRING
```

### Шифрование и отправка
Кадр НЕ уходит в открытом виде: `SpecWriteChannelManager->encryptSendData`
шифрует его сессионным ключом, приём — `SpecChannelManager->decryptReceiveData`.
Путь: JS → JSON `{objects:[...]}` → байты (выше) → broadcast
`action.miot.write.specv2.ble.data` (`mac`,`value`) → encryptSendData →
канал **6** на `0x001a`; ответ — `0x001b` → decrypt → `key_spec_json_resp`.

Также в `BleSecurityConnector` есть `checkSupportSpecV2Notify` / `openSpecNotify`
и флаг `support_spec_v2` — то есть notify на `0x001b` нужно ВКЛЮЧАТЬ отдельно.

### ⚠️ Что здесь ещё гипотеза
- `0x2000` в поле длины — старшие 3 бита похожи на код операции (read/set), но
  проверена только одна ветка `packed-switch` в `n14`; для set/notify флаг может отличаться.
- Какой `typeCode` ставить в ЗАПРОСЕ на чтение (значение отсутствует, valueLen=0) —
  из этой ветки не следует; возможно 0 либо ожидаемый тип свойства.
- Схема `encryptSendData` (какой из ключей сессии и счётчик) не подтверждена —
  предполагаем ту же AES-CCM, что и в login (`ccm_encrypt`: key=sk[16:32], nonce=sk[36:40]+0000+cnt).

### 7. Живая попытка чтения — ОТРИЦАТЕЛЬНЫЙ результат пока

`probes/spec_read.py`, самокат включён, логин OK. Пять вариантов кадра
`siid=1 piid=2` (BATTERY_LEVEL): канал 6 открытым текстом, канал 6 c CCM-шифрованием
(key=sk[16:32], nonce=sk[36:40]+0000+cnt, как в login), без канальной обёртки (raw),
и с `flag=0`. Ответы собирались со ВСЕХ характеристик.

**Результат: полная тишина на всех вариантах** — ни ACK, ни notify, нигде.

### Проверенное допущение (держится)
Мапинг UUID подтверждён дизасмом `_m_j/dj8->Oooooo(I)`:
`String.format("0000%04x-0000-1000-8000-00805f9b34fb", n)` ⇒ `26 = 0x001a`,
`27 = 0x001b`. Характеристики выбраны верно.

### Методическая ошибка первой попытки (исправлена)
Сначала использовался `Transport.send_stream`, но его `_wait_ack_full` фильтрует
ответ строго по той характеристике, куда шла запись (`s == char`). У spec-протокола
write (`0x001a`) и notify (`0x001b`) — РАЗНЫЕ менеджеры, поэтому ACK терялся и
код рапортовал «нет start-ACK». Переписано на собственную отправку, собирающую
ответы со всех характеристик — тишина подтвердилась и после исправления.

### Наиболее вероятная причина
Устройство молча отбрасывает кадр, который не смогло расшифровать. Наша схема
шифрования была **догадкой**. Реальный путь (из дизасма
`SpecWriteChannelManager$1->onResponse`): шифрование — асинхронный вызов
`encryptSendData`, результат которого уходит в `IBleChannelWriter.write(bytes, 0, cb)`
(канальную обёртку CTR/DATA делает уже сам writer). Сама криптография —
`BluetoothApi.standardAuthEncrypt` / `miotBleEncrypt` (обе видны в
`internal/bluetooth/OooO0o->OooO00o`).

### Следующий шаг (конкретный)
Отреверсить `standardAuthEncrypt` / `miotBleEncrypt`: какой ключ из сессии, какой
nonce/счётчик, есть ли префикс/заголовок у шифрованного блока. Без этого перебирать
варианты вслепую бессмысленно — устройство на неверный кадр не отвечает ничем,
то есть обратной связи для перебора нет.

### 8. Схема шифрования отреверсена точно — блокер был не в шифровании

### `BleSecurityChipEncrypt.encrypt` (реверс `_m_j/au0->OooO0OO`, `classes12.dex`)
```
sk    = сессионный ключ устройства (у нас 64 Б из HKDF)
key   = sk[16:32]
nonce = sk[36:40] || 00 00 00 00 || counterBytes(4)
ct    = AES-CCM(key, nonce, кадр)          // tag 4 Б
провод = [u16 LE counter] || ct            // ← 2-байтовый префикс счётчика
```
`counterBytes` (`_m_j/zt0->OooO0O0()[B`): `[low&0xFF][low>>8][high&0xFF][high>>8]`,
то есть 32-бит LE из пары short'ов. Инкремент (`zt0->OooO00o`): `low++`, и когда
переворачивается бит 0x8000 — `high++`.

Итог: **наши ключ и nonce были угаданы верно**, не хватало только префикса счётчика.
Дешифровка ответа — зеркально на ключах устройства (`sk[0:16]`, `sk[32:36]`).

### Активации нет
`BleSecurityConnector->openSpecNotify` — это просто
`IBleConnectManager.notify(mac, FE95, 0x001b, cb)`, т.е. включение CCCD на `0x001b`;
`checkSupportSpecV2Notify` лишь проверяет существование обеих характеристик.
Наш `Transport.connect()` подписывается на все notify-характеристики, так что этот
шаг уже выполнен. Никакого отдельного «открытия spec-канала» в коде нет.

### Живая проверка: снова тишина, но диагностика сместилась
8 вариантов (CCM+префикс, счётчики 0..3, канал 6 и 7, `0x001a` и `0x0016`,
открытый кадр) — **ответа нет ни на одной характеристике**.

**Главное наблюдение (новое и важное):** CTR не ACKается и на `0x0016` — той самой
характеристике, где во время логина ACK приходит стабильно. Причём это верно и для
канала 5 (заведомо рабочего в логине), и для канала 6. То есть:

> После завершения логина устройство перестаёт ACKать CTR на `0x0016` вообще.

Значит стена **не в spec-payload и не в шифровании** (они отреверсены), а в
**канальном слое: после логина канал закрыт/неактивен**, и мы не знаем, чем его
открыть (нужен ли повторный A4, MNG-переговоры на `0x001a`, keepalive, или spec
требует иного порядка).

### Следующий шаг — снять HCI-снуп реальной сессии Mi Home
Ровно так был решён DFU: по снупу телефона. Нужен btsnoop **с самого начала**:
включить Bluetooth HCI snoop в настройках разработчика, открыть Mi Home, зайти на
самокат (чтобы приложение прочитало батарею), выгрузить лог. Парсер готов:
`research_bin/snoop_parse.py`. Снуп покажет: что телефон пишет на `0x0010/0x0016`
после логина, ACKает ли устройство CTR, и на какой характеристике реально идёт spec.
⚠️ Прошлый снуп не годится: он был DFU-сессией и с обрезанными до 3 байт payload'ами.

Пробег вышел ровным `440.0` во float32 — это подтверждает и декодирование типа,
и то, что пробег отдаётся сразу в км. Напряжение float `5344` ⇒ единицы 0.01 В.

### Что было исправлено относительно дизасма

**1. Номер канала = 0, а НЕ 6.** По дизасму `SpecChannelManager->writeBle` я прочитал
`const v3, 6` и решил, что это канал. Снуп показал `CTR 00 00 00 00 01 00` ⇒ **channel 0**
(6 в дизасме — другой параметр). Именно из-за этого раньше была полная тишина.

**2. frameSize = 18.** Кадр надо дробить (как в DFU). Устройство на большой кадр отвечает
pull'ом `ACK 05 [seq]`. Телефон в снупе шлёт крупные кадры, потому что согласовал MNG;
мы MNG на `0x001a` не делаем, поэтому действует дефолт 18.

**3. Ответ приходит МНОГОКАДРОВЫМ потоком, а не одним пакетом.** Устройство само
присылает CTR на `0x001b` (`[0000][00][ch][fc]`), надо ответить `[0000][01][01]`,
собрать fc кадров `[seq u16][data]`, затем `[0000][01][00]`.

**4. Код операции (байт по смещению 4) = 2 для чтения.** Я ставил 0 — устройство
отвечало эхом с пустыми значениями. С `op=2` пошли реальные значения; в ответе `op=3`.

**5. В ОТВЕТЕ у объекта на 2 байта больше, чем в запросе** — есть поле статуса:
```
запрос : [u8 siid][u16 LE piid][u16 LE (type<<12)|vlen]              = 5 + vlen
ответ  : [u8 siid][u16 LE piid][u16 LE status][u16 LE (type<<12)|len] = 7 + len
```

**6. type 9 = FLOAT32** (`SpecValueType`: BOOL0 UINT8=1 INT8=2 UINT16=3 INT16=4
UINT32=5 INT32=6 UINT64=7 INT64=8 FLOAT=9 STRING=10). Читать целым — мусор
(напряжение выглядело как 1168572416).

### Итоговый протокол — проверен на живом устройстве
```
1) login (ECDH P-256 + HKDF + AES-CCM, пин 12****)  -> sk (64 Б)
2) кадр spec: [u16 LE len|0x2000][u16 LE tid][u8 op=2][u8 count] + объекты
3) шифр: [u16 LE cnt] || AES-CCM(key=sk[16:32],
             nonce=sk[36:40]||00000000||counterBytes(cnt), tag 4)
4) 0x001a: CTR [0000][00][0][fc] -> ACK 01 -> DATA [seq u16][18Б] xfc -> ACK 00
   (на ACK 05 [seq] — переслать указанные кадры)
5) 0x001b: CTR от устройства -> ACK 01 -> собрать кадры -> ACK 00
   payload = [u16 LE devCnt][ct], дешифр: key=sk[0:16], iv=sk[32:36]
```

Как u16 **big-endian**: `[0, 10240, 256, 3, 1000]`.

- `0` = циклы = `NUMBER_OF_CYCLES` (0) ✓

## 11. Pipeline обновления MCU в Mi Home — реверс MeshDfuManager

Класс: `com.xiaomi.smarthome.core.server.internal.bluetooth.mesh.MeshDfuManager`
(обфусцирован в `mesh/OooO00o`; реальные имена восстановлены по трассировочным строкам).
Плагин механики не содержит — только `Host.ui.openBleCommonDeviceUpgradePage({auth_type:1})`.

### Полный порядок

```
1. openCommandNotify / openDataNotify     notify на 0x0017 (cmd) и 0x0018 (data)
2. handleProtocolVersion                  версия протокола устройства
   («should update app, current app cannot read mcu fragment index,
     device protocol version is:» ⇒ чтение MCU-индекса зависит от версии протокола)
3. getFragmentSize -> handleFragmentSize  у нас измерено: fragmentSize = 512
4. getLastFragmentIndex (BLE) / getMCULastFragmentIndex (MCU)
   + checkLastFragmentIndex + readInputStreamCRC32   докачка со сверкой CRC32
5. transferFragment / getFragmentBuffer / sendFragmentData / sendData
6. switchFirmware
7. pollMcuVersion                         только для MCU-части
8. onUpgradeSuccess / onUpgradeFailed -> release
```

### switchFirmware: выбор BLE/MCU берётся из состояния сессии

```java
x08 st = stateByMac.get(mac);
int opcode = 4; boolean isMcu = false;                  // по умолчанию BLE
if (st != null && st.OooO0o) { opcode = 6; isMcu = true; }   // MCU
if (isMcu) { log("mcu installing timeout=" + this.OooO0O0);
             invokeResponse(cb, 4, null); }              // прогресс-состояние 4
byte[] params = k81.OooOO0(1);                           // = 01 00 00 00
sendCommand(opcode, params, new fx0(this, isMcu));
```
⇒ `params` совпадает с тем, что шлёт наш флешер (`struct.pack("<I", 1)`) — подтверждено.
⇒ Одна DFU-сессия «знает», BLE-часть она сейчас применяет или MCU (флаг в `x08`).

### pollMcuVersion — как приложение ждёт установку MCU

```java
byte[] p = { 0x01 };                                     // опкод 1 = mcu_version
IBleConnectManager.write(mac, ry0.OooO00o /*FE95*/,
                         ry0.OooOOo0 /*= 28 = 0x001c*/, p, handler(3));
```
**Это тот же однобайтовый кадр `[01]` на инфо-канале `0x001c`, который читаем и мы.**
Отсюда же понятно назначение канала `0x001c`: он обслуживает OTA (версии/железо/серийник),
а не является пробросом к MCU.

⇒ Установка MCU **асинхронная**: BLE-чип ретранслирует образ в контроллер по USART3, MCU
прошивает себя сам, а приложение опрашивает версию до её смены (лог `start poll mcu version`,
`mcu installing timeout=`).

### Тайминги и автомат Handler

| Сообщение | Назначение |
|---|---|
| `12289` (0x3001) | таймаут DFU-команды — **`sendEmptyMessageDelayed(12289, 20000)` = 20 с**, снимается по `DfuCommandCompleteEvent` (сверка по `getCommandOpcode`) |
| `12290` (0x3002) | сторож передачи данных: `removeMessages` + `sendEmptyMessage` на каждом фрагменте |
| `12291` (0x3003) | ставится по `DfuTransferCompleteEvent` |
| `12292`, `12293` | снимаются по `DfuCommandCompleteEvent` |

### Предусловия — из плагина

Заряд **≥ 10 %** (`IS_LOW_POWER`), BLE подключён, самокат **не в движении**
(`isRunning === false`). Обновление стартует только при всех трёх.

### Что из этого гипотеза, а не факт

- `"time_out": 30` из ответа `latest_ver` **разбирается** (`PluginHostApiImpl->parseVersionResponse`),
  и правдоподобно является тем самым «mcu installing timeout». Полную цепочку до поля
  `MeshDfuManager.OooO0O0` не проследил — считать предположением.
- Порядок «сначала BLE-часть, потом MCU» напрямую в коде не подтверждён: флаг `x08.OooO0o`
  говорит лишь о том, что сессия различает части. Порядок покажет снуп реального обновления.

### Практический вывод для нашего флешера

Не хватает шага 7: после `switchFirmware` для MCU надо опрашивать `[01]` на `0x001c`
до смены версии, с таймаутом. Сейчас `dreame_flasher.py` отправляет команду и завершается —
для BLE это нормально (чип перезагружается сам), для MCU это пропущенное подтверждение.

```
#0  @0x18036  n=22   3412..4111 мВ          одиночная (полный диапазон -> OCV/зарядная?)
#1..#4        n=27   3041..3454 / ..3341 / ..3239 / ..3182     группа 1
#5..#8        n=27   3040..3499 / ..3421 / ..3362 / ..3293     группа 2
#9..#12       n=27   3037..3516 / ..3463 / ..3405 / ..3351     группа 3
#13..#16      n=27   3150..3583 / ..3536 / ..3483 / ..3431     группа 4
#17..#20      n=27   3150..3602 / ..3551 / ..3503 / ..3460     группа 5
```
Диапазон 3.02–4.11 В = **напряжение ячейки Li-ion в мВ**. Структура строго регулярна:
20 кривых по 27 точек = **5 групп по 4**, шаг между кривыми 54 Б.

**Интерпретация (сильная, но не проверенная на устройстве):**
- внутри группы конечное напряжение **падает** (3454 → 3341 → 3239 → 3182) ⇒ ось
  **тока разряда**: больше ток — сильнее просадка;
- между группами конечное напряжение **растёт** (3454 → 3499 → 3516 → 3583 → 3602) ⇒ ось
  **температуры**: теплее — меньше просадка;
- рядом лежит ось `-10, 0, 10, 25, 40` — ровно **5** значений, совпадает с 5 группами.

⇒ это **модель батареи 5 (температура) × 4 (ток)** для оценки заряда/остатка.
Согласуется с телеметрией: `REMAINING_BATTERY` в мА·ч, `SOH`, `MORE_BATTERY_INFO`.

**Что НЕ установлено:** ось X внутри кривой (27 точек). Кандидаты рядом — оси
`0..10000` шаг 500 (21 знач., `@0x17fae`) и `0..800` шаг 100 (`@0x17fe6`) — ни одна не
даёт 27, так что X-ось пока не сопоставлена.

### Другие крупные таблицы
```
@0x17784   16 знач., равномерный шаг 4129      (масштабирование/деление?)
@0x236b8 1017 знач., шаг ~50                   линеаризация (ADC/угол?)
@0x23f46  256 знач., шаг ~201                  256-точечная линейная таблица (PWM/DAC?)
```

### Методическая заметка — отрицательный результат
Первая попытка искать **коды ошибок** (`10,11,12,14,15,18,21,24,28,29,39,40,45,50,52`,
взятые из плагина) как байты в образе **провалилась**: 271 «совпавшее» окно — маленькие
байтовые значения встречаются в коде повсеместно, сигнал утонул в шуме. Метод непригоден.
Именно эта шумная проба случайно и вывела на блок таблиц выше, но искать по ней коды
ошибок нельзя. Для кодов нужен другой якорь (например, xref на функцию установки ошибки).

### 12.1 Попытка найти КОД, который читает таблицы — отрицательный результат

Цель: от найденных таблиц (§12) выйти на функции, которые их используют, — это дало бы
и назначение таблиц, и «якорь» в код (в т.ч. для кодов `FAULT`).

**Проба 1 — поиск указателей на таблицы.** Нашлось всего 2 кандидата, оба **ложные**:
```
@0x0ec5c -> 0x00018448   на самом деле это КОНСТАНТА 99400 (в том же пуле рядом:
@0x0ec64 -> 0xffff3cb0 = -50000,  @0x0ec68 -> 0x000186a0 = 100000)
```
То есть `0x18448` совпал с адресом внутри блока кривых чисто случайно: диапазон адресов
блока перекрывается с обычными «круглыми» десятичными константами. Второй кандидат
(`0x08018168`) — того же рода. **Указателей на таблицы в образе нет.**

**Проба 2 — определить базу загрузки APP по литеральным пулам.** Собраны все 33 142
4-выровненных литерала внутри кодовых секций; для каждой базы-кандидата (0x08000000..
0x08040000 и 0x00000000..0x00040000, шаг 0x400) посчитано, сколько значений попадает в
диапазон образа. **Кластера нет:** база 0 даёт 606 попаданий, соседние базы 592–602 —
распределение плоское, то есть это просто мелкие константы, а не указатели.

**Вывод (и почему проба валидна):** обе пробы дали бы явный сигнал, если бы таблицы
адресовались абсолютными адресами из литеральных пулов — так устроено большинство
Cortex-M прошивок. Сигнала нет ⇒ доступ к данным идёт через **базовый указатель в RAM**,
вычисляемый в рантайме.

Это **та же стена**, что уже зафиксирована для дескрипторов USART3 (§«Попытка вытащить ID
команд опроса USART3 — предел»): «базы дескрипторов НЕ заполняются memcpy из flash…
команды пишутся динамически через указатель-базу + смещения». Два независимых захода с
разных сторон дали один и тот же предел ⇒ это **структурное свойство прошивки**, а не
случайность.

**Что это значит практически:**
- **содержимое** таблиц восстанавливается статически (сделано, §12);
- **код, который их использует**, статически не достаётся — нужен SWD-дамп RAM живого MCU
  (пункт C плана), где базовые указатели уже проинициализированы.

## 13. Четвёртый режим езды X / PERFORMANCE — разбор

`1.1 RIDING_MODE`: `11`=P(ходьба), `2`=D(стандарт), `3`=S(спорт), `4`=**X(PERFORMANCE)**.
Наш самокат отдаёт `3` (спорт) — это верх из трёх документированных.

### Признаки того, что режим X не выпущен
| Признак | Наблюдение |
|---|---|
| Локализация | **29 файлов локали, ни в одном нет подписи 4-го режима** (искал `performanceMode`, `turboMode`, `boostMode`, `xMode`, `(X)`). При этом `walkingMode`/`standardMode`/`sportMode` есть во всех. |
| Подсказка UI | Перечисляет ровно три: «…между режимом ходьбы, стандартным режимом (D) и спортивным режимом (S)» |
| Отрисовка | `getDriveModeDesc` (`modules/10010.js`) ветвится только на P/D/S; значение 4 → общая подпись «Режим езды» |
| Гейтинг по модели | Ветка `PERFORMANCE` НЕ обёрнута в условие по PID — хотя модельные функции гейтятся (атмосферная подсветка только `PID5max`) |
| Приём значения | Есть в двух независимых обработчиках: `modules/10013.js:558`, `modules/10448.js:69` |

**Вывод (по совокупности, не факт с устройства):** X — зарезервированный или
недовыпущенный режим, а НЕ функция старшей модели. Плагин общий для трёх PID и локаль
тоже общая, поэтому если бы режим где-то поставлялся, строка нашлась бы в этих же файлах.

### Попутно установлено
- Переключение режимов — **двойным нажатием кнопки питания на самокате**, не из приложения.
- Ходьба ограничена **6 км/ч** (в mi-локали также 3.7 mph); стандарт — по умолчанию;
  спорт — «более быстрый разгон, чем стандартный».
- Плагин обслуживает три модели: `PID5=20886`, `PID5pro=20691` (наш), `PID5max=21166`.
  `CONFIG_PID=20691` совпал с `product_id=0x50d3` из MiBeacon — независимое подтверждение.

### Отрицательный результат: порогов скорости в MCU не нашёл
Пробовал найти в `mcu_0007.bin` таблицу ограничений (ходьба 6 / максимум 25 км/ч) в
кодировках raw, ×10, ×100 — чтобы посмотреть, три там уровня или четыре.
Единственное «попадание» (`600` рядом с `2500`) оказалось ложным: это внутри уже
известной оси `@0x17fe6` (0,100,200,…). **Метод, по-видимому, неверен принципиально:**
в BLDC-контроллере ограничение задаётся в электрических оборотах / периоде коммутации,
а км/ч возникают только при отображении. Искать надо не км/ч.

## 14. Плагин как источник форматов: что удалось декодировать

Подход: у нас оставались свойства, чей формат мы не смогли разобрать. В плагине есть
готовые парсеры — их и извлекли. Все находки перенесены в `docs/FACTS.md`.

| Свойство | Было | Стало |
|---|---|---|
| `4.7 MORE_BATTERY_INFO` | ошибочно прочитано как u16 BE | hex-строка по символам: 3 Б отдача энергии, 2 Б суммарная ёмкость, 2 Б глубокие разряды |
| `4.8 MORE_BATTERY_INFO_2` | не разобрано | год/мес/день/час/мин/сек + u16 секунд |
| `3.7 TIRE_MAINTENANCE` | `"2030030"` непонятно | десятичное `[состояние][интервал дни][остаток дни]` |
| `SIID 6 LOG_1..LOG_5` | «пустые логи» | **журнал поездок**, 10 записей по 4 десятичных поля |
| `1.3 REMAINING_BATTERY` | «мА·ч (подтверждено)» | ⚠️ снова НЕ установлено — плагин это свойство не читает |

### Главный результат — журнал поездок
`LOG_1` запись 0 = `0240 0044 0106 0160` ⇒ **24 мин, 4.4 км, средняя 10.6 км/ч, макс 16.0 км/ч**.

Две независимые сходимости, которых у нас раньше не было:
1. пробег из журнала (4.4 км) **точно совпал** с `TOTAL_MILEAGE` 4.40 км — это подтверждает
   масштаб **0.01 км**, ранее выведенный лишь косвенно (дата активации + 0 циклов);
2. 4.4 км / 10.6 км/ч = 0.415 ч = **24.9 мин** ≈ 24 мин из поля длительности — формат
   внутренне согласован.

Попутно: «логи пустые» было неверно — пустой была только ВТОРАЯ запись в `LOG_1`.

### Ограничение скорости по региону — клампинг в приложении
`modules/10199.js`, `getSpeedValue(speed, SN[0:5])`: EU/German → 20 км/ч, US → 32, иначе 25.
Таблица префиксов SN для трёх моделей есть в `docs/FACTS.md`. Наш префикс `60555`
(distributionReg) ⇒ 25 км/ч. Это клампинг ОТОБРАЖЕНИЯ; поведение прошивки не проверено.

### Методическая заметка
Ошибка с `MORE_BATTERY_INFO` показательна: правдоподобная группировка байт (u16 BE) дала
числа, которые «сошлись» с независимыми свойствами (0=циклы, 1000=SOH) — и это было принято
за подтверждение. Настоящий парсер режет строку иначе, таких полей в формате нет.
**Вывод: совпадение 2 чисел при свободном выборе группировки — не доказательство.**
Проверка считается пройденной, только если разбор взят из источника (парсер/дизасм) либо
если сходимость независима и количественна (как 4.4 км == TOTAL_MILEAGE выше).

## 15. Региональные префиксы SN — есть и в прошивке MCU

Вопрос: знает ли сам контроллер про регион из серийника, или это только приложение?

### Найдено: MCU хранит таблицу префиксов своей модели
В `mcu_0007.bin` @0x24164 лежит **сплошная ASCII-таблица** из 7 префиксов, БЕЗ разделителей:
```
6055 06 05 55 60 55 66 05 57 60 56 16 05 64 61143   (42 байта = 7 × 6 символов)
= 60550 60555 60556 60557 60561 60564 61143
```
Это **в точности все 7 префиксов Scooter 5 Pro** из плагина (`snId_5pro`), и никаких чужих
(5 / 5 Max) — набор модельно-специфичный, не случайный. Лежит в конце последней кодовой
секции (`0x19a00..0x24200`), окружён бинарными данными ⇒ встроенный массив констант.

Проверка по обоим образам:
- **MCU**: 7 префиксов как ASCII (все — 5 Pro). u16 — нет.
- **BLE (RTL8762C)**: как ASCII — НЕТ НИ ОДНОГО; много «совпадений» u16 LE/BE, но это
  ложные срабатывания (числа 60548… как 2 байта встречаются в шифрованном/кодовом мусоре).
  ⇒ значимо только ASCII-присутствие в MCU.

### Что это значит, и чего мы НЕ знаем
✅ **Регион закодирован и в контроллере, а не только в UI-клампинге приложения.** Это
отвечает на исходный вопрос: да, префикс присутствует в MCU-прошивке.

❓ **КАК MCU его использует — статически недостижимо.** Таблица не адресуется абсолютным
литералом (u32 == её адрес не встречается нигде), как и все прочие данные MCU — доступ идёт
через рантайм-базу (та же стена, что с дескрипторами USART3 и калибровочными таблицами §12).
Поэтому НЕЛЬЗЯ статически сказать:
- сравнивает ли MCU реальный серийник с этой таблицей;
- влияет ли результат на ограничение скорости или только на что-то ещё (маркировку, режимы).

⇒ Гипотеза «MCU ограничивает скорость по региону из серийника» стала **правдоподобной**
(таблица есть, модельно-специфичная), но НЕ доказана. Доказать/опровергнуть можно лишь
SWD-дампом RAM живого MCU (пункт C) — увидеть, читается ли серийник в сравнение с этой
таблицей и куда идёт результат.

### Дальнейшая проверка, тоже статическая — что рядом с таблицей
- **Модельность подтверждена жёстко:** в MCU НЕТ ни одного префикса Scooter 5 или 5 Max
  (проверены все 12) — только 7 от 5 Pro. У каждой модели своя прошивка контроллера.
- **Сразу ПОСЛЕ таблицы (@0x24188)** идёт `63 7c 77 7b f2 6b 6f c5…` = **AES S-box**
  (криптоконстанты), а НЕ значения лимитов.
- **ПЕРЕД таблицей (@0x24140)** — пары u16 (0x7ff9/0x7ffd/0x7ffe, 0x2fb9/0x2acd…),
  это не 20/25/32 ни в каком масштабе.
- Значений `20/25/32` (и ×10/×100) в окне ±0x70 вокруг таблицы **нет**.
- Таблица префиксов — **единственная осмысленная ASCII-строка** в области 0x23f00..0x24200
  (всё прочее — бинарные данные).

⇒ Уточнение вывода: наличие таблицы ≠ «MCU режет скорость по региону». Самих порогов рядом
нет, связь «префикс → лимит» внутри MCU не видна. Список регионов может использоваться и для
другого (валидация серийника при активации, набор функций, маркировка). Гипотеза про
скоростной лимит остаётся правдоподобной, но НЕ усиливается статикой дальше этого — предел.

⚠️ Практика: настоящий серийник самоката — уникальный идентификатор транспортного средства,
а региональные лимиты (20/25 км/ч) — требование ПДД для дорог общего пользования. Даже если
MCU сверяет префикс, подмена серийника ради снятия лимита выходит за рамки анализа протокола;
инструмент для этого не делаем. Разбор механизма — да; средство обхода — нет.

### 15.1 Аппаратный путь: серийник ЗАПИСЫВАЕТСЯ по UART — community-инструмент

Источник: `scooterteam/bw-flasher` (UART-флешер контроллеров Brightway/LEQI). Пользователь
подтвердил, что **прошивка MCU этим путём на данной модели работает** (по железу, не по BLE).

**Ключевое для §15 — скрипт `scripts/set_serialnumber.py`:** серийник (а значит и
регион-префикс) можно ПЕРЕЗАПИСАТЬ по UART. Формат кадра:
```
5A 12 97 [len] 30 [19 ASCII серийника] [CRC16-H] [CRC16-L]
```
- команда `0x97` (set serial), 19 символов ASCII, 19200 бод, 8N1;
- CRC-16/XMODEM (poly 0x1021, init 0x0000);
- по разбору адресовано **BLE-чипу RTL8762C** — тому, что у нас отдаёт серийник опкодом 8
  на `0x001c` и свойством `4.4 SCOOTER_SN`. Т.е. серийник хранится/обслуживается BLE-чипом
  и записываем этим кадром.

**Почему по UART шьётся то, что по BLE отвергается:** UART-разъём ведёт к бутлоадеру чипа
(у MCU-флешера — свой крипто-обмен «CRC/bit-reversal/encryption»), работающему НИЖЕ уровня
приложения и Mijia-подписи. Подпись защищает только беспроводной OTA (наш `switchFirmware`
→ status 5/6), физический бутлоадер её не проверяет. Полностью согласуется с нашей моделью.

**Что это меняет для §15 (честно):**
- ✅ ФАКТ: серийник (и регион-префикс) — **записываемый** по UART. Раньше мы только читали.
- ❗ Это НЕ доказывает, что MCU режет скорость по региону. Мы по-прежнему знаем лишь, что
  ПРИЛОЖЕНИЕ зажимает ОТОБРАЖЕНИЕ по префиксу; enforcement в прошивке не подтверждён.
- 🔬 Но появляется РЕШАЮЩИЙ эксперимент для нашей гипотезы: сменить префикс на регион с иным
  лимитом и померить РЕАЛЬНУЮ максималку. Рост скорости → MCU region-locked по серийнику;
  без изменения → лимит зашит иначе. Это и закрыло бы §15.

**Границы (в рамках проекта):** документируем МЕХАНИЗМ (где хранится, как записывается,
где таблица, что проверяет прошивка). Готовый рецепт подмены серийника ради снятия
скоростного лимита для дорог общего пользования — НЕ делаем (это уже не про понимание
протокола). Инструмент чтения/сниффа/дампа — можно; средство обхода лимита — нет.

**Полезное на будущее (в рамках):**
- сниффинг дашборд-UART живого контроллера → реальные ID команд MCU (стена рантайм-RAM);
- если бутлоадер MCU умеет Read Memory (RDP не залочен) → дамп полного flash (config/NVM,
  которых нет в OTA-образе);
- рядом с UART-разъёмом почти наверняка SWD-пятаки → дамп RAM (пункт C плана).

## 16. Эмуляция реальной прошивки MCU, Unicorn — ограничение рантайм-RAM частично снято

Инструмент: `emulator/mcu_emu.py` (Unicorn ARM Thumb). Это НЕ поведенческая модель
(`emulator/scooter_device.py`), а **исполнение настоящих инструкций** `mcu_0007.bin`.

### Метод
Функциональная эмуляция: у нас только APP-регион (нет вектор-таблицы/boot), поэтому
не «boot-from-reset», а вызов конкретной функции с поднятым состоянием. Карта памяти:
flash @0 (+зеркало 0x08000000), RAM @0x20000000, периферия @0x40000000 (заглушки),
Cortex-M @0xE0000000. Хуки: код (счётчик/лимит), запись в USART3 DR, запись в область
дескрипторов, обращения к незамапленному.

### Результат: механизм отправки USART3 доказан исполнением
Прогон планировщика `0x1f600` с поднятыми предусловиями (адреса из его лит-пула):
```
[0x200002c2] = слот (0..2)      [0x200002c1] != -> есть работа
таймер now [0x200001e0] - last [0x20000198] > 432 тиков  -> межслотовый гейт
межбайтовый таймер [0x200001a0] > 8                       -> межбайтовый гейт
USART3 SR [0x40004828] бит14 = 0                          -> «не занято»
```
→ эмулятор записал в USART3 (`0x1f1c2: str r0,[r1,#4]`) байт **`0xD0`** = descriptor[0]
(первый байт засеянного дескриптора слота 0).

**Полностью раскрытый конвейер (по исполнению, не по догадке):**
```
байт_в_USART3 = descriptor[slot*150 + byte_index]     дескрипторы @0x20000a43
descriptor[slot*150 + 0] = ДЛИНА кадра
3 слота × 150 байт, round-robin по [0x200002c2]
1 байт за вызов, byte_index (в [0x20000170+0xb]) инкрементится до длины
таймеры: межслотовый 432 тика, межбайтовый 8 тиков
```
⇒ **ID/кадры команд MCU — это буквально байты рантайм-массива `0x20000a43`.** Раньше это
была «стена» (§«Попытка вытащить ID команд USART3 — предел»). Эмуляция её сняла на уровне
МЕХАНИЗМА.

### Что ещё нужно — честно
Сами ЗНАЧЕНИЯ команд = содержимое дескрипторов, которое заполняет функция инициализации
(в статике не нашли — пишется через рантайм-базу). Следующий шаг: прогнать init-путь под
эмулятором (найти функцию, заполняющую `0x20000a43`, либо эмулировать с более высокой точки)
→ снять реальные байты команд. Метод подтверждён рабочим, осталось применить к init.

### Значение для оценки % разбора MCU
Было: поведение ≈0% (глухая стена рантайм-RAM). Стало: **конвейер USART3 разобран
исполнением реального кода**; не хватает лишь значений из init. Эмуляция — первый
софт-путь к MCU-логике, не требующий железа (SWD/снифф остаются альтернативой).

### 16.1 Извлечён РЕАЛЬНЫЙ кадр команды MCU — эмуляция даёт значения из рантайма

Метод-taint: прогнали ВСЕ 503 функции под эмулятором с хуком записи в область
дескрипторов `0x20000a00..0x20000c10` (`emulator/mcu_emu.py --find-writers`). 47 функций
туда пишут; из них шаблон КАДРА КОМАНДЫ строит одна — **`0x1f1cc`** (вплотную к кластеру
USART3: `0x1f1c0` writer, `0x1f600` scheduler).

Исполнение `0x1f1cc` записало в дескриптор слота 0:
```
0x20000a43: 04 63 44 a7 9c
  [0]=0x04 = длина кадра (4)
  кадр = 63 44 a7 9c
```
Байты пишутся как **immediate-константы** (`movs #0x63; strb [r7,#2]` …) ⇒ команда
ЗАХАРДКОЖЕНА в коде, значение надёжное. Слот берётся из `[0x200002c1]`, селектор из
`[0x2000017c]`; длина и контент — в едином массиве `0x20000a43` (длина в байте 0, что
совпадает с тем, как её читает планировщик).

**Это пробивает «стену рантайм-RAM» на конкретном значении:** ID/кадр команды MCU, которого
НЕТ в статике как данных, извлечён исполнением реального кода. Прежний вердикт «список ID
статически не извлекается» — снят для этого кадра.

### ПОЛНЫЙ набор команд USART3 и ФОРМАТ КАДРА (декодировано)
Разбор всех веток `0x1f1cc` (строго: immediate читается из кода с тесной привязкой к
регистру strb) дал **5 команд** одного формата:
```
кадр = 63 | CMD | (0x63 + CMD) & 0xFF | 9C
       header    checksum(=hdr+cmd)     trailer (0x9C = ~0x63, комплемент header)
CMD ∈ {0x42, 0x43, 0x44, 0x45, 0x46}
```
Кадры: `63 42 a5 9c`, `63 43 a6 9c`, `63 44 a7 9c`, `63 45 a8 9c`, `63 46 a9 9c`.
Все с согласованной контрольной суммой. Это периодические ЗАПРОСЫ, которые MCU шлёт
BLE-чипу по USART3 (5 категорий данных, выбор ветки — по таймингам, порог `0x19<<7=3200`).

⇒ **«Список ID команд статически не извлекается» — ОКОНЧАТЕЛЬНО СНЯТО.** Формат кадра +
5 команд получены. (Header 0x63 / trailer 0x9C = комплементы — это framing, не 55AA.)

### Что ещё не сделано (честно)
- **Семантика** команд 0x42–0x46 (какая что запрашивает — батарея/скорость/статус?) —
  нужен снифф живого USART3 либо разбор RX-обработчика (ответы BLE→MCU).
- **RX-путь**: хукнуть чтение USART3 RX, подать ответы → пройти парсер ответа → увидеть,
  куда в RAM-стейт раскладываются телеметрия/статусы. Следующая цель эмуляции.
- Прочие 46 функций пишут в дескриптор ПОЛЯ СОСТОЯНИЯ (флаги/счётчики), не кадры.

### Итог по методу
Эмуляция реального кода: (1) доказала механизм отправки USART3; (2) вытащила конкретный
кадр команды из рантайма. Это первый софт-путь, реально добывший значения из-за «стены»,
без SWD/железа. Полный набор команд = развитие того же подхода (модель подпрограмм + RX).

### 16.2 Граница функциональной эмуляции — что берётся, что нет, проверено

После извлечения команд USART3 попробовали ту же эмуляцию на двух других целях —
получили ЧЁТКУЮ границу метода:

| Цель | Адресация данных | Результат эмуляции |
|---|---|---|
| USART3 команды (`0x1f1cc`, `0x1f600`) | **абсолютные литералы** (0x20000a43, 0x40004800) | ✅ взято полностью (§16–16.1) |
| RX-парсер ответов BLE→MCU | IRQ-хендлер (нет в вектор-таблице OTA) | ❌ функцию не локализовать без вектор-таблицы |
| Регион-проверка по SN (таблица `0x24164`) | **вычисляемый указатель-база** | ❌ read-taint по 503 функциям → **0 чтений** таблицы |

**Read-taint (проверка):** прогнали все 503 функции с хуком чтения `0x24160..0x241a0`
(таблица префиксов). При RAM=0 база указателя не резолвится в 0x24164 → 0 попаданий.
Абсолютных литералов на таблицу тоже нет (проверено). ⇒ доступ строго через рантайм-базу.

**Вывод (честно):** функциональная эмуляция (вызов одной функции) чисто добывает всё, что
адресовано **абсолютно**, и упирается там, где нужен указатель из общего состояния.
Это не случайность — структурная граница.

**Что сдвинет дальше (по убыванию):**
1. **Широкая эмуляция от init/main** — чтобы рантайм-указатели поставились сами. Блокер:
   в OTA-образе НЕТ вектор-таблицы/reset (только APP), точки входа нет. Кандидат в «главный
   init» искать отдельно, исход неясен.
2. **Снифф живого USART3** — семантика команд 0x42–0x46 + формат ответов сразу.
3. **SWD-дамп RAM** — все вычисленные указатели уже готовы.

### 16.3 Широкая эмуляция от init — попробована, упёрлась в отсутствие точки входа

Апгрейд `emulator/mcu_emu.py`: `run_broad()` — маппинг страниц по требованию, детект
spin-loop, толерантность к периферии (инфраструктура работает). Цель: прогнать init,
чтобы рантайм-указатели (для регион-проверки / RX) поставились сами.

**Кандидаты в main/init** — по числу уникальных `bl`: `0x123d4` (65), `0x06fc0` (39),
`0x0799c` (29), `0x063b8` (28). `0x123d4` — ещё и топ-писатель в глобальный стейт.

**Результат:** все выходят за **131–1630 инструкций** — гейтятся аргументами/предусловиями
(при пустом состоянии early-return, 65 вызовов в непройденных ветках). Каскад инициализации
не стартует.

**Причина — подтверждена строго:** искали вектор-таблицу Cortex-M (SP + reset + Thumb-
обработчики) по всему образу → **не найдена** (единственный «кандидат» @0x17e8 — ложное
совпадение, 0 соседних векторов). ⇒ в OTA-образе **нет reset-хендлера/точки входа** (они
в загрузчике, вне образа). Бутстрапить рантайм-состояние не с чего.

### 16.4 RX-ПУТЬ — полностью разобран и доказан исполнением, 2026-08-17

«Следующая цель» из §16 (RX-парсер ответов BLE→MCU) закрыта. Инструменты:
`emulator/mcu_emu.py --rx-feed`, `research_bin/mcu_rxloop.py` (полный цикл: ISR-фреймер +
диспетчер, всё исполнением), `research_bin/mcu_dispatch.py`.

#### 16.4.1 USART3 RX ISR `0x1e480` — побайтовый фреймер (доказано исполнением)

Статически идентифицирован как USART3-ISR, исполнением подтверждён побайтово:
```
вход:  USART3 SR [0x4000483C] бит10 (RXNE) — гейт; байт из DR [0x40004800]
стейт: state [0x200002be], слот [0x200002bf], idx u16 @0x20000038, timeout u16 @0x200002bc
RX-дескрипторы: база 0x20000881, 3 слота × 150 Б (ОТДЕЛЬНО от TX-дескрипторов 0x20000a43!)
computed-goto через хелпер 0x21b52; индекс свитча = state+1 (проверено 8/8)
```
Состояния: 0=синх(0x74) → 1=CMD → 2=LEN → 3=цикл данных (пока idx<LEN+3) →
4=трейлер1 → 5=трейлер2 + finalize (слот++). Нехарактерный байт в состоянии 0 —
таймаут-сброс. Producer `[0x200002bf]` инкрементируется 0→1→2→0 после кадра.

#### 16.4.2 Формат RX-кадров (выведен исполнением, не догадкой)

```
Класс A:  74 CMD LEN DATA[LEN] CHK2 8B        длина = LEN+5
          CHK2 = sum(frame[0..LEN+2]) & 0xFF   (сумма ВСЕХ предыдущих байтов)
Класс B:  74 CMD 4F 4B CHK1 8B                длина = 6 («OK»: ASCII 'O','K')
          CHK1 = (0x74 + CMD + 0x4F + 0x4B) & 0xFF
Класс A CMD: 0x41–0x46, 0x48–0x4A, 0x60, 0x61
Класс B CMD: 0x40, 0x47, 0x4B, 0x63
```
**0x8B = ~0x74 — комплемент синхро-байта.** Та же схема комплементов, что и в TX
(0x9C = ~0x63): framing не 55AA, а «header + комплемент». Класс B — это ответы-ACK
(«OK») на команды MCU; класс A — данные-ответы на запросы 0x42–0x46.

#### 16.4.3 Диспетчер `0x1e9e0` — ступенчатая машина (доказано исполнением)

Каждый вызов = одна ступень. Стейт в CTX-структуре @0x20000170:
```
CTX[1]@+1 = ступень   CTX[2]@+2 = «кадр валиден»   CTX[3]@+3 = LEN
CTX[4]@+4 = idx суммы  CTX[5]@+5 = накопленная сумма  CTX[6]@+6 = 0x8B
consumer [0x200002c0], producer [0x200002bf] (от ISR); consumer==producer → выход
```
Ступени: 0=синх(0x74) → 1=разбор CMD →
- класс B: 2=(frame[2]==0x4F?) → 3=(frame[3]==0x4B?) → 4=CHK1 → 5=frame[5]==0x8B;
- класс A: (CTX[3]:=LEN) → 10=цикл суммы CHK2 → 11=frame[LEN+4]==0x8B.
Ошибка на любой ступени: consumer++ (кадр отклонён), ступень→0. Успех: CTX[2]=1 →
**секция извлечения полей** в том же вызове, затем consumer++.

**Отрицательный тест:** кадр с битым CHK2 → ступени 0→1→10, на 10 отклонён,
consumer++, записей полей нет, флаг 0x2c9=0. Проверка реально работает.

#### 16.4.4 ПОЛНАЯ карта «поле кадра → адрес RAM» — все 15 CMD, сверено исполнением

Каждый кадр подавался побайтно в реальный ISR, затем реальный диспетчер; записи в RAM
снимались хуком. Данные-тест: DATA[i]=0x11+i.

| CMD | хендлер | куда (RAM) |
|---|---|---|
| 0x40 | (класс B, ACK) | ничего — чистый ACK |
| 0x41 | `0x1ec74` | [3..4]→u16 BE @0x2b0; [5]→нибблы (lo@0x2b2, hi@0x2b3); [6]→@0x2b4; бит7([7])→@0x2b5; @0x2b6=0 (?); [7],[8],[9]→@0x2b7..0x2b9. **Зеркало того же расклада: @0x2e8..0x2f1** |
| 0x42 | `0x1ed90` | [3..9] → 7 байт @0x2cb..0x2d1 ✅ (совпало со статикой §6.5) |
| 0x43 | `0x1edba` | [3..9] → **7** байт @0x2d2..0x2d8 (в статике §6.5 было 6 — поправка!) |
| 0x44 | `0x1eeb4` | [3]→@0x2e6; [4]→@0x306; [5..6]→u16 LE @0x308; [7..8]→u16 LE @0x30a; [9]→@0x30c; [10..11]→u16 LE @0x30e ✅ (§6.5) |
| 0x45 | `0x1ef08` | 6×u16 LE @0x2da,0x2dc,0x2de,0x2e0,0x2e2,0x2e4; [0xf]→@0x2e7 ✅ (§6.5) |
| 0x46 | `0x1ee86` | буфер @0x2f2..: сначала обнуление, затем frame[3..3+LEN) копируется; счётчик → CTX[4]@0x174 ✅ (§6.5) |
| 0x47 | (класс B «OK») | флаг @0x2c9=1; копия кадра @0x200010b5.. |
| 0x48 | `0x1ef58` | [3..6] → 4 байта @0x354..0x357 (НОВОЕ, не было в §6.5) |
| 0x49 | `0x1efc8` | LEN→u16 LE @0x36a; DATA[13] → буфер @0x20001585.. (НОВОЕ) |
| 0x4A | `0x1f036` | LEN→u16 LE @0x36c; DATA[13] → буфер @0x20001607.. (НОВОЕ) |
| 0x60 | `0x1f0ca` | только флаг @0x2c9=1 — событийный кадр (НОВОЕ) |
| 0x61 | `0x1f112` | только флаг @0x2c9=1 — событийный кадр (НОВОЕ) |
| 0x4B | (класс B «OK») | флаг @0x2c9=1; сброс байта @0x369 (НОВОЕ) |
| 0x63 | (класс B «OK») | флаг @0x2c9=1; сброс байта @0x36f (НОВОЕ) |

**Общее для всех хендлеров:**
- **флаг `0x200002c9` ← 1** — «есть новые RX-данные» (его опрашивает main-loop);
- **лог-буфер последнего кадра @0x200010b5**: `[0]=длина кадра, [1]=тип(0x64/0x65),
  [2]=?, [3]=N, [4..4+N)=данные, ..., [-1]=chk` — диагностический эхо-хвост.

#### 16.4.5 Значение

1. **RX-путь закрыт полностью**: побайтовый вход → фреймер → валидация (2 контрольные
   суммы + комплементы) → извлечение полей → RAM-стейт. Всё исполнением реального кода.
2. **Семантика TX-команд 0x42–0x46 теперь известна структурно**: запрос `63 CMD xx 9c`
   от MCU вызывает у BLE-чипа ответ-класс-A с тем же CMD, поля которого раскладываются
   по адресам из таблицы выше. Телеметрия = данные этих ответов.
3. Статика §6.5 подтверждена исполнением (0x42/0x44/0x45/0x46), исправлена (0x43: 7 байт)
   и расширена (6 новых CMD-хендлеров, которых в статике не было).
4. Остаток по семантике: ФИЗИЧЕСКИЙ смысл полей (батарея/скорость/…) — это разбор
   ПОТРЕБИТЕЛЕЙ адресов (кто читает 0x2cb.. и т.д.) или живой снифф для сверки значений.

### ИТОГ по эмуляции MCU — честно, окончательно для софта
| Что | Софт-эмуляция |
|---|---|
| Механизм отправки USART3 | ✅ доказан исполнением (§16) |
| Набор команд USART3 (5 шт, формат кадра) | ✅ извлечён из рантайма (§16.1) |
| RX-путь: фреймер + валидация + парсер | ✅ полностью разобран исполнением (§16.4) |
| Карта «поле ответа → RAM» для всех 15 CMD | ✅ снимка хуком записей, сверено (§16.4.4) |
| Физическая семантика полей (батарея/скорость) | ◐ структурно: ответ→адрес; значения — потребители/снифф |
| Регион-проверка по SN (§15) | ❌ вычисляемый указатель, read-taint = 0 |
| Широкая эмуляция от init | ❌ нет точки входа в OTA-образе |

**Граница софта сдвинута:** RX-путь, который раньше казалось недоступным без вектор-
таблицы (IRQ-хендлер), взят — функция была найдена статически, а «нет вектор-таблицы»
не помешало: вызов ISR напрямую с поднятым SR-регистром работает. Осталась только
физическая семантика полей (потребители адресов) и регион-проверка (вычисляемая база).

## 17. Кросс-референс: Scooter 4 Pro, SWD, предыдущее поколение — подтверждает §15

Источник: `CamiAlfa/m365-Electric-Scooter-4-Pro-stlink` (SWD-флешер контроллера 4 Pro).
4 Pro — прямой предшественник 5 Pro, то же семейство (STM32F1-контроллер). НЕ наш самокат,
но сильная аналогия: тот же класс чипа, те же региональные значения скорости.

### Флеш-раскладка контроллера 4 Pro — STM32F1, по SWD
```
0x08000000  boot.bin      (2956 Б)   загрузчик,  вектор-таблица (SP=0x20000560, reset=0x08000121)
0x08001000  EC_ESC_Driver (46260 Б)  прошивка,   вектор-таблица (SP=0x20004338, reset=0x08001101)
0x0801c800  data.bin      (512 Б)    конфиг/NVM
```
Скрипт `flash_pro4_1gen.py`: `stm32f1x unlock 0` (снять RDP → mass-erase), читает UUID чипа
`0x1FFFF7E8`, пишет в конфиг: **SN@0xa8, UUID@0x1b4/1b8/1bc, пробег(KM×1000)@0x52**.

### Регион→скорость энфорсится в контроллере — доказано на 4 Pro
Diff `EC_ESC_Driver_V0.2.2.bin` vs `_mod.bin` (анлок): 100 байт в 18 участках, два вида:

**(а) Подъём лимитов скорости — прямые константы @0x08007dcc:**
```
stock: 14 22 … 4f f0 19 0e   movs r2,#0x14(20) … mov.w lr,#0x19(25)
mod:   19 22 … 4f f0 20 0e   movs r2,#0x19(25) … mov.w lr,#0x20(32)
```
⇒ **20→25 и 25→32 км/ч** — ровно значения EU/прочие/US из плагина (§FACTS).

**(б) NOP проверки серийника/региона @0x08008a64:**
```
stock: 41 78 35 29 … 81 78 38 29 … c1 78 30 29 … 01 79 32 29
     = ldrb serial[1];cmp '5'  [2];cmp '8'  [3];cmp '0'  [4];cmp '2'
mod:   00 bf …  (всё NOP)
```
⇒ контроллер ЧИТАЕТ серийник, сравнивает символы регион-префикса и ветвится на лимит; анлок
вырезает это сравнение. Плюс ноплены записи флагов `strb [r6,#0x3e..0x45]` (те же смещения
стейт-структа, что видели в 5 Pro).

**Вывод:** гипотеза §15 («MCU режет скорость по региону из серийника») — для **4 Pro доказана
в прошивке**. Для 5 Pro это НЕ прямое доказательство (другое поколение), но сильнейшая
аналогия: то же семейство чипа, тот же механизм (cmp символов серийника → константа лимита),
те же значения 20/25/32.

### Поправки к нашему SWD-плану — пункт C
1. **RDP ВКЛЮЧЁН** на этом поколении → на 5 Pro наивный `dump_image`, вероятно, заблокирован,
   а `unlock` уничтожает flash. Дамп может оказаться **деструктивным** или недоступным без
   стирания. Проверять осторожно (сначала статус RDP, без unlock).
2. **Полный образ = вектор-таблица + boot + app + config** → SWD-дамп даёт точку входа,
   снимая блокер широкой эмуляции (§16.3). Но см. п.1 (RDP).
3. **Шаблон конфига:** SN@0xa8, UUID-привязка@0x1b4, пробег@0x52 — что искать в дампе NVM.

⚠️ 4 Pro ≠ 5 Pro. Всё выше — аналогия предыдущего поколения, не факт с нашего устройства.

## 18. Подписка на пуш свойств — механизм = CCCD, 2026-08-15

Вопрос: как включить потоковую телеметрию (пуш изменившихся свойств), чтобы снять
ограничение «одно свойство за запрос» (§7, §9).

### Механизм — уже есть в нашем транспорте
Подписка на пуш = **CCCD на `0x001b`** (spec-notify). `Transport.connect()` сам вызывает
`start_notify` для ВСЕХ notify-характеристик FE95, включая `0x001b` — т.е. CCCD ставится ещё
до логина. Отдельной «команды подписки» на уровне протокола НЕТ (см. §«Активации нет»:
`IBleConnectManager.notify(..., 0x001b)` = включение CCCD; `bt.subscribeMessages` плагина —
это лишь локальная маршрутизация JS-колбэков по темам `prop.<siid>.<piid>`).

### Доказательство того, что RX-путь работает
`spec_read.py` успешно принимает ОТВЕТЫ на чтение на `0x001b` — а приходят они тем же
notify-путём, который требует установленной CCCD. Значит подписка реально работает; пуш идёт
**тем же путём**, только без предшествующего запроса на `0x001a`.

### Что это даёт
- 20 подписываемых свойств (из `modules/10013.js parseNotifyData`):
  `1.1 1.2 1.4 1.5 1.6 1.7 1.8 1.9 2.1 2.7 2.13 2.14 2.15 2.16 2.17 2.18 3.1 3.2 3.4 3.10`.
- Пуш приходит **только при ИЗМЕНЕНИИ** свойства ⇒ на стоящем самокате с полным зарядом
  тишина не опровергает механизм; чтобы поймать трафик, надо менять состояние (газ/свет/движение).

### Инструмент
`probes/spec_listen.py` — слушатель: логин → слушает `0x001b`, дешифрует (ключи устройства),
разбирает spec-кадр, печатает свойства с единицами. Только чтение (+обязательные ACK).
В этот раз исправлен вводящий в заблуждение docstring (подписка ЕСТЬ через `connect()`) и
добавлен `SUBSCRIBABLE` — свойства вне списка помечаются `[вне списка подписки]`.

### Осталось — требует живого устройства
Live-подтверждение: `python probes/spec_listen.py --secs 120` на включённом самокате с
активным изменением состояния. Механизм и парсер готовы; не хватает только поймать реальный
пуш на проводе (предыдущие «тихие» прогоны были без изменения свойств).

## 19. Найден официальный источник по флеш-раскладке RTL8762C — новая зацепка по AES-ключу, 2026-08-15

Через WebSearch/WebFetch найдены и прочитаны два официальных документа Realtek:
`RTL8762C Flash User Guide` и `RTL8762C Memory User Guide` (v1.1, 2018/09/12, помечены
"Confidential" — не сохранены в репозиторий, только прочитаны и законспектированы).

### Flash User Guide
Ничего нового по шифрованию — только API флеш-драйвера, bit-mode, Block Protect, XIP-механизм
переключения сцен. Подтверждает уже известную карту адресов: cache-регион `[0x800000,0x1000000)`,
non-cache `[0x1800000,0x2000000)` — совпадает с полями заголовка нашего BLE-образа
(`header[0x20]=0x01805fc8`, `header[0x28]=0x01803000`).

### Memory User Guide — раскладка физического флеша чипа
```
Reserved      0x800000   4K    зарезервировано
OEM Header    0x801000   4K    конфиг устройства: BT-адрес, AES-ключ, раскладка флеша
OTA Bank 0    0x802000   var   OTA Header + Secure Boot + Patch + APP (+ APP Data1/2)
OTA Bank 1    var        var   резервный банк (если поддержан bank-switch)
FTL           var        var   логическая адресация BT-стека/APP-данных
OTA Tmp       var        var   буфер OTA (сюда шли наши DFU-фрагменты)
APP Defined   var        var   свободная зона
```
(Базовый адрес `0x800000` — это RTL8762C SDK по умолчанию; у Dreame использован non-cache
алиас `0x1800000`, тот же относительный layout — уже подтверждено в §«RTL8762C SDK-репозиторий».)

**Ключевая находка:** по описанию Realtek сектор `OEM Header` явно хранит **AES-ключ**
(наряду с BT-адресом и раскладкой флеша) как часть конфигурации устройства. Это отдельный
физический сектор флеша, ВНЕ `OTA Bank 0` — то есть вне того, что содержится в нашем `.bin`
(наш файл = только тело OTA Bank0/OTA Tmp, начинается с `OTA Header`, не с `Reserved`).

**Почему это меняет план:** весь прежний вывод «расшифровка невозможна без SWD» (§«Вывод про
расшифровку», §«ИТОГ по обходу AES-стены») основан на том, что ключ живёт в OTP/eFuse, а
`rtltool read_flash` читает только сырой (для APP — зашифрованный) флеш. Но `OEM Header` —
КОНФИГУРАЦИОННЫЙ сектор, не код приложения; нет оснований считать его зашифрованным той же
XIP-схемой, что и `OTA Bank 0`. Если ключ там лежит открытым текстом — это читается ОБЫЧНЫМ
`rtltool.py read_flash` по UART, БЕЗ SWD.

⚠️ **Не доказано и не проверено:**
- совпадает ли ключ из `OEM Header` с тем, что реально шифрует `OTA Bank 0` (выбор через
  `enc_key_select=7` в OTA-заголовке нашего образа — не исключено, что это ссылка именно на
  eFuse/OTP, а ключ в `OEM Header` используется для чего-то другого, например BT-storage);
- сам факт, что `OEM Header` не зашифрован — это вывод из общей формулировки документа,
  не из проверки на конкретном чипе.

**Следующий шаг (дёшево, до SWD):** `rtltool.py read_flash 0x801000 0x1000` (и/или на алиасе
`0x1801000`) — прочитать сектор `OEM Header`, посмотреть на энтропию/структуру, и если похоже
на ключевой материал — прогнать через `research_bin/decryptor.py` как кандидат для `OTA Bank 0`.
Перенесено в `todo.md` §B как первый шаг (дешевле SWD, тот же UART, что уже используется
для `chip_id`/`read_mac`).

### 19.1 MP Tool / Pack Tool User Guide — судя по всему, ДВА разных ключа, 2026-08-15

Пользователь скачал официальный пакет `BeeMPTool-v1.1.2.4.zip` с realmcu.com (это же
позволило почить `rtltool` под текущую версию MP Tool — см. правки в `zip_archives/rtltool/`,
файл-стаб теперь называется `RTL8762C_FW_B.bin`, а не `firmware0.bin`). Внутри — `RTL87x2x MP
Tool User Guide-EN.pdf` (70 стр.) и (из `MPPackTool_v2.0.6.9.zip`) `RTL87x2x Pack Tool User
Guide-EN.pdf` (16 стр.). Оба "Confidential", в репозиторий НЕ сохранены — только выжимка фактов.

**Похоже, что "AES-ключ" из `OEM Header` (§19) и ключ, которым реально шифруется APP
(`enc_key_select`) — это ДВА РАЗНЫХ ключа:**

1. **"OTA AES Key"** (MP Tool, MP Setting page, дважды упомянут в тексте гайда) — по описанию:
   «used to set whether the OTA needs to be encrypted for transmission, and the AES Key used
   for encrypted transmission can be input by the users». Похоже на ключ **транспортного**
   шифрования OTA-пакета (то, что мы уже реверснули на канальном уровне — `useCrc32Verify=false`
   и вся канальная обвязка DFU), а не обязательно на шифрование самого APP-образа. Именно этот
   ключ и хранится, по всей видимости, в секторе `OEM Header` флеша (см. §19) — задаётся
   производителем произвольно при конфигурации MP Tool, значит-то место и есть плейсхолдер
   `OTA_AES_KEY` из `oem_config.c` SDK (который мы уже пробовали в `decryptor.py`, безрезультатно).

2. **"OCEK"** (новый термин, MP Tool §"Security Config", генерирует `Efuse.json` для
   **прошивки в eFuse**, отдельно от Flash): «"Security Config" feature is used for encrypting
   the App Image. Users can enter or import OCEK and password... select encryption level...
   see RTLxxxx Security Mechanism User Guide». **Это, вероятно, и есть тот самый ключ, на
   который ссылается `enc_key_select=7` в заголовке нашего образа** — раз он прошивается
   именно в eFuse (OTP), а не во Flash-сектор `OEM Header`.

**Так что вывод из §19 нужно уточнить:** ключ из `OEM Header` (Flash, потенциально читаемый
по обычному UART) — вероятно, **другой ключ** (транспортный/OTA-пакет), а не тот, что
расшифровывает содержимое `OTA Bank 0` при XIP-исполнении (это, судя по всему, "OCEK" в eFuse).
**UART-дамп `OEM Header` всё ещё стоит попробовать** (дёшево, может совпасть или дать зацепку
про формат ключа), но ожидания снижены — вероятнее всего, потребуется именно SWD/eFuse-путь.

⚠️ Существует ещё документ **`RTLxxxx Security Mechanism User Guide`** — в скачанном наборе
инструментов его нет (это SDK-документ, не идёт в комплекте с MP/Pack Tool). Если найдётся —
там должна быть точная механика App-шифрования и расшифровка значений `enc_key_select`.

### 19.2 Найден `RTL8762C Security Mechanism User Guide` — вопрос закрыт почти полностью, 2026-08-15

Найден и прочитан (WebSearch → usermanual.wiki, "Confidential", в репо не сохранён — только
факты). Это авторитетный документ именно про механизм шифрования APP/ключей, на который
ссылался MP Tool Guide. Отменяет и уточняет часть выводов §19/§19.1.

**§2.1 Image Encryption:** AES-128 (не 256), симметричный. **«When IC is booting, image will
be decrypted by reading the key in eFuse»** — ключ читается ТОЛЬКО из eFuse при загрузке.
Про `OEM Header` (Flash) как источник ключа для APP — нигде не сказано; значит «AES Key» в
`OEM Header`, вероятно, и есть тот отдельный **транспортный** «OTA AES Key» из §19.1, а НЕ
ключ, расшифровывающий `OTA Bank 0`. UART-дамп `OEM Header` остаётся дешёвой пробой, но
ожидания по нему теперь низкие: ключ приложения по документу живёт только в eFuse.

**§2.2 eFuse Key — ключ per-chip, не общий:** "Encryption and decryption use the same 128-bit
key" — OCEK симметричен. НО: при прошивке ключа в конкретный чип **Download Tool читает UUID
чипа и комбинирует его с оригинальным OCEK, чтобы получить НОВЫЙ, уникальный для каждого
конкретного экземпляра ключ**. Точная формула комбинирования не документирована. Значит даже
если бы утёк "мастер" OCEK Dreame (например, из прошивочной цепочки/сборочного скрипта),
расшифровать конкретно НАШ образ всё равно нельзя без UUID именно нашего чипа И знания
формулы комбинирования — она нигде в этом документе не раскрыта.

**§3 Security Level — САМОЕ ВАЖНОЕ, меняет план по SWD:**

| Level | SWD | eFuse Read | eFuse Write | HCI Download |
|---|---|---|---|---|
| 0 (открыто) | Enable | Enable | Enable | Enable |
| 1 (мелкосерийно) | по паролю | по паролю | Enable | Enable |
| 2 (**рекомендован для mass production**) | по паролю | **Disable** | по паролю | Enable |

На Level 2 (который Realtek сам рекомендует для серийного производства — то есть именно то,
что почти наверняка стоит на коммерческом самокате Dreame) **чтение eFuse ОТКЛЮЧЕНО
БЕЗ ВОЗМОЖНОСТИ РАЗБЛОКИРОВКИ ПАРОЛЕМ** — в отличие от SWD и eFuse-write, у которых
есть путь "по паролю", у eFuse Read стоит голое "Disable". Пароль тоже прошит в eFuse и
нам неизвестен ни при каком уровне.

**Что это значит практически:**
1. **Прямое чтение ключа из eFuse — тупик** при Level 1/2 (наиболее вероятный сценарий для
   серийного продукта), с паролем или без — на Level 2 эта дверь просто отсутствует.
2. **SWD тоже вероятно за паролем** (Level 1/2), которого у нас нет и получить неоткуда
   (он не в файле, не в переданных нам архивах — вводится вручную при конфигурации MP Tool
   на заводе Dreame). Реактивировать SWD через "Password Debug" (§2.4/§4.4) мы не можем.
3. **НО план из `todo.md` §B (SWD-дамп XIP-региона `0x0180E000`) в принципе остаётся
   правильным по методу**, если SWD окажется открытым (Level 0) или Dreame не следовал
   рекомендации Realtek: чтение по SWD идёт через ту же шину, что и исполнение кода — то есть
   через тот же аппаратный декрипт "на лету", и НЕ требует знать сам ключ. SWD дамп не читает
   ключ напрямую, а читает уже расшифрованные байты с шины — эта часть метода не пострадала
   от находки про eFuse Read.
4. Значит единственный практический тест теперь — **физически проверить, отвечает ли SWD
   вообще** (до чтения eFuse, которое почти наверняка не потребуется/не сработает). Если SWD
   молчит/просит пароль — тупик без физической атаки на кристалл (вне рамок проекта).

Также обнаружено (не по теме ключа, но полезно на будущее): `10.4 Password` — у флеша есть
отдельный **пароль блокировки** (Password key), не связанный с AES; `chip_id`/`read_flash` в
нашем `rtltool` его не используют. По `Flash User Guide` (§19) Block Protect ограничивает
только WRITE/ERASE, не READ — так что пароль не должен мешать именно `read_flash`.

## 20. Повторный разбор APK и плагина — что упущено, 2026-08-16

### 20.1 Плагин: ключа прошивки нет, крипта нативная (подтверждено)
242 JS-модуля RN-бандла. `aes` встречается только внутри локализации (итал. «Pa**es**e»),

### 20.2 LED/button `0x0101/0x0102` из плагина — на 5 Pro отсутствуют
`modules/10724.js`: `UUID_LED_READ_WRITE`=`00000101-…`, `UUID_BUTTON_READ_WRITE_NOTIFY`=`00000102-…`.
Плагин обслуживает 3 модели (PID5pro=20691, PID5=20886, PID5max=21166). Живое GATT-перечисление
нашего 5 Pro (2026-08-16) показало характеристики `0x0004,0x0005,0x0010,0x0016,0x0017,0x0018,
0x001a,0x001b,0x001c` — **`0x0101/0x0102` физически нет**. Это характеристики другой модели, не
упущенная поверхность. Button-notify в `10679.js` расшифровывается тем же `securityLock.
decryptMessage` — то есть это UI привязки (activate/QR), а не скрытый обход.

### 20.3 Новое: характеристики `0x0004` и `0x0005` (см. FACTS.md)
`0x0004` [read] = версия BLE открытым текстом без логина. `0x0005` [read+notify] — событийный
encrypted-notify, по read пуст, пассивно молчит. Подробности и способ триггера — в FACTS.md
(раздел GATT). Оба в снупе не встречались, в проекте раньше не документировались.

### 20.4 Реверс SET-протокола из dex — «стена последней мили» закрыта, 2026-08-16
Декомпиляторов в системе нет — поставлен `androguard` (pip). APK `64bitpackage.apk` → извлечены
`classes*.dex`; класс `L_m_j/n14;` (spec packet) — в `classes9.dex`. Декомпиляция
`n14->OooO0o0()[B` (spec toBytes) дала недостающий **op-байт для SET**:

- дискриминатор пакета (`n14.OooO0o0 I`, 3-й арг конструктора) → `packed-switch` на 3 ветки;
- **case 0 → wire op=5 (ACTION)**, **case 1 → wire op=2 (GET)**, **default → wire op=0 (SET)**;
- элемент SET = `[siid][piid u16][ (type<<12)|vlen  u16 ][value]` (`c6c.OooO0oO`/`OooO0oo`).

Прежняя `dreame_dfu_protocol.md` фиксировала «стену»: наш property-set транспортом ACK'ался, но
устройство молча его роняло; op-байт был угадан как `0x00`-без-значения / позже я пробовал `4` —
оба мимо. Верный ответ: **op=0 СО значением**. Проверено live записью `IS_LOCKED(2,2)` 1→0
(самокат заблокировался и разблокировался, ответ `op=1 status=0`). Формат set + весь
session-транспорт теперь замкнуты — можно менять настройки самоката по BLE (с согласия, §5).

Побочно: `0x0005` на lock/unlock не реагирует (0 кадров) — его триггер не блокировка.

### 20.5 Назначение `0x0005` определено из dex — характеристика привязки, 2026-08-16
UUID строятся из int через `L_m_j/dj8->Oooooo(I)UUID`. Таблица констант — R8-класс
`L_m_j/ry0;` (= `com.xiaomi.smarthome.library.bluetooth.BluetoothConstants`): `Oooooo(65173)`
= сервис `0xFE95`, далее char'ы 1,4,5,16,19..28. `0x0005` уникален — привязан к **двум** полям
(`ry0.OooO0o0`, `ry0.OooO0oO`), у `0x0004` одно.

Кросс-dex поиск использований этих полей (androguard, все 13 dex) дал роли:
- `OooO0o0` → `BleRc4FastConnector`/`BleStandardAuthFastConnecter`: `sendCountryCode` (`IL/CN`),
  `sendBindkeyIndex`, `sendAPPWD` (OOB/app-password), `sendRestoreCommand`, `sendRetryCommand`;
- `OooO0oO` → `BleComboConnector$NotifyReceiver.onReceive` / `openComboNotify` (broadcast
  `bluetooth.character_changed`).

⇒ `0x0005` = стандартная Mijia-характеристика **combo/register** (write+notify) — используется
только при первичной привязке (страна, bindkey, OOB). У нас молчит, т.к. привязка завершена;
несёт секреты (§6), триггерить пере-привязкой не нужно. Вопрос `0x0005` закрыт.
(Валидация: `0x0004`=`ry0.OooO0Oo` → `readFirmwareVersionFromDevice`/`getBleMeshFirmwareVersion`.)

## 21. Процедура привязки (bind) — первый живой снуп, 2026-08-16

Пользователь отвязал самокат, задал PIN и заново привязал через Mi Home, сняв Android-bugreport
(внутри `FS/data/misc/bluetooth/logs/btsnoop_hci.log`). Это первый в проекте снуп СВЕЖЕЙ
привязки — все прежние были обычными логинами. Разобрано `scratchpad/bind_trace.py`
(хронологический ATT-трейс по каналам самоката с направлением).

### Последовательность (успешная, ~599–602.6 s снупа)
```
a4 → MNG(0006f2, maxPkg=6 dmtu=242)
CTRL 10800000   BIND-REQUEST (0x10)          PHONE→DEV
CTRL e1000000   device готов (0xe1)          DEV→PHONE
LOGIN(0x0016): взаимная cert-аутентификация + ECDH
   DEV→  X.509: 3082019f… (device cert) + 30820192…0201·07 (Mijia CA)
   PHONE→ токен "7b8bQxFKoKH9sWIH", ECDH-обмены (AES-CCM, не расшифровать)
CTRL 13000000   BIND-COMMIT (0x13)           PHONE→DEV
   PHONE→ X.509: 30820177…0201·01 (клиентский cert приложения) + 1496b7a2…
CTRL 11000000   BIND DONE (0x11)             DEV→PHONE
```
Через ~10 с — первый обычный login уже новым ключом: `a4 → 20000000 → ECDH(42B) → 21000000 OK`.

### Выводы
- **Bind ≠ login**: свои control-опкоды `0x10/0xe1/0x13/0x11` (у login — `0x20/0x21/0x22`).
- **Взаимная аутентификация по сертификатам**: устройство предъявляет Mijia-подписанный
  cert-chain (та же PKI, что MITFOTA-подпись прошивки), приложение — клиентский cert.
- **`ltmk` провижинится внутри cert-аутентифицированной ECDH** ⇒ каждая привязка его ротирует
  (отвязка/factory-reset — нет; проверено login'ом: после ре-привязки `0x22`).
- Из снупа `ltmk` НЕ извлечь (эфемерный ключ телефона отсутствует). Ключ восстановлен через
  облако (`askbluetoothkey` по сохранённой Mi-сессии + деривация PIN-ом, §ниже в FACTS) —
  снуп дал ПРОТОКОЛ привязки, а не сам ключ. См. FACTS.md «Процедура привязки (bind)».

## 22. MCU: физическая семантика RX-полей — анализ потребителей, 2026-08-18

Продолжение `mcu_0007.bin`. Задача (оставалась с §16.4.5): **физический смысл полей**
RX-телеметрии (батарея/скорость/…) — разбор **потребителей** адресов из карты «поле → RAM».
Метод: для каждого целевого диапазона в RAM найти функции, которые его **читают**, и по
окружающему коду (cmp/mul/shift/clamp) вывести, что значение делает.

Инструменты: `mcu_consumers.py` (статика: literal-пулы + динамика: read-taint по 678 функциям),
`mcu_disasm.py` (дизассемблер с резолвом пулов), ручная трассировка.

### 22.1. Ключевая находка — главная петля коммуникации `0x1dfd8`

Функция `0x1dfd8` — **тик-обработчик связи** (вызывается по указателю из main-loop,
не прямой `bl`). Она и есть «сердце» протокола MCU↔BLE. Последовательность вызовов:

```
0x1dfd8 (тик, ~периодически):
  bl 0x1b67c            ; флаги/статус: читает 0x30c(44.b9) при state@0x24e==6;
                        ;   перегрев ≥46°C ИЛИ высокое напр. >532 → флаг @0x318
      └─ bl 0x1d898     ; логика батареи/запаса хода/температуры (читает 0x306,0x30c,0x30e)
  u16@0x2ba++ (мс-счётчик); если ≥1000: сброс в 0; bl 0x2186c (RTC/календарь)
  расчёт battery-% → byte@0x306   (из i16@0x200017a0, маппинг [415..535]→[0..100])
  bl 0x1e9e0            ; RX-диспетчер (кадры BLE→MCU)
  bl 0x1f1cc            ; сборщик TX-запросов (63 CMD CHK 9C)
  bl 0x1f71c            ; агрегатор (24-состоянная машина, jump-table по CTX[0x10])
  bl 0x211f8            ; push статуса/телеметрии (кадры 61 …)
```

⇒ **тик ≈ 1 мс** (мс-счётчик оборачивается в 1000; секунда RTC инкрементится каждый цикл).
Это снимает вопрос «кто и когда» для всех полей — они живут в этом тике.

### 22.2. Блок C41 (кадр `0x41`) = **RTC / календарь** (доказано)

Потребитель `func_0x2186c` (вызывается из `0x1dfd8` раз в «секунду») — полноценная
календарная машина. Поля блока `0x2b0..0x2ba`:

| Адрес | Тип | Смысл | Доказательство в коде |
|---|---|---|---|
| `0x2b0` | u16 BE | **год** | инкремент только при переходе 12→1 месяц (`strh old+1`) |
| `0x2b2` (lo-ниббл) | 4 бита | **месяц** 1..12 | `cmp #0xc; strb #1` — обёртка 13→1 |
| `0x2b4` | byte | **день** месяца | лимиты по месяцам: 30-дневные {4,6,9,11}, февраль через високосный |
| `0x2b5` | bit | режим 12/24 ч | выбирает mod 12 / mod 24 для часов |
| `0x2b6` | byte | parity/blink | переключается каждый цикл (`ands #1`) |
| `0x2b7` | byte | **часы** (mod 12/24) | обёртка 12 или 24 |
| `0x2b8` | byte | **минуты** (mod 60) | `cmp #0x3c; strb #0` |
| `0x2b9` | byte | **секунды** (mod 60) | `cmp #0x3c; strb #0` |
| `0x2ba` | u16 | мс-счётчик (гейт 1000) | `ldrh; cmp #1000; strh #0` |

**Високосный год** — прямое доказательство, что это календарь: ветка февраля делит
«год» на 400 и на 100 (`bl #0x19968` = div), `year%400==0 || year%100!=0` → 29 дней.
Иерархия подтверждена: каждая старшая единица обновляется **только** при переполнении
младшей (секунда→минута→час→день→месяц→год).

Кадр `0x41` **двунаправленный**: RX-ветка кладёт поля в RAM, а `func_0x1f208` собирает
исходящий `0x41` (репак нибблов, контрольная сумма, трейлер `0x9C`). ⇒ время приходит
**телефон → BLE-чип → USART3 → RTC MCU**. Это объясняет тачеймпы в журнале поездок (§14):
у самоката нет своего генератора времени — его синхронизирует приложение.

### 22.3. Блок C44b (кадр `0x44`) = **батарея / температура**

| Адрес | Смысл | Как используется (потребитель) |
|---|---|---|
| `0x306` | **SoC, %** (0..100) | считается в `0x1dfd8`: из `i16@0x200017a0`, `≤415→0`, `≥535→100`, иначе `(v−415)·100/120`. Туда же пишет RX-ветка `0x44` |
| `0x30c` | **температура, °C** (int8) | `0x1d898`: холодная коррекция при **−5..1°C**: `val −= (2−t)·i16@0x206/8`. `0x1b67c`: **перегрев ≥46°C** → флаг `@0x318` |
| `0x30e` | u16, **бит14 = «холодный режим»** | `0x1d898`/`0x1c34c`: ветка по бит14 |
| `0x2e6`,`0x308`,`0x30a` | без локальных потребителей | только ретрансляция в телефон (§22.4) |

**Оценка запаса хода** (`0x1d898`, читает `0x306`):
```
SoC < 10%   → запас = const u16@0x206
10 ≤ SoC<20 → линейная интерполяция (20−SoC)·(u16@0x1e−full)/10
SoC ≥ 20%   → запас = u16@0x1e(r4)
результат → [r4+0x16]
```
Классическое занижение «остатка» на низком заряде. Единицы исходного `i16@0x200017a0`
(напряжение/ADC-счёт) статически не устанавливаются — маппинг `[415..535]→[0..100]%` надёжен,
абсолютная шкала — нет (нужен живой снуп для сверки).

### 22.4. Расширение TX-протокола: кадры `0x61`

`func_0x211f8` строит **исходящие** кадры с заголовком `0x61` (MCU→BLE), которых не было
в прежней картине (§16.1 знал только запросы `63 CMD CHK 9C`):

| подтип | payload | содержимое |
|---|---|---|
| `61 30 …` | 10 Б | статус/режим (флаги, i16 знаковыми парами) |
| `61 31 09 …` | 9 Б | **телеметрия = блок `0x44`**: `0x2e6`, SoC`0x306`, u16`0x308`, u16`0x30a`, temp`0x30c`, u16`0x30e` (u16 на проводе **BE**) |

Трейлер `0x9E`, контрольная сумма = сумма предыдущих байт. ⇒ MCU не только отвечает на
запросы BLE-чипа, но и **сам пушит** статус/телеметрию. Блок `0x44` доходит до телефона
именно так (подтип `0x31`).

### 22.5. Агрегатор `0x1f71c` — 24-состоянная машина

`func_0x1f71c` (6860 Б, вызывается из `0x1dfd8`) — ступенчатая машина с jump-table
(`add r3,pc; ldrh [r3,#4]; add pc,r3`), индекс = `CTX[0x10]` (0..0x17). Потребляет
RX-дескрипторы (шаг `0x96`=150 Б) + лог-буфер `0x200010b5` + системный тик. Это
**мультикадровая сборка/ретрансляция** (0x46-буфер, 0x49/0x4A). Физический смысл его
выходных не сводится к одному полю — это протокольный слой, не датчик.

### 22.6. Отрицательные результаты / пределы (честно)

- **C48/C49/C4A** (`0x354..`,`0x36a`,`0x36c` + буферы `0x1585/0x1607`): локальных
  потребителей **нет** (только RX-парсер пишет). Данные складываются в RAM, но MCU-логикой
  не читаются — вероятно, уходят только через агрегатор/ретрансляцию или вообще неиспользуемы.
- **C42/C43** (`0x2cb..0x2d8`): потребитель только агрегатор `0x1f71c`. Динамический
  read-taint дал «чтение» `0x2cc/0x2d0` через `0x085c8` — но это **GPIO-вайлер**
  (`0x0332c→0x085c8`, таблица дескрипторов из flash), вычисляемый доступ, а не прямой
  потребитель поля. Отнесено к ложному следу.
- **C45** (6×u16 `0x2da..0x2e4` + byte `0x2e7`): читает только агрегатор — физический
  смысл не установлен.
- Абсолютные единицы исходных значений (напряжение/ADC для SoC, «год» как u16 без эпохи) —
  статически не достать; нужен живой снуп USART3 или SWD-RAM.

### 22.7. Итог по семантике

| Поле | Смысл | Уверенность |
|---|---|---|
| `0x41` блок | **RTC/календарь** (год/месяц/день/час/мин/сек, високосный) | ВЫСОКАЯ (исполнение+дизасм) |
| `0x306` | **SoC %** (расчёт MCU, [415..535]→[0..100]) | ВЫСОКАЯ (маппинг), СРЕДНЯЯ (единицы v) |
| `0x30c` | **температура °C** (холод −5..1, перегрев ≥46) | СРЕДНЕ-ВЫСОКАЯ |
| `0x30e` bit14 | «холодный режим» | СРЕДНЯЯ |
| `0x308/0x30a/0x2e6` | телеметрия → телефон (без локального смысла) | СРЕДНЯЯ |
| `0x42/0x43/0x45/0x48/0x49/0x4A` | протокольные, без явного физического поля | НИЗКАЯ |

**Сдвиг границы:** до §22 физическая семантика полей = «нужен снуп». Теперь **RTC, SoC и
температура** установлены статически (по потребителям), без железа. Остаток — абсолютные
единицы исходных датчиков и протокольные блоки C42/C43/C45/C48-C4A.

## 23. MCU: данные-канал приложения (кадры 0x51..0x54) — полный маппинг подкоманд, 2026-08-18

Продолжение `mcu_0007.bin`. §22 закрыл физическую семантику полей класса A (`74 CMD …`).
Теперь — **второй канал** USART3, который до сих пор был тёмным: агрегатор `0x1f71c`
(24-состоянная машина) обрабатывает кадры с заголовками **0x51..0x54 / 0x5a / 0x64** из
RX-кольца. Оказалось: это **данные-канал приложения Mi Home** — команды «set/get» между
телефоном и MCU, ретранслируемые BLE-чипом.

Инструменты: `mcu_agg.py` (динамический трассировщик состояний), `mcu_subcmds.py`
(генератор валидных кадров + захват всех RAM-записей на подкоманду).

### 23.1. Архитектура канала

```
RX-кольцо @0x20000c05 (3 слота × 150Б, шаг 0x96)   ← фреймер кладёт сырые кадры BLE→MCU
TX-кольцо @0x200010b5 (3 слота × 150Б)             ← MCU складывает ответы, планировщик шлёт
CTX @0x20000170: [0x10]=state, [0x11]=«кадр валиден», [0x12]=off, [0x13..0x15]=вспомогательные
slot-индексы: reader=byte@0x2c8, writer=byte@0x2c7 (RX), slotB=byte@0x2c9 (TX)
```

**Форматы кадров** (выведены из состояний 0..5, подтверждено исполнением):
```
Path A (subcmd 0x10..0x1b, 0x53) — «set с payload»:
    HDR SUB LEN DATA×LEN CHK TRAILER
    CHK = Σ(frame[0..LEN+2]) & FF        (state 2: цикл суммы)
    TRAILER = 0xFF − HDR                 (state 3, frame[LEN+4])
Path B (subcmd 0x20..0x2f, 0x35, 0x36, 0x50, 0x51) — «get/контроль»:
    HDR SUB CHK TRAILER [DATA…]
    CHK = (HDR + SUB) & FF               (state 4, frame[2])
    TRAILER = 0xFF − HDR                 (state 5, frame[3])
```
Машина ходит по одному состоянию за тик: `0→1→(2→3 | 4→5)→0+dispatch`. После валидации
`CTX[0x11]=1`, и **return-path `0x202de`** диспатчит payload-хендлер по SUB.

### 23.2. Полная таблица подкоманд (исполнением, hdr=0x51)

**Set-команды (Path A):**

| SUB | Куда в RAM | Смысл |
|---|---|---|
| 0x10 | биты: hi/lo-нибблы data[0]→@0x228/@0x229, bit5/6(data[1])→@0x22b/@0x22c; +@0x22a..0x235, u16@0x27e | конфигурация режимов/флагов |
| 0x11 | u16 LE @0x23a и @0x23c = (data[1],data[2]) | числовой параметр (дублируется) |

| 0x15 | blob (data+chk+trailer) → @0x2000084b (заголовок @0x844); флаг @0x170=1 | строка/конфиг #1 |

| 0x21 | хардкод: ответ `0C 64 21 07 '0''0''0''7' …` | **версия прошивки MCU = "0007"** (совпадает с именем файла!) |

### 23.3. Что это меняет в картине (§16/§22)

1. **C42/C43/C45/C46 нашли потребителей** — их возвращает приложению get-подкоманды
   0x23/0x24/0x26/0x27. В §22 они были «только агрегатор» — теперь понятно, что
   агрегатор = данные-канал. Физический смысл блоков остаётся за BLE-чипом (что именно
   он кладёт в 0x42..0x46 — вероятно, счётчики/статистика: пробег, поездки, время).
2. **Кадры 0x48/0x49/0x4A/0x60/0x61 запрашиваются по требованию приложения**, а не только
   по периодике MCU (подкоманды 0x2c/0x2e/0x2f/0x50/0x51).
3. **Время задаётся двумя путями**: RX-кадр 0x41 (§16.4) и данные-кадр 0x51/0x14 — оба
   пишут в тот же RTC-блок @0x2b0..0x2ba.
4. **Версия прошивки MCU = "0007"** (hardcoded в ответе 0x21) — совпадает с именем файла
   `mcu_0007.bin`. CRC-самопроверка (0x2b) покрывает flash-регионы 0x3000..0x3D5F и
   0x10800..0x1081A.
5. **TX-кольцо @0x200010b5** — это не «лог», а очередь исходящих кадров MCU→BLE
   (формат `LEN HDR SUB DLEN DATA CHK TRAILER`, HDR=0x64/0x65, TRAILER=0xFF−HDR).
   Планировщик @0x20000a43 шлёт их по USART3.

### 23.4. Остатки / пределы (честно)

- **u16 @0x32e/0x330** (get 0x36): писатель не найден ни статически, ни динамическим
  taint'ом по 678 функциям — вероятно, вычисляется из данных 0x49/0x4A в рантайме
  (вычисляемая база) или пишется только в специфическом состоянии. Нужен живой снуп.
- **Содержимое blob-ов** (конфиги #1..#3, @0x84b/0x85d/0x871): в эмуляции RAM нулевая,
  физический смысл (SN? алиас? калибровка?) требует реальных значений из снупа.
- **Таблицы @0x200016aa** (построение по 0x1a): выглядят как интерполяционные
  (напряжения/токи); точный смысл — по живой калибровке.
- Заголовки 0x52/0x53/0x54 и семья 0x5a (подтипы 0xa0..0xa6/0xae) не проверялись отдельно
  (диспетчер общий; 0x51 покрыт полностью).

### 23.5. Итог

Данные-канал приложения **разобран на 100% по подкомандам** (все 32: 12 set + 20 get/req)
исполнением реального кода. Канал = «руки и глаза» Mi Home на MCU: установка времени,
версия прошивки, CRC-самопроверка, get телеметрии BLE-чипа (0x42..0x46), on-demand
запросы (0x48/0x49/0x4A/0x60/0x61). Сдвиг границы: «агрегатор = чёрный ящик» →
полная таблица подкоманд. Остаток — физический смысл payload'ов, которые генерирует
BLE-чип (его прошивка у нас есть: `ble_2.7.0_0015.bin` — следующий кандидат).

## 24. MCU: событийный канал 0x5a — сессионный протокол (мастер-значение + fan-out), 2026-08-18

Продолжение `mcu_0007.bin` (очередь AGENTS.md, задача #1). Третья семья кадров данных-канала
(§23): заголовок **0x5a**, формат `5A 51 0A SUBTYPE DATA…` (LEN=10 фиксированный; проверки
frame[1]==0x51, frame[2]==0x0a идут в состояниях 20→21→22). Все подтипы подтверждены
исполнением (`mcu_agg.py` + целевые прогоны с поднятыми флагами).

### 24.1. Сессионные флаги

| Адрес | Устанавливает | Сбрасывает | Роль |
|---|---|---|---|
| `byte@0x339` | **0xa0** (в стартовом окне) | **0xa6** | флаг «сессия активна» — гейт для 0xa1/0xa2/0xa3/0xa4 |
| `byte@0x33a` | **0xa2** (по гейту @0x339) | **0xa5** | подфлаг сессии |

Гейт реализован в dispatch'е: `ldrb r3, [0x339]` между проверками подтипов — в хендлерах
`cmp r3, #1`. (Важная деталь дизассемблера: interleaved-загрузки в цепочке cmp/beq легко
пропустить — капстан без резолва пулов их «съедает».)

**0xa0 имеет стартовое окно**: 64-битное сравнение системного тика с константой **79936**
(`subs r0,[sp]; sbcs r1,#0` против слова из пула) — действие только при tick < 79936
(~80 с при тике 1 мс, §22.1). Т.е. «начало сессии» принимается лишь в первые ~80 с работы.

### 24.2. Таблица подтипов (исполнением)

| SUB | Гейт | Действие |
|---|---|---|
| **0xa0** | tick < 79936 | `@0x339 = 1` — **начало сессии** + ACK |
| **0xa2** | @0x339==1 | `@0x33a = 1` + ACK |
| **0xa5** | — | `@0x33a = 0` + ACK |
| **0xa6** | — | `@0x339 = 0` — **конец сессии** + ACK |
| **0xa1** | @0x339==1 | если `i16@0x272 ∈ [1876, 2275]`: `u16@0x1ec = raw×41/48`, `u16@0x266 = raw×9/8` (перекалибровка ADC-канала) + ACK |
| **0xa3** | @0x339==1 | frame[4]==0: **мастер `u16@0x1e8` += 6**; иначе ±δ «круг» (см. §24.3); **fan-out в 18 полей** + ACK |
| **0xa4** | @0x339==1 | frame[4]==0: **мастер -= 6**; иначе ∓δ; fan-out + ACK |
| **0xae** | — | ответ-строка устройства: `10 57 5A 4B "PA68407 V0007"` (HDR=**0x57**, ASCII: `P A 6 8 4 0 7 ␣ V 0 0 0 7`) |

**ACK-формат** (общий): `0A 5A 61 0A SUBTYPE 00 00 00 00 XORCHK A5` — длина 10, HDR=0x5a,
SUB=0x61, DLEN=0x0a, эхо подтипа, 4 нуля, **XOR** байтов [1..8] (не сумма!), трейлер
`0xFF−0x5a = 0xA5`.

### 24.3. Мастер-значение и fan-out (проверено численно)

Мастер `V = u16@0x200001e8`. Обновление (0xa3/0xa4, frame[4]≠0): два шага
`V ±= V·frame[4]/256` — «круг»: при V < 217 второй шаг пропускается (условие
`(V−0xd9)` с переносом), при V ≥ 217 шаги почти компенсируют друг друга. Реальные
шаги — **±6** на событие с frame[4]==0. Т.е. V — ступенчатый счётчик/оценка,
гонилая событиями BLE-чипа.

После каждого обновления (и при frame[4]==0) — **fan-out в 18 производных полей**
(все значения сверены прогоном: V=100, frame[4]=5):

| Адрес | Формула | Коэфф | | Адрес | Формула | Коэфф |
|---|---|---|---|---|---|---|
| @0x1e8 | V (мастер) | 1.0 | | @0x202 | 12·(V/10)+(V/10)/2 | 1.25 |
| @0x1f2 | V | 1.0 | | @0x204 | 12·(V/10) | 1.2 |
| @0x1f6 | 18·V/10 | 1.8 | | @0x206 | V | 1.0 |
| @0x1fe | 19·V/10 | 1.9 | | @0x208 | 8·(V/10) | 0.8 |
| @0x1f4 | −(7·V/10)/10 (signed) | −0.07 | | @0x20a | 7·(V/10) | 0.7 |
| @0x1f8 | V/10 (sxth) | 0.1 | | @0x20c | 3·(V/10) | 0.5 |
| @0x1fa | 30·(V/10) | 3.0 | | @0x20e | 2·(V/10) | 0.2 |
| @0x1fc | 25·(V/10) | 2.5 | | @0x210 | V/200 | 0.005 |
| @0x200 | 15·(V/10) | 1.5 | | @0x212/0x214/0x216 | (V/10)/4, /2, 7V/100 | — |

**Связь с §22:** блок @0x1e8..0x216 — тот же, что читает оценка запаса хода `0x1d898`
(u16@0x206, u16@0x1e) и статус-флаги `0x1b67c`. Значит мастер-значение (скорость/обороты?)
непосредственно питает расчёт запаса хода. Единицы — по живому снупу.

### 24.4. Интерпретация и пределы

Канал 0x5a = **сессионный протокол управления/телеметрии «движение»**: BLE-чип открывает
сессию (0xa0, только в первые ~80 с), шлёт ступенчатые события ±6 (0xa3/0xa4) и ADC-
калибровки (0xa1), закрывает сессию (0xa6). MCU ведёт мастер-оценку и раскладывает её
по производным полям, которые используются в логике хода/статуса. 0xae — идентификатор
устройства «PA68407 V0007» (вероятно, внутренний код продукта + версия; совпадение с
MCU-"0007" (§23) не случайно).

Честные остатки: физическая единица мастера V и i16@0x272 (окно [1876..2275]) — статически
не установить; ±δ-«круги» для frame[4]≠0 выглядят как почти no-op (возможно, намеренное
сглаживание или рудимент). Кто именно генерирует 0x5a-кадры (BLE-чип по своим датчикам
или ретрансляция команд приложения) — вопрос к прошивке BLE (`ble_2.7.0_0015.bin`).

## 25. MCU: ADC и источник батарейного значения — полный контур «сенсор → SoC %», 2026-08-18

Закрываем две задачи §22/§24: (а) кто пишет сырые каналы скользящих средних
`u16@0x278/@0x284/@0x29c`, (б) откуда берётся источник батарейного % `i16@0x200017a0`.
Оба ответа — в одном прерывании: **ADC ISR `0x1a31c`** (+ последовательный таск-драйвер).

### 25.1. Железо

- ADC-периферия: **ADC1 @0x40012400, ADC2 @+0x40 (0x40012440)**, общий блок @0x40012c40
  (раскладка регистров расширенная относительно классической STM32F1: данные на
  `+0x28/+0x2C/+0x30/+0x34` у ADC2; точная Si не идентифицирована).
- Кастомный блок **0x40023c00** с протоколом «команда → результат»:
  `CMD@+0x00`, `DATA@+0x04`, `RESULT@+0x08`, `CTRL@+0x10` (бит0 = старт). Используется
  минимум в двух местах: ADC ISR state-5 и функция `0x1bb1c`.
- **Бфер сэмплов @0x2000168a..0x20001693** (5×u16) — заполняется **DMA** (CPU-записей в
  него нет ни в одной функции; init-код `0x1c1xx` кладёт адреса бфера в регистры
  периферии: `str r1(=0x20001692), [reg+4]` + опрос).

### 25.2. ADC ISR `0x1a31c` (машина состояний, state-byte @0x248)

Вход: `ADC1->SR → запись в +0x14` (сброс EOC). Далее:
- `byte@0x246 == 1` → `bl 0x1a894` и выход;
- `byte@0x3c0 == 1` → сброс флага, `bl 0x1e298`.

Состояния (r5 = &бфер@0x168a, r4 = &struct@0x30):

| state | Действие |
|---|---|
| 0 | `u16@0x24a = buf[1]`; обнуление acc u32@0x250 и счётчика u16@[r4+6] |
| 1 | `u32@0x250 += ADC2[+0x34]`; `u16@0x24a = buf[1]`; счётчик++; при ==**1024**: **`u16@[0x110+0x3c] = acc/1024`** (среднее 1024 сэмплов), state=2 |
| 3 | накопление `ADC2[+0x28/+0x2C/+0x30]` ×1024 → **`u16@[0x110+0x18/0x1A/0x1C] = acc/1024`**; сброс бита5 в `common+0x14`; state=4 |
| 5 | полный снимок (см. 25.3) |
| 2, 4 | idle (сразу выход) |

Общий хвост каждого вызова: инкремент тик-счётчиков — 64-битные `@0x222/@0x378/@0x360`,
u16 `@0x2bc/@0x2c4/@0x370` (кап **16000**), u16 `@0x27e/@0x23e` (кап **256000**); затем
`bl 0x1d3d0; bl 0x1f600; bl 0x216e4; bl 0x1a5c4` (SWSTART ADC). **Вывод: ADC ISR —
сердцебиение системы** (источник тиков, на которые опираются гейты §22, напр. «1600 тиков»).

### 25.3. State-5: полный снимок + батарейный протокол

```
bl 0x1bf24 → byte@0x26b
if i16@0x24c > 2382 (0x94e): bl 0x1a688        ; счётчик событий (кап 10000) + режим-машина
byte@0x268 = (byte@0x26b ? bl 0x23374 : 0)
bl 0x1bb1c(r0=&struct@0x154)                    ; батарейный замер №2 (см. ниже)
i16@0x26c = i16(ADC2[+0x34] − u16@[0x110+0x3c]) ; дельта к среднему из state-1
IIR: acc u32@0x3c += delta; i16@0x26e = (acc−old)/8
i16@0x270 = buf[2]
IIR: acc u32@0x274 += buf[2] − old; *** i16@0x272 = (acc−old)/256 ***
--- батарейный замер №1 (источник SoC!) ---
CTRL(0x40023c00+0x10) |= 1                      ; старт
CMD(+0)  = 410 × i16@0x272                      ; отфильтрованный ADC
DATA(+4) = u16@0x1ec                            ; калибровочный коэффициент (0x5a/0xa1!)
*** i16@0x200017a0 = RESULT(+8) ***             ; <- источник батарейного % из §22
u16@0x24a = buf[1];  u16@0x278 = buf[3]         ; сырые каналы для §22
bl 0x1c040(u16@0x24c)
u16@0x284 = buf[4];  u16@0x29c = buf[0]         ; сырые каналы для §22
bl 0x1a938                                                 ; батарейные пороги (§22)
```

**Ключевые находки:**
1. **Сырые каналы скользящих средних §22** — это копии DMA-бфера, сделанные здесь:
   `u16@0x29c = buf[0] @0x168a`, `u16@0x278 = buf[3] @0x1690`, `u16@0x284 = buf[4] @0x1692`.
2. **`i16@0x272`** (окно [1876..2275] из 0x5a/0xa1, §24) — IIR-фильтр (÷256) от `buf[2]`.
3. **Источник SoC `i16@0x200017a0`** — результат кастомного блока 0x40023c00, которому MCU
   подаёт `(410 × IIR_avg(buf[2]), u16@0x1ec)`. Т.е. «батарейное значение» — не прямой ADC,
   а вычисление аппаратного блока по отфильтрованному сэмплу и калибровке, которую шлёт
   BLE-чип (0x5a/0xa1: `u16@0x1ec = raw×41/48`, §24). Контур замкнут:
   **калибровка из BLE → замер → i16@0x17a0 → [415..535]→[0..100]% (u16@0x306) → запас хода**.

### 25.4. `0x1bb1c` — батарейный замер №2 (struct @0x154)

Вызывается из state-5 с `r0=&0x20000154`. Логика:
- счётчик `u16@struct+0xc` (кап 2000) → флаг `byte@0x100`;
- второй счётчик `u16@[0xac+0x32]` (кап 5088) с авто-сбросом;
- при смене режима (`struct[0x14] != byte@0x268`): счётчик смен `u16@[0xac+0x34]++`,
  табличный lookup `table@0xa63a[mode]`, флаги `struct[0xa]`/`byte@0x380`;
- **DATA = сумма 6 i16 из таблицы @0xac+0x44, индекс = старый mode×2**;
- протокол: `CMD=0xffff`, `DATA=sum`, старт → **`u16@struct+8 (@0x15c) = RESULT`**.

### 25.5. Таск-драйвер (последовательность замера) ~`0x1cbf0`

RTOS-таск, выходящий на каждом тике через `strb r0,[r5]` (r5=&0x248). Шаги:
1. **гейт: `i16@0x24c > 2382`** — иначе замер не запускается вообще;
2. state=1 (накопление ADC2[+0x34] ×1024) → ожидание;
3. state=3 (накопление трёх регистров ×1024) → ожидание;
4. state=0 (сброс);
5. опрос готовности (`bl 0x221e6` в цикле) → **state=5** (полный снимок + оба замера).

**`i16@0x24c`** — канал-триггер — сам является фильтром: в начале `0x1b67c`
(статус-флаги, §22) вычисляется `i16@0x24c = IIR(÷32)(i16@0x24a)`
(acc u32@0x430), а `u16@0x24a` — копия `buf[1]` из ADC ISR. Цепочка триггера:
**DMA buf[1] @0x168c → u16@0x24a (ISR) → i16@0x24c (IIR ÷32, в 0x1b67c) → порог 2382**.

### 25.6. Итоговая схема контура

```
ADC1/ADC2 (DMA, непрерывно)
   └→ бфер u16[5] @0x2000168a
        ├ buf[0] → u16@0x29c ─┐
        ├ buf[1] → u16@0x24a ─┼→ IIR÷32 → i16@0x24c ─(>2382)→ запуск последовательности
        ├ buf[2] → i16@0x272 (IIR÷256) ─×410─┐
        ├ buf[3] → u16@0x278 ─┤               ├→ блок 0x40023c00 → i16@0x200017a0
        └ buf[4] → u16@0x284 ─┘   u16@0x1ec ←──┘   (0x5a/0xa1 из BLE: raw×41/48)
                                        └→ [415..535]→[0..100]% → u16@0x306 (SoC) → 0x1d898 (ход)
```

### 25.7. Честные остатки

- Физический смысл пяти DMA-каналов (buf[0..4]) и канала-триггера — только по живому снупу.
- Природа блока 0x40023c00 (BMS-мост / специализированный фронтенд) — статически не
  определяется; единицы RESULT тоже.
- Что именно стоит за `bl 0x1bf24` (byte@0x26b) и `0x1a894`/`0x1e298` (альтернативные режимы).

## 26. MCU: структура образа, загрузка (data-driven) и финальный вердикт по u16@0x32e/0x330, 2026-08-18

Задача «писатель get 0x36» (§23.4) потребовала пройти весь образ — и привела к
архитектурному открытию: **MCU загружается data-driven, точка входа в RAM**.

### 26.1. Структура файла `mcu_0007.bin` (0x24D39 Б)

Файл — **упакованный образ прошивки**, а не сырая флеш с векторной таблицей в нуле:

| Смещение | Содержимое |
|---|---|
| 0x000 | заголовок: слово `0x00400200`, ASCII «1080», версия **«000700010001»** |
| 0x800 | магия **«DEPRD5C»** + `01 88 00 b9` |
| 0x810..0xFFF | padding 0xFF |
| **0x1000** | **векторная таблица Cortex-M**: SP=**0x20004E40**, reset=0x0800315D, NMI/HardFault/MemMgmt/Bus/Usage, затем IRQ-хендлеры |
| 0x1200.. | код (регионы A..J) + данные |

**SP=0x20004E40 ⇒ у MCU ~20 КБ SRAM** (все известные RAM-адресы < 0x1800 — согласуется).
IRQ-хендлеры из таблицы: `0x128FC` (UART RX-машина), `0x71D6`, `0x13CAC` (DMA-копирование
→ @0x309d..), `0xB714/0xB6DC` (стейт-машины, флаги @0xefa/@0xef9), `0x14FD0/0x14FD8`
(счётчики @0xc90/@0xc9b/@0xfd3), дефолт `0x3176`.

### 26.2. Загрузка: точка входа из RAM (инжектится бутером)

Reset-хендлер `0x315C`:
```
str 0, [sp]          ; [SP]=0
mov r0, sp
bl  0xcd0c           ; init периферии (блок @0x40002824: рег. -0x1c/-0x14, задержка)
pop {r1, r2, r3, pc} ; *** pc = RAM[SP+12] = 0x20004E4C ***
```
Т.е. **адрес C-main/задачи читается из RAM @0x20004e4c**, который заранее заполняет
сторона, запускающая MCU (BLE-чип). Подтверждение: топ-задачи `0x1dfd8` (main tick),
`0x1c838` (калибровка/секвенсор §25), `0x21a08` (NVRAM-save), `0x1a31c` (ADC ISR)
**не имеют ни одного статического ссылающегося** — ни `bl`, ни pool-указателей.
Они вызываются по таблице указателей в RAM.

### 26.3. NVRAM (flash @0x0801F400..0x0801FFFF) — карта

| Флеш | → RAM | Что |
|---|---|---|
| @0xF400 u16LE | u16@0x1e8 | **мастер-значение** (fan-out §24) |
| @0xF404 u16LE | u16@0x1ec | **калибровка батарейного замера** (DATA блока 0x40023c00, §25) |
| @0xF600..+0xF 4×u16 | u16@[0x110+0x18/0x1A/0x1C/0x3C] | калибровки (проверка: v−1549 < 999) |
| @0xF800+i·4 (i=0..7) | blob-байты 0..7 @0x844 | конфиг #1 (slots по 4Б) |
| @0xF81C+i·4 (i=0..0x12) | blob-байты 7..25 @0x84B | конфиг #1 продолжение |
| @0xF864+i·4 (i=0..0x14) | blob-байты 0x19..0x2D @0x844 | конфиг #3 (@0x871..) |
| @0xF8B4 | byte@0x242 (если byte@0x241==1) | флаг |
| @0xF8B8+i·4 (i=0..0xF) | blob-байты @0x871+0x2D.. | конфиг #3 продолжение |

Сохраняет таск `0x21a08` (гейт: byte@0x170==1 + бит31 `common+0x14`); синхронизация
мастер/калибровка с тенями u16@0x1ea/@0x1ee. Загрузка в обратную сторону — в
`0x1c838` (§25: @0xF400/+4 → @0x1e8/@0x1ec; fan-out 18 полей; NVRAM-save при
калибровке+402).

### 26.4. Финальный вердикт: u16@0x32e/0x330 (get 0x36)

Исчерпывающий поиск писателя:
- **Статика**: pool-слова (прямые и соседние базы 0x320..0x348), линейный трек
  регистров по 527 функциям, паттерн «одометр» (ldrh→+1→strh) — ничего.
- **Динамика**: свип всех 527 функций (включая ранее не сканированные регионы
  `0x17A00..0x18E00` — 98% код, `0x12400..0x12800`, `0x10200..0x10400`) × 12 сидами
  (ADC states, таск-стейты, flash-калибровки) с write-хуком на 0x32C..0x334 —
  единственная запись в окрестности: `byte@0x32d = 1` @pc=0x1c998 (флаг калибровки).
- RX-кадры 0x40..0x4B (§16.4), подкоманды данных-канала (§23), ADC/батарея (§25) —
  не пишут туда.

**Вывод:** в этом образе CPU-писателя нет. Значения либо загружаются на старте по
инжектированной RAM-таблице задач (NVRAM-restore «счётчиков» — блок, которого нет в
нашем файле), либо пишутся DMA/аппаратно. Для закрытия нужен живой забор:
SWD-RAM чтение @0x32e/0x330 на устройстве (+ динамика во времени) или USART3-снуп.

### 26.5. Инструменты

`mcu_writers.py` — динамический свип писателей (write-хук на произвольный RAM-диапазон,
произвольные сиды, расширенные кодовые регионы).

## 27. MCU: таблицы @0x200016aa — расшифрованный конфиг #3 (S-box шифр) + ключи шифрования, 2026-08-18

Закрываем задачу «смысл интерполяции таблиц @0x200016aa» (§23, subcmd 0x1a).
Оказалось: это **не интерполяция, а зашифрованный конфиг из приложения**, который MCU
расшифровывает в рабочую таблицу — и использует её же как ключевой материал.

### 27.1. Цепочка (subcmd 0x1a)

```
Mi Home → BLE → RX-кольцо: кадр `51 1A LEN DATA… CHK TRAILER` (Path A, §23)
  → хендлер ~0x20972:
      if byte@0x338==1 (флаг «флеш пуста», 0x1c838) или byte@0x241==1 (subcmd 0x18):
          копирование 16 байт frame[3..18] → @0x20000864..0x873
              (заголовок @0x86a, данные @0x871..)
          при ИЗМЕНЕНИИ байта: *** bl 0x1a628(r0=&0x871) — ДЕШИФРОВКА ***
          CTX[0]=1 → ACK `65 1A 4F 4B`
      else: только ACK
```

### 27.2. Шифр (0x1bfa0, вызов через трамплин 0x1a628)

`0x1a628`: `mov r1, r0(=src); ldr r0 = &0x16aa; bl 0x1a5f2 → bl 0x1bfa0(&table, src)`.
Алгоритм (48 байт: 16-байтный хедер + 32 байта = 8 блоков по 4):
1. Первые 16 байт копируются как есть;
2. Каждый 4-байтовый блок прогоняется через **два S-box'а** — таблицы в flash
   **@0x0000a907** и **@0x0000ab07** (по 256 Б) — с перестановкой байтов
   (порядок 3,1,2,0) и XOR-комбинацией с бегущим состоянием [sp..sp+3];
3. Итог — рабочая таблица **u8[48] @0x200016aa** (хедер 16Б + payload 32Б).

Обратное направление — **шифратор** через трамплин `0x21c64`:
`mov r1, r0; ldr r0 = &0x16aa; bl 0x1a5e4 → bl 0x1a7ac(plaintext, &table)` —
**10-раундовый блочный шифр** (4×4 XOR-сетка с таблицей @0xa907, ротации,
`cmp r5,#0xa`). Т.е. таблица @0x16aa служит **ключевым материалом** для шифрования
(кто именно шифруется — вызов идёт по RAM-указателю, статически не резолвится;
см. §26.2 data-driven загрузку).

### 27.3. Персистентность

NVRAM-save таск `0x21a08` (§26.3): байты @0x871..0x880 → flash @0x0801F8B8 (slots по 4Б).
Загрузка при старте — в `0x1c838`/NVRAM-restore (по RAM-таблице задач, §26.2).

### 27.4. Интерпретация и честные остатки

- Конфиг #3 — **калибровочный блок из приложения** (Mi Home шлёт его при привязке/
  калибровке; в §24 окно i16@0x272 [1876..2275] и u16@0x1ec=raw×41/48 — та же тема
  батарейной калибровки). Называть поля «интерполяционными таблицами» некорректно:
  это зашифрованный blob, а не открытые кривые.
- Физический смысл 32 байт payload — по живому снупу (захват кадра 0x1a из Mi Home +
  дамп @0x16aa после расшифровки) либо разбором APK-генератора этого конфига.
- Оба трамплина (0x1a628/0x21c64) не имеют статических `bl`-вызывающих — вызываются
  по RAM-указателям (§26.2).

### 27.5. Инструменты

Расшифровка подтверждена исполнением (mcu_subcmds.py, §23): валидный кадр 0x1a даёт
записи в @0x16aa..; битые CHK — нет.

## 28. MCU: два UART'а и TX-планировщики — как кадры уходят в BLE, 2026-08-18

Закрываем задачу «планировщик TX @0x20000a43» (§23.5-очередь). Итог: у MCU **два
UART'а** на сторону BLE, и два независимых byte-by-byte отправителя.

### 28.1. Физический уровень

| UART | База | DR | SR (TC=бит16) | Направление |
|---|---|---|---|---|
| **USART3** | 0x40004800 | +4 (0x40004804) | +0x28 | RX телеметрия (`74 …`), данные-канал RX (`51-54/5a/64`) + **TX запросы `63 CMD CHK 9C` и push `61 30/31 … CHK 9E`** |
| **UART4** | 0x40004C00 | +4 (0x40004C04) | +0x28 | **TX ответов данных-канала** (кольцо @0x10b5) |

Байт-райтеры: `0x1f1c0` = `str r0,[0x40004804]` (USART3), `0x211ec` =
`str r0,[0x40004C04]` (UART4). Инициализация USART3 — `0x1f6b4` (GPIO-блок
@0x48000800, делитель 0x4B00, HAL_UART_Transmit `0x23188`, enable-биты в +0x2C).

### 28.2. Планировщик описателя @0xa43 — `0x1f600` (USART3)

Вызывается из хвоста ADC ISR (каждый тик). Логика:
```
if byte@0x2c2 == byte@0x2c1: return                 ; нет нового слота
if u64(now@0x1e0) − u64(CTX+0x28/0x2C) < 432: return ; период между кадрами
slot = byte@0x2c2; len = desc[slot*0x96 + 0]        ; описатель @0xa43, шаг 0x96
CTX+0xA = len; сброс CTX+0xB (индекс байта) при обходе
u64(CTX+0x30/0x34) = 11/0                            ; межбайтовый таймер
byte@0x2c2++ (mod 4); запечатлеть now в CTX+0x28/0x2C
; каждый тик:
if u64(CTX+0x30/0x34) < 8: return                    ; пауза 8 тиков между байтами
if USART3 SR бит16 (TC) не готов: return
bl 0x1f1c0(desc[slot*0x96 + CTX+0xB])                ; байт в USART3 DR
CTX+0xB++; u64 таймер = 0
```
Т.е. запросы `63 CMD CHK 9C` (сборщик `0x1f1cc`) и push `61 …` (`0x211f8`) уходят по
**USART3**, не более одного байта за тик, кадр не чаще раза в 432 тика.

### 28.3. Отправитель TX-кольца @0x10b5 — `0x216e4` (UART4)

Тоже из хвоста ADC ISR:
```
if byte@0x2ca (reader) == byte@0x2c9 (writer): return   ; кольцо пусто
slot = byte@0x2ca; frame = @0x10b5 + slot*0x96; len = frame[0]
CTX+0x18 = len; CTX+0x19 = индекс байта (сброс при обходе)
гейт по mode = byte@0x358:
    0: u64(now@0x1e0) − u64(CTX+0x40/0x44) >= 432      ; период 432 тика
    1: u64-счётчик @0x360 >= 0x50 (80)                 ; после отправки счётчик = 0
    иначе: не шлём
if UART4 SR бит16 (TC) не готов: return
bl 0x211ec(frame[CTX+0x19])                             ; байт в UART4 DR
CTX+0x19++; при завершении кадра: byte@0x2ca++ (mod 8)
```
Т.е. **ответы приложения** (`LEN 64/65 SUB DLEN DATA CHK TRAILER`, §23) уходят по
**UART4**, а не по USART3.

### 28.4. Симметрия каналов (итог по протоколу)

```
BLE → MCU (USART3 RX, фреймер 0x1e480, кольцо @0xc05):
    74 …          — телеметрия C41..C4A/C60/C61
    51-54/5a/64   — данные-канал приложения (агрегатор 0x1f71c)
MCU → BLE (USART3 TX, планировщик 0x1f600, описатель @0xa43):
    63 CMD CHK 9C — запрос телеметрии
    61 30/31 … 9E — push статус/телеметрии
MCU → BLE (UART4 TX, отправитель 0x216e4, кольцо @0x10b5):
    LEN 64/65 SUB DLEN DATA CHK TRAILER — ответы данных-канала
```

### 28.5. Остатки

- Кто пишет `byte@0x358` (mode TX-кольца) и почему два режима (432 vs 80 тиков) —
  читается в `0x211f8`; писатель — по RAM/задачам (§26.2).
- Физически UART4 — вторая жила связи с BLE-чипом (у RTL8762C несколько UART);
  подтверждение — по разводке/снупу.

## 29. MCU: заголовки 0x51..0x54 — идентичны, это «канал/версия» без поведения, 2026-08-18

Закрываем задачу «проверить 0x52/0x53/0x54 отдельно от 0x51». Метод: mcu_subcmds.py
прогнан для всех 4 заголовков × все 32 подкоманды (Path A + Path B), сравнены
состояния автомата, RAM-записи и ответы.

**Результат: 0 различий в поведении.** Все состояния, все записи в RAM и все
ответные кадры совпадают побайтово для 0x51/0x52/0x53/0x54. Единственные отличия —
сами сохранённые CHK/TRAILER байты в blob-заголовках (@0x853/0x854, @0x865/0x866,
@0x879/0x87a), т.е. MCU просто копирует байты кадра (HDR-зависимые CHK и
TRAILER=0xFF−HDR) в хранилище — ожидаемо.

Вывод: **HDR 0x51..0x54 — логический идентификатор канала/версии**, который MCU
игнорирует (агрегатор 0x1f71c принимает все четыре одинаково). Различия, если они
есть, живут на стороне BLE-чипа/приложения (маршрутизация между «каналами»).

Артефакт: research_bin/hdr_cmp.txt (полный лог 4×32 запусков).
