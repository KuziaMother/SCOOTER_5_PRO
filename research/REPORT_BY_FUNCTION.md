## Глава 1. Образы и FOTA

### 1.1 BLE-образ `ble_2.7.0_0015.bin` (153 890 Б)

Два 1 КБ заголовка FOTA (не один — см. §62), payload'ы, сертификатная цепочка:

| Смещение | Содержимое | § |
|---|---|---|
| 0x0000..0x0400 | **HDR#1** (boot/ctrl): enc=1, xip=0, enc_key_select=1 (SCEK+RTKCONST), exe_base=RAM 0x203800 | §62 |
| 0x0400..0x9ff4 | payload HDR#1 — **PLAINTEXT** bootloader/OTA (~39 КБ) | §63 |
| 0xA000..0xA400 | **HDR#2** (main app): xip=1, enc=0 (legacy), payload_len=111496 | §62 |
| 0xA400..~0x2542d | payload HDR#2 — **CIPHERTEXT** main-app (~110 КБ, SCEK/XIP) | §62 |
| ~0x2542d..end | cert chain + ECDSA-подпись | §30.2/§44 |

Оба заголовка: ic_type=5, uuid `6d67def13e33e811b1024d2df40cde01`. Флаги enc/xip — LEGACY;
реальная шифровка at-rest = **hardware XIP-decrypt ключом OTP/eFuse** (§62, §43.3).

### 1.2 MCU-образ `mcu_0007.bin` (150 841 Б / 0x24D39)

Упакованный образ (не сырая флеш), **Cortex-M4F** (GD32/STM32F1-class), ~20 КБ SRAM,
data-driven загрузка (§26):

| Смещение | Содержимое | § |
|---|---|---|
| 0x000 | заголовок: `0x00400200`, «1080», версия «000700010001» | §26.1 |
| 0x800 | магия **«DEPRD5C»** | §26.1 |
| **0x1000** | **векторная таблица**: SP=0x20004E40, reset=0x315C | §26.1/§54 |
| 0x1200..0x23680 | код (регионы A..J) + данные | §26.1 |
| 0x236B8..end | трейлер: build-метаданные, X.509 Mijia, LUT | §38.5 |

**Загрузка:** reset `0x315C` читает C-main из RAM `@0x20004e4c` (инжектится BLE-чипом);
топ-задачи (`0x1dfd8`, `0x1c838`, `0x21a08`, `0x1a31c`) вызываются по RAM-таблице, без
статических ссылок (§26.2).

### 1.3 FOTA-пакет (общий формат MCU и BLE)

| Элемент | Описание | § |
|---|---|---|
| Заголовок(и) | 1 КБ (BLE — два, §62); поля: ic_type, uuid, enc/xip flags, exe_base, payload_len | §42.1/§62 |
| Payload | код (PLAIN или CIPHER по флагу) | §42.1 |
| Cert chain | 2 PEM-сертификата Mijia (одинаковы в обоих образах) | §30.2/§44 |
| ECDSA-подпись | DER 70 Б; верифицируется до Mijia Root CA (в APK Mi Home) | §42/§44 |

**Вердикт (§30.7):** хвост MCU — данные для **внешнего верификатора** (телефон/BLE-чип
проверяет подпись и AES-расшифровывает при OTA), не исполняемый код MCU. Формат
подписываемого манифеста статически не восстанавливается.

### 1.4 Сертификаты и подпись

- **Mijia Root CA** найден в APK Mi Home (§44.1); полная цепочка верифицируется до trust
  anchor (§44.2). Публичные ключи cert0/cert1 идентичны в обоих образах (§30.7).
- Подпись MCU-образа не проходит проверку ни одним из ключей по стандартным диапазонам —
  композитный манифест Mi-OTA, возможен отдельный leaf-ключ (§30.7).

## Глава 2. BLE / RTL8762C

### 2.1 Flash layout и security

| Факт | § |
|---|---|
| Flash base: SDK `0x00800000`, у Dreame **`0x01800000`** (тот же layout) | §6.11 |
| Официальные User Guides: Flash / Memory / MP Tool / Security Mechanism | §19/§19.1/§19.2 |
| **ДВА ключа** (MP Tool vs runtime): вопрос почти закрыт по Security Mechanism Guide | §19.1/§19.2 |
| SWD-доступ: TAPID 0x2ba01477, flash bank 0x00800000 | §6.11/§17 |

### 2.2 SCEK / XIP-модель (почему main-app не читается статически)

- **SCEK** = per-chip ключ в eFuse/OTP; расшифровка main-app — только hardware XIP-decrypt
  на живом чипе (§62, §43.3).
- Флаги `enc`/`xip` в заголовке — LEGACY; реальная шифровка at-rest не зависит от них (§62).
- **Вердикт A2 (§43.4):** дефолтного OTA AES-ключа Realtek не существует → main-app
  (110 КБ) без SWD/XIP недоступен.

### 2.3 PLAIN-код (bootloader + flash/OTA) — что разобрано

PLAIN-регионы: `0x400..0x3000` (bootloader/DFU) + `0x5C00..0x9FF4` (flash/OTA-драйвер) —
170 функций, ~18.6% файла (§46.2). Ключевое:

| Функция/объект | Роль | § |
|---|---|---|
| CTR length-gate `0x23f0` | валидные длины {5} ∪ [0x12c..0x12e] (control 5B + data 300-302B) | §64 |
| DFU event dispatcher `0x245a` | type==4/[r3]==1 или type==2 → timer; type==4/[r3]==3 → bl 0x2e2e | §64 |
| Flash-драйвер (кластер 0x6xxx) | SPIC-доступ: `0x639a`→SPIC+0x11c, `0x63a4`=config | §63/§64 |
| SPIC register map | dr[32]@0x60, rd_fast_single@0xE0, wr_single@0xF4, wr_enable@0x108, auto_length@0x11C | §64 |
| Runtime-struct каркас | главная `0x20016400` (10 ссылок), буферы `0x200e4xxx` | §65.1 |

**Потолок статической декомпиляции BLE (§65):** глубинная логика (CTR/DFU/flash r/w/e) —
trampoline в RAM (0x2xxxxxx/0x4xxxxxx), тела не в образе; SPIC-функции не запускаются без
точного рантайм-состояния. PLAIN-разобрано 1.9% (в основном тривиальные setter/init + гейты).

### 2.4 CTR / DFU-протокол

Валидация кадров: length-gate `0x23f0` (гейт по длине) + полная валидация через callees в
RAM (trampoline). DFU-события диспатчатся в `0x245a`. Детали — §64.

### 2.5 Вердикт по расшифровке main-app

**Невозможно из файла** (§6.2, §43.4): нужен SWD/XIP-дамп на живом чипе (SCEK в eFuse) или
FOTA-захват. Прикладной протокол BLE реверсится по **APK/плагинам Mi Home** (Глава 6), не
по этому образу (§46.2).

## Глава 3. MCU: протокол USART3 (MCU⇄BLE)

### 3.1 Архитектура связи (§31.1)

```
Mi Home (APK) ⇄ BLE-чип (RTL8762C, APP-регион ЗАШИФРОВАН, §30)
    ⇄ [USART3 0x40004800: RX телеметрии + данных-канала; TX запросов/push]
    ⇄ [UART4  0x40004C00: TX ответов данных-канала]
MCU (data-driven, §26.2) → ADC ISR 0x1a31c = системный тик (~1 кГц)
    → 0x1d3d0 → 0x1f600 (TX USART3) → 0x216e4 (TX UART4) → 0x1a5c4
```

### 3.2 Форматы кадров (§31.2)

| Направление | Кадр | Значение | § |
|---|---|---|---|
| BLE→MCU (USART3) | `74 CMD LEN DATA CHK 8B` | телеметрия C41..C4A, C60, C61 (класс A) | §16 |
| BLE→MCU (USART3) | `74 CMD 4F 4B CHK 8B` | OK-ответ (класс B) | §16 |
| MCU→BLE (USART3) | `63 CMD CHK 9C` | запрос телеметрии (сборщик 0x1f1cc) | §16/§32 |
| MCU→BLE (**UART4**) | `61 30 0A … CHK 9E` | push статуса (0x211f8, кольцо @0x10b5) | §22/§33 |
| BLE→MCU (USART3) | `51-54 SUB LEN DATA CHK TRAILER` | данные-канал, Path A (set) | §23 |
| BLE→MCU (USART3) | `51-54 SUB (HDR+SUB)&FF TRAILER [DATA]` | данные-канал, Path B (get) | §23 |
| MCU→BLE (UART4) | `LEN 64/65 SUB DLEN DATA CHK TRAILER` | ответы данных-канала | §23/§28 |
| BLE→MCU (USART3) | `5A …` | сессия/калибровка: 0xa1 recalib, 0xa3/0xa4 master, 0xae версия | §24 |

CHK Path A = Σ(frame[0..LEN+2])&FF; TRAILER = 0xFF−HDR. Заголовки 0x51..0x54 идентичны (§29).

### 3.3 RX-путь (BLE→MCU)

| Функция | Роль | § |
|---|---|---|
| `0x1e480` | USART3 RX ISR — побайтовый фреймер (доказано исполнением) | §16.4.1 |
| `0x1e9e0` | RX-диспетчер — ступенчатая машина, полная карта «поле→RAM» (15 CMD) | §16.4.3/§59.6 |
| RX-кольцо @0xc05 | шаг 0x96, reader @0x2c8, flag @0x2c7 | §31.4 |

### 3.4 TX / UART'ы (MCU→BLE)

| Функция | Роль | § |
|---|---|---|
| `0x1f600` | TX-планировщик USART3 (описатель @0xa43, шаг 0x96) — полностью разобран | §6.7/§28.2 |
| `0x216e4` | отправитель TX-кольца UART4 (@0x10b5) | §28.3 |
| `0x1f6b4` | инициализация USART3 | §28 |
| `0x1f1cc` | сборщик TX-запросов `63 CMD` (все 63, CHK=0x63+CMD) | §32 |

### 3.5 Данные-канал приложения (кадры 0x51..0x54)

- **Path A (set):** sub 0x10..0x16 (конфиги #1/#2/#3, RTC), 0x18 (флаг), 0x19, 0x1a
  (конфиг #3 → расшифровка @0x16aa, §27), 0x1b, 0x53.
- **Path B (get):** sub 0x20..0x2f, 0x35, 0x36 (u16@0x32e/0x330 — «счётчики», писатель
  только живой, §26), 0x50, 0x51 (версия "PA68407 V0007").
- Агрегатор `0x1f71c` (jump-table, 32 подкоманды) — §22.5/§23.2/§36.6.

### 3.6 Событийный канал 0x5a (сессия/калибровка)

Сессионные флаги @0x339/@0x33a; подтипы: 0xa1 recalib, 0xa3/0xa4 master-значение (fan-out),
0xae "PA68407 V0007". Мастер-значение + fan-out проверены численно (§24.3).

### 3.7 Push `61 30 0A …` (MCU→BLE, UART4)

| Функция | Роль | § |
|---|---|---|
| `0x211f8` | push-сборщик (пролог), полевая карта | §34 |
| кадры 'a'/'a0'/'a1' | телеметрический канал: 'a0'=телеметрия 16Б, 'a1'=батарея 15Б | §47 |

Только подтип 0x30, уходит по UART4 (корректировка §33).

### 3.8 Телеметрия-CMD + слой siid/piid

Полная двунаправленная таблица телеметрии-CMD (заголовок `74`) — §35.1/§35.2. Спецификация
Mi Home (siid/piid) живёт в плагине/DEX, не в MCU (§35.3).

### 3.9 Протокольный референс (сводка)

Полная шпаргалка — **§31** (архитектура, кадры, RAM-адреса, индекс функций, открытые вопросы).

## Глава 4. MCU: функции по подсистемам

### 4.1 Моторный контур (крупнейшая подсистема)

**Вердикт:** это **FOC-регулятор PMSM/BLDC** (§59.9/§60), а не «батарейные пороги» и не
трапеция (коррекция §6.5). Полная цепочка regulator → slew → duty% разобрана (§41);
runtime-применения к TIM1 CCR в образе НЕТ (§41.4 — duty% уходит на мониторинг/телеметрию,
применение на железе вне образа или DMA).

| Функция | Роль | § |
|---|---|---|
| `0x1a938` | **моторный FOC-рутин** (3296 Б, крупнейшая): TIM capture → векторные операции → секторная коммутация → PWM-вывод. ВСЁ разобрано+верифицировано | §59.9/§60 |
| `0x1be1c` | TIM capture → FOC реконструкция фазных токов (6-секторная) | §60 |
| `0x1e410` | табличная декодировка Q15 @flash 0xA6C6 | §60.1 |
| `0x1d7ac` | cross+dot, X из таблицы | §60.1 |
| `0x1d818` | cross+dot / 2D rotate, X из RAM+0x10c | §59.9/§60.3 |
| `0x1bd88` | 6-секторный FOC-классификатор | §60.2 |
| `0x7494` | **motor parameter setup** (1282 Б): clamp входов [1000,5000] → интерполяция `sdiv(d×(mn−3200), u16(1000−d))` → bit-gated window-gate + табличная интерполяция 0x16fde + /100. Working-struct RAM+0x2fec | §66 |
| `0x799c` (slot 2) | регулятор: mode=getter 0x8f58, lerp 0xe160, `round((10000−sensor)×2443/10000)`, clamp [−2752,10000] → i16@RAM+0x13a8 | §41.1 |
| `0x7a30..0x7d60` (slot 3) | state-machine над выходом регулятора (TBB @0x7aa0, таблица @0x7aa4) | §41.1 |
| `0xe408` | **двухсторонний slew-limiter** (рамп с ограничением скорости изменения) | §39.5/§41.1 |
| `0x162ce` / `0x16222` | signed division (с округлением) в регуляторе | §41.1 |
| `0xe658` | вторичный round-robin диспетчер (группа BLE/моторных задач); vendor-dispatch @0xe684 | §57 |
| `0x1e3a4` | safe-stop / park | §39.4 |
| `0x1d640`/`0x1bf48`/`0x1c1ac` | мотор-инициализация (периф @0x48000000) | §59.5 |
| TIM1 init | инициализация моторного моста (раскладка +0x10: PSC=0x30) | §39.2 |

**Ключевые RAM (мотор):** st+0x20=i16@RAM+0x13a4 (sensor), st+0x24=i16@RAM+0x13a8 (out),
u16@RAM+0x12a7/0x1357 (prev/out), byte@RAM+0xfd3 = duty% (0..100), флаги @0xa5c/@0xa5e.

| `0x11bac` | date/time formatter (остаточная цепочка, делители [31104000,2592000,86400,3600,60], 100/100) | §61 |
| `0x17170`/`0x17214` | i16×i16→i64 ([arg2]=HIGH, [arg3]=LOW) | §50.3 |

**Важно:** MCU использует **software long-division** (не hardware sdiv) несмотря на
Cortex-M4F — основа всей fixed-point математики (§67).

| Полка | Функций / байт | § |
|---|---|---|

| 13–64 Б | 267 функций / 9 444 Б | §49 |
| 65–128 Б | 141 функция / 12 518 Б | §50 |
| 132–256 Б | 98 функций / 17 840 Б | §51 |

## Глава 5. MCU: эмуляция и верификация

### 5.1 Метод (§16)

Unicorn-эмуляция реальной прошивки (emulator/mcu_emu.py): flash @0x08000000, RAM
@0x20000000, периферия замаплена. Граница функциональной эмуляции — §16.2; широкая
эмуляция от init упёрлась в отсутствие точки входа (data-driven) — §16.3.

### 5.2 Верификация каталога: 149/149 тестов PASS

Батчи эмуляторной верификации (§50.7→§59.8): RAM-accessors, set/clear, структуры,
memset, RCC/FLASH, fixed-address getter'ы, wait-циклы, clock-OFF (I2C/DMA), NVIC/SCB,
busy-delay, AFIO remap, GPIO-dispatch, «частично»-функции, «own» round, периодический
таск USART3, FOC-подфункции. Итого **149/149 PASS** (рост: 22→56→86→98→109→111→112→
115→120→121→125→129→…→149).

### 5.3 Чиповые отклонения от ARM (важно для всех тестов)

| Отклонение | § |
|---|---|
| `bls/CC` = ≤ (включая равенство!), `bhi/HS` = > строго | §59.2 |
| RAW-shift: сдвиг по регистру со счётчиком ≥32 → 0 | §58 |
| Bcond encoding D0xx — нестандартное кодирование условных веток | §59.6 |
| Context slot stride = 0x96 (150 Б) | §59.6 |
| Vendor-dispatch @0xE684: невалидный TBB по стандарту ARM | §57.3 |
| TBB [pc,r0]: PC = (addr+4)&~3 (эмпирически, НЕ +2 по спецификации) | §41.5 |

### 5.4 Методологические находки (баги инструментов)

- **Unicorn 2.1.4:** баг сдвига по регистру при большом счётчике (§50.7); register IDs ≠
  архитектурные (R0–R9 = 66–75, R13=12, R14=10, R15=11) — §55; `bl` не пушит lr (§56).
- **Capstone:** систематически ненадёжен для literal-pool оффсетов и odd-start сдвига;
  эмуляторный трейс — единственный авторитет (§53.2/§59.2).
- **set-then-clear = forced clear** (паттерн «clock OFF»); `bx lr` с вручную записанным
  LR «падает вниз» в этом билде Unicorn (§58).

## Глава 6. Телеметрия / Mi Home

### 6.1 Чтение телеметрии (live)

- Инфо-канал 0x001c: перебор 256 опкодов (`probes/mcu_opcode_sweep.py`) — §6.12.
- **MIoT-спека: телеметрии нет** (авторитетно) — §6.12.2.
- Путь через плагин Mi Home: полная карта телеметрии `modules/10724.js`, транспорт
  0x001a/0x001b каналы 6/7 — §6.13.
- **Телеметрия прочитана** (live): батарея/скорость/пробег; единицы установлены
  проверками — §6.14.

### 6.2 Форматы плагинов / APK

- Плагин = чистый JS, без нативного кода (§6.13.2); ключа прошивки нет, крипта нативная
  (§20.1).
- **Журнал поездок** — главный результат декодирования плагина (§14).
- Ограничение скорости по региону — клампинг в приложении (§14).
- Бинарный формат spec-кадра (реверс `buildBytes`, DEX) + шифрование `BleSecurityChipEncrypt`
  отреверсено точно (§6.13.6/§6.13.8).

### 6.3 Live-сессия (самокат включён)

Полный свип свойств 88/88; SIID_6 LOG_1..LOG_5 = журнал поездок (декод по 10463.js);
SET-механика верифицирована live; пуши свойств — отрицательный результат; build-строка =
номера единиц партии + кастомный S-box в трейлере (§45).

### 6.4 Процедура привязки (bind)

Первый живой снуп: последовательность привязки за ~599–602.6 с (§21). Характеристика
`0x0005` = привязка (§20.5). **OOB_CODE — секрет** (§6.14/§37.5).

### 6.5 Подписка на пуш (CCCD)

Механизм = CCCD, уже есть в транспорте (§18). RX-путь работает (доказательство §18.2).
