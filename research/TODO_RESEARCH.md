## A. Статический RE (из файлов, без железа)

- [ ] **BLE APP: проверить Realtek SDK default OTA AES-ключ.** Поиск в SDK/сообществе
      фиксированного OTA-ключа; если Dreame не менял — `ble_2.7.0_0015.bin` расшифровывается
      программно (IV-кандидат — `header[0x0c:0x1c]`). Шансы низкие (§19.2: ключ per-chip из
      eFuse), но это самая дешёвая проверка. *Открывает:* всю логику BLE-app (payload'ы
      C42..C46, канал 0x51, siid/piid-слой). — §6.10, §19.2
- [ ] **MCU: применение duty к мотору (остаток §39).** Стейт/регулятор картированы (§39.5):
      `0x0799c`→стейт-машина 0x07B5C→**slew-limiter `0xe408`** (feedback u16@RAM[0x1357])→пороги
      500/9496. Цепочка работает в **round-robin-диспетчере `0xE658`** (TBB, счётчик @0xA62,
      гейты RAM[0xA49]/RAM[0x35]; вызов 0x129C0→0x12470→0xE658) — подтверждено исполнением
      с seed гейтов: на холодных данных слот-2 выдаёт сентинель 0xFEED (входной lerp `0xE160`
      по 7-точечной таблице flash @0x19FD8 вырожден). НЕ найдено: запись в TIM1 CCR1/2/3
      (+0x44/48/4C, layout +0x10!) и применение u16@RAM[0x1357] к периферии — ни pool-ссылок,
      ни при исполнении. Осталось: (а) live-снуп TIM1 CCR/DMA (B-класс), (б) полный
      boot-эмуляция с seed «живого» стейта (гейты + lerp-вход + рукопожатие M[0x319]=3),
      (в) проверка отдельной платы привода. Таблица @0x17d3a (8×8 нибблов после `55 AA`)
      — без кодовых ссылок. — §39
- [ ] **MCU: физический смысл 3-проводной шины режима** (пины 6-8 порта1, `byte@0x26b`;
      джамперы/BMS/свитч?) + расширенные биты кастомного DMA (0x5D000041, контроллер
      @0x40022000). Живой снуп / даташит. — §40.7

## B. Живое устройство (снуп USART3 / Mi Home)

- [ ] **siid/piid ↔ CMD 0x41..0x4B.** Mi Home read/write свойств + параллельный перехват
      USART3. *Открывает:* полный маппинг «приложение ↔ MCU» (MCU — поставщик сырых
      значений, BLE-чип — GATT-слой). — §35.3
- [ ] **Живой пуш-захват.** `python probes/spec_listen.py --secs 120` на включённом самокате
      с активным изменением состояния (газ/свет/движение) — механизм и парсер готовы,
      не хватает поймать реальный пуш на проводе. — §18
- [ ] **FOTA-захват из Mi Home (обновление BLE).** Пакет приходит расшифрованным/подписанным
      → формат подписываемого манифеста становится ясен. *Закрывает:* §30.3, §30.7 и часть
      вопроса по BLE-app (§30.6). **Дополнено (§38):** trust anchor уже найден в образе MCU —
      X.509-цепочка Mijia Root→Mijia Open→cert + ECDSA-подпись (P-256), публичные ключи
      извлечены (`scripts/mcu/tmp_certs/`) → подпись захваченного пакета проверяется офлайн.
      — §30.6, §38
- [ ] **u16@0x2000032e/0x330 (get 0x36).** Читатель найден: sub 0x36 → ответ `64 36` (§36.5);
      CPU-писателя в образе нет (§26.4) — USART3-снуп (+ динамика во времени) или SWD-RAM.
      *Открывает:* единицы и источник значения. — §31.6.1, §36.5
- [ ] **Живая верификация «own»-рукопожатия.** Статика (§37): инициатор — BLE-чип
      (кадры `64 6F 77 6E 20 <cmd>` = "down …" по USART3, стейт-машина M[0x180]:
      0→0xa→0xb→0xc→0xd→0xe). Осталось: **когда** (power-on / bind / периодичность);
      снуп USART3 в момент power-on/bind. *Модель `crypto_own.py` позволяет офлайн
      вычислить любой ответ MCU* — нужен только сид: GET sub 0x2A (`64 2A`) из Mi Home
      (возвращает @0x871..@0x880) + сверка снупленных кадров 'b'/'m' с моделью.
      *Открывает:* роль шифроблока `0x21c64` и маски @0x1565 в связке с BLE-чипом. — §36.2, §37
- [ ] **Направление переключения режима TX-кольца (432↔80 тиков) при byte@0x358=1.**
      До/после «own»-обмена; снуп UART4 + USART3. — §28.5, §36.4
- [ ] **Blob-конфиги @0x84b/@0x85d/@0x871.** Захват кадров 0x15/0x16/0x1a из Mi Home при
      реальной привязке + дамп @0x16aa после расшифровки (или разбор APK-генератора). — §23.4, §27.4
- [ ] **Единицы push-значений.** i16@0x31c / i16@0x290 (обработанные ADC-каналы) и
      u16@0x236 (=val×100/208, %) — корреляция с датчиками по живому снупу. — §34
- [ ] **Режимы `byte@0x229` (0x02/0x03/0x0B).** Смена speed-limit в Mi Home + наблюдение
      @0x229 и кадров push. *Открывает:* state-машина режимов ~`0x1d0c6`. — §34.2
- [ ] **Абсолютные единицы `i16@0x17a0`.** Калибровка [415..535]→% известна, «сырьё» — нет;
      живой снуп. — §31.6.3
- [ ] **RAM-записи RX-хендлеров 0x40/0x63 (группа A).** Эмуляция заблокирована data-driven
      вызовом (§26) — живой снуп. — §31.6.9
- [ ] **Мастер V и i16@0x272 [1876..2275] (канал 0x5a).** Физические единицы + кто генерирует
      0x5a-кадры (BLE-чип по своим датчикам или ретрансляция команд приложения). — §24.4
- [ ] **ADC buf[0..4] + канал-триггер.** Физические сигналы (пины → датчики): схема/

- [ ] **Блок `0x40023c00`.** Природа (BMS-мост / специализированный фронтенд?) и единицы

## C. Аппаратный доступ (SWD / UART-тест-точки)

- [ ] **SWD-проба RTL8762C (BLE).** Сначала физически проверить, отвечает ли SWD вообще
      (Level 0? / за паролем?) — до любых чтений. Если открыт → дамп XIP-региона
      `0x0180E000` (100 КБ) = **расшифрованное BLE-app** (чтение идёт через шину с
      inline-декриптом, ключ знать не нужно). Метод: ST-Link/J-Link + OpenOCD
      (`debug/rtl8762c.cfg`, TAPID `0x2ba01477`). *Закрывает:* главный блокер BLE-части. — §6.11, §19.2
- [ ] **SWD-проба GD32 (MCU).** ⚠️ На 4 Pro RDP включён: сначала статус RDP **без unlock**
      (unlock уничтожает flash — дамп может быть деструктивным). Если открыт → полный образ
      с вектор-таблицей (снимает блокер широкой эмуляции §16.3) + рантайм-RAM: таблица
      команд @0x20000A43, счётчики, NVM (шаблон 4 Pro: SN@0xa8, UUID-привязка@0x1b4,
      пробег@0x52). — §17
- [ ] **UART-дамп RTL8762C через rtltool** (тест-точки GND/RX/TX/RST/LOG, LOG→GND при сбросе).
      Приоритет низкий: при XIP-шифровании дамп = шифртекст (§6.11); полезен для сверки
      flash-раскладки/OEM Header и как дешёвая проба «OTA AES Key» (транспортный ключ §19.1). — §6.10, §19.1–19.2
- [ ] **Писатель @0x33b (16 Б, источник XOR-маски «own»).** В данных-канале только читается;
      статических писателей нет → SWD-RAM (дамп @0x2000033b до/после «ok»-обмена) + сверка
      с NVRAM-картой. — §36.2, §36.7
